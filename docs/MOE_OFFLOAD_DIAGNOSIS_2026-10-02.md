## 2. 必须先处理的实现问题

### A. 关闭 3b 的回退路径构造了错误任务（已复现，P1）

`src/quant/moe_residency.cpp:1609`：
`tasks.emplace_back(off + t, off + t + 1)` 选择的是
`vector<int>(count, value)`，并非单元素任务。

当 `Q4T_MOE_PREAD_MERGE=0`、首批 n=1 时任务为空，却仍推进
`next_stage/next_commit`；n=2 时第二任务索引为 2，越过长度 2 的
plan；n=16 时产生 120 个条目而非 16 个，并有越界索引。
因此该开关目前不能作为安全回退。正常 3b=1 的成功结果不覆盖此路径。

host-only C++23 复现（零警告、无 CUDA、仅打印不执行越界访问）：
`.q4t-work/offload-audit-20261002/pread_merge_rollback_semantics.{cpp,txt}`。
修复应明确构造 singleton，并覆盖 off=0/off>0、1/2/16 条任务的
完整索引排列合同。

### B. 合并读取的短读重试写错位置（代码确认，P1）

`src/io/safetensors.cpp:290–311` 的 `ReadRangev` 在短读落入某个
iovec 中部时只更新 `off`，下次 `preadv` 没有同步前移该 iovec 的
目标指针或缩短长度。文件位置向后而目标从头写，可能覆盖前缀、错位，
继续请求超过剩余范围。正常本地文件一次读满时不会触发。

应以注入短读/EINTR/EOF 的 host 合同修复；已有 108/108 与常规
输出一致性不能证明这个异常分支正确。本轮未注入实际 I/O 短读。

### C. 分片驱逐缺少读期间的所有权保护（代码确认的条件风险，P1）

`src/io/weight_loader.cpp:132–170` 在锁内取 `Shard*`，随后
`ReadTensor/ReadRange/ReadRangevShard` 在锁外使用；另一 worker 可以
`open.erase(victim)`，销毁仍在读取的对象或关闭 fd。

最终配置 200 覆盖全部约 197 分片，规避了这一驱逐条件。较小上限在
同时活跃分片多于容量时没有安全保证；不能把默认 32 曾经发生的
reopen 性能问题写成已经实测发生 UAF。应使用读期间持有的共享所有权
或 pin/lease，另做小缓存、跨分片并发复现，而非靠永不驱逐掩盖合同。

### D. 其他有界合同缺口

- `InitHot`（`moe_residency.cpp:1358–1364`）用尚未提交的
  `expert_slot_` 检查本批重复，实际不能去重。现有重复列表测试只验
  数量，未验最终 distinct 集合。部署热点文件已校验无重复，当前
  生产候选不由此证明受影响。
- 故障钩子在 `ClaimExpert` 的前置位置报错；现有恢复检查不能覆盖
  部分 H2D 入队后失败。`CommitExpert:1286–1336` 的失败返回可能
  留下部分覆写的槽位和旧身份；镜像 D2H 失败后的旧映射/在途 buffer
  也需明确处置。这是未实测的故障合同边界，应定义槽位失效、等待或
  服务不健康规则后做对应注入。

## 3. 内存与 I/O 口径需要纠正

**68.34 GB 是现有脚本算出来的数，但不能称为包含模型页缓存的物理峰值。**

`tools/acceptance/c3-pagecache-protocol.sh:221–246` 使用
`Cached(post-matrix) − Cached(post-load)`；后者已包含模型加载形成的
缓存，前者还是矩阵服务退出后的快照。

| C3 候选快照 | Cached（KiB） |
|---|---:|
| drop 后 | 211220 |
| 模型加载后 | 57887272 |
| 预热后 | 68780072 |
| 矩阵服务退出后 | 65002984 |

加载期增长约 59.06 GB 被扣掉，最终仅加入 7.286 GB；矩阵监控的
全机 Cached 峰值为 76.94 GB。`final-acceptance.sh:109–158` 再把
7.286 GB 加到 RSS+GPU 峰值 61.056 GB，得到 68.34 GB。它既漏掉
加载期缓存，也不是各组成项在同一时刻的总峰值。

不能简单把 59 GB 补上就宣布另一个权威值：Cached 是全机数，必须
处理模型归属、RSS file 页与页缓存的重叠，以及 Thor CUDA/pinned
计数的交叠。当前应保留各原始量，标记“含缓存总峰值待重算”，不能
继续用 68.34 GB 作为已证明的内存中性上限。用户接受 C=256 超支的
授权保留，但授权不证明测量公式正确。

`monitor_memory.py:230` 还把已是 bytes 的 gpu 字段再乘 1024 写入
`peaks_bytes.gpu_bytes`；独立 `gpu_peak_bytes` 与本次 gate 用的
`service_total_physical_peak_bytes` 不受这项单位错误影响。
另 `c3-pagecache-protocol.sh:205–215` 将 pread_avg_us 原值写入
warm_pread_avg_ms；433.144 的实际单位是 μs，字段名错了 1000 倍。

`nvme_read_bytes/nvme_mb` 实际累计的是请求读取的文件字节：页缓存
命中同样累计。目标档约 7.89 TB 不能解释为 SSD 实际读了 7.89 TB。
后续应分开记录逻辑文件读取、块设备实际读取、H2D、镜像 D2H；暖缓存
E2E 可以证明暖缓存性能，不能据此证明受限 RAM 下的真实 SSD 吞吐。

## 4. 当前优化方法的主要偏差

### Prefill 的重读有结构性下界

`moe.cu:416–429` 已拿到该层整个 forward 的路由；目前按专家 ID 集
的字典序排列 token（465–470），贪心切到 distinct≈C（507–536）。
`PlanResolve` 会保护本子块全部专家。若相邻集合均约 256、槽位也是
256，则下一块至少换入 `|S_next − S_current|`；驱逐算法几乎没有
选择空间。

所以相邻块约 70% 重叠不能推出“LRU 把这些重叠专家逐出了”。应先
量化当前分区下不可避免的换入与额外错失，比较固定分区的理想驱逐
上界，再研究块排序/分区。此前日志和提交说明对该归因过强。

17.28 倍是 45056 预热请求的 loads/24576，目标 261887 档约
117.6 倍。它不是按请求实际 distinct 去重的精确“重复读取因子”，
不同长度不能共用同一个目标基数。

### Phase D 混合了不同统计单位

`ObserveRouterWeights`（`moe_residency.cpp:1415–1435`）每次 layer
forward 只增加一个时钟，却累加该批全部 T×k 路由权重。同专家同批
再次命中时不再衰减；8192-token prefill 累加大量权重，1-token
decode 也只算一 tick，并且统计跨请求保留。

这不是统一 token 时间尺度的 EMA。更大的 router 权重也不直接代表
更大的加载收益：被选中的每个专家仍须完整执行和读取同样大小权重。
应分开 prefill 的已知未来访问与 decode 的频次/复用距离/加载代价。
直接调整 decay 不能解决单位混淆。

已有干净实验：Phase D on 的 204800/261887 decode 比正式候选下降
5.6%/13.6%，目标档跌破旧 50% 门槛，重读量基本不变。维持 off 合理。

### L2 与镜像需看净收益

L2=16 存的多是刚装入 GPU 的副本；GPU 下一次 miss 所需的专家未必
在这 16 个副本里。L2 命中为零不能单独证明其 LRU 是主要瓶颈，盲目
增大 L2 又与内存目标冲突。

当前 `CommitExpert:1189–1264` 不分 prefill/decode 地尝试镜像被
驱逐权重。d0 已完成的 261887 run1 有 mh=36347、mw=2027096：
约 5.60 TB D2H 写回换来约 0.10 TB 文件读取避免，命中/写回约 1.8%。
这些是逻辑流量推算，不直接等于可节省的延迟；但支持优先检验
prefill 禁止无效镜像或按已知 next-use 选择写回。K0/K8 的旧验证
不能代替 C5/C6 暖缓存条件下的当前净收益对照。

### 3b 的现有覆盖率有限

`LoadPhase1:1573–1605` 先取最多 16 个 miss，再在这 16 个内部排序
合并，未利用整个 plan 的邻接性。d0 目标档 run1 合并覆盖
207119/2890981≈7.2%，平均每 run 约 2.06 专家；降低调用次数的
潜力有限，增大合并 cap 还可能降低 worker 并行度。

截至审查，d0 的 204800 三次 TTFT≈694.4 s、decode≈9.90–9.97；
目标档仅前两次 TTFT≈909 s、decode≈9.03–9.12，第三次在途。
这些只支持约 3% 的 TTFT 改善迹象，不能宣布达到 30% 或完整验收。
定向脚本与正式矩阵的预热服务生命周期、先前请求序列、目标档输出
256/257 不完全相同，小幅差异不宜全归因于 3b。

## 5. 离线研究与验收工具的问题

- `tools/trace/capacity_curve.py:145–174` 在每个 split 内重新按
  本 split 的频次选 top；policy/final_validation 的 static/hybrid
  结果使用了自身留出数据。它们只能解释为事后上界，不能作为部署
  留出预测。`make_hot_list.py:55–56` 确实仅用 calibration，未发现
  实际 hot-256 被上述工具污染的证据。
- `.q4t-work/moe-residency-20260930/sim/nonuniform_dp.py:62–93`
  用 HOLD_REQS 建 miss 曲线，再用这些曲线优化 C_l；同批收益应称
  策略选择集结果。它还只回放 decode，省略请求间 prefill 对驻留
  状态的改写，并以逐专家 LRU 代替整组保护，不能直接外推线上收益。
- `tools/acceptance/run-e2e.sh:19` 硬编码 `build/q4t`，C3 传入的
  BIN 只控制预热探针；BASE_BIN/CAND_BIN 的跨二进制矩阵意图可能
  丢失。本次正式矩阵原始摘要都确为 ed68cd3d，因此该缺陷不否定
  此轮已核对的性能事实。
- `compare_e2e.py:105–111,131–135,168–176` 的 all_pass 仅合并
  decode 比例，未合入输出/目标容量/重复次数；FAIL/INCOMPLETE 仍
  正常退出。`final-acceptance.sh:91–95` 未以比较失败阻止后续步骤，
  内存门缺失也可能被当 0。自动脚本退出成功不能替代逐项验收。
- `run-e2e.sh:11,55` 删除同 tag 旧证据，并用非 JSON 文本覆盖
  runner 的 exit.json。下一轮应使用唯一目录、保留原始结构化退出
  结果。实际 Q4T_MOE_* 有效值与热点内容摘要也应纳入同一身份清单。
- `moe.cu:612–616` 以 T_sub==1 认 decode，会把单 token prefill
  尾块计进去；d2h 计时是 router 回读与 stream 同步，包含前序 GPU
  工作，不能解释为独立镜像回写耗时。应从调用者传阶段并统一单位。
- 当前部署说明混有旧 L2=128、下限 8 与最终 L2=16 配置。实际代码
  下限随 worker 数（默认 16）；最终配置需用明确 manifest 固定。

## 6. 建议的推进顺序

1. **收口合同与身份。** 封存 ed68cd3d 及完整配置为已验证参考；新候选
   保持 Phase D off。成组修复 3b 回退、短读、分片读期所有权，补
   精确异常合同；修复验收脚本的 binary 透传与失败退出。Bug 修复
   先做直接测试，再补受影响 HTTP，遵守 EVALUATION，不重跑无关项。
2. **重建内存与流量账。** 从进程启动前覆盖加载、预热、推理全过程；
   同时点记录 CUDA/pinned、进程匿名/file、模型文件缓存与全机 RAM/
   swap，并核对重叠。原始数据可复用的先重算；缺少归属的部分再做
   一次有界采集。不要预先把误算的 68.34 GB 当新上限。
3. **离线建立可实现上界。** 先复现真实 prefill→decode、整组保护、
   跨请求驻留状态与当前分区，再比较固定分区理想驱逐、块重排、低
   换入分区、阶段独立 decode 策略。热点/容量选择与最终评估分开。
   不先增加缓存容量，不只根据选择覆盖率推断加载量。
4. **只选一个在线优化。** 优先检验 prefill 镜像净收益；若其上界不足，
   再做已知路由下的分区/排序。decode 另用频次/复用距离策略；GEMM
   冻结。冻结出口后，性能改动第一项测试仍为真实 HTTP E2E，避免
   一边改多个策略一边重复长矩阵。
5. **统一验收。** 同身份、同输入/输出/服务生命周期/缓存协议；质量、
   六档吞吐、TTFT、完整内存与生命周期分开判定。保留旧失败，重用
   身份和依赖未变的证据。暖缓存达标与受限内存 SSD 场景分别报告。

本轮只新增诊断及文档纠正。所有运行时修复、额外 HTTP/故障注入、
新的总内存测量均未执行；在途 d0 结果应由其原任务单独收尾。
