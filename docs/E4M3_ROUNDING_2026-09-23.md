# E4M3 编码边界审查与候选（2026-09-23）

## 源码发现，不是原错题根因结论

审查独立参考量化合同时发现include/q4t/quant/format.h的
FloatToE4m3与同文件解码公式/最近偶数约定不一致：

- 旧编码正常数分支对exp>14直接返回0x7e（448）。解码支持
  exp=15、mantissa=0..6，其中0x78为256；所以精确256被编码
  成448，256..416的其他精确可表示值也受影响。
- 次正规区用int(a*512+0.5)，是半入舍入，不是最近偶数；如
  半个最小步长应舍入0，旧分支得到1。
- 次正规区将结果限制在7，不能在接近最小正常值时进位到
  code8。上述例子来自源码算式推导，尚未运行数值测试。

这些转换用于MoE prefill GatherQuant/SwiGLUQuant和decode
Prepare路径，不是仅测试辅助函数。是否在原4K请求触发、是否
导致其失败尚未知。不能因为格式错误确定，就断言模型错误已定位。

## 参考与旧测试的独立性缺口

quant_fp4_test.cpp的精确roundtrip值有128、448而无256..416；
次正规仅测精确code5，没有半步与正常区进位。其单调性检查不
足以发现把高端整段饱和成448。多个MoE参考计算直接调用同一个
FloatToE4m3，不能独立发现被复制的量化错误。未执行这些旧测试。

门禁后应使用独立枚举的127个有限非负E4M3值及相邻中点/两侧
作为编码真值，核对host/device，同时核对实际CUDA格式转换；
不要让参考再调用待验证转换器。未准备或运行该低层测试。

另外，tools/verify/ref_dump.py注释称BF16专家参考，但实际
_dequant_one_expert保留numpy float32，模型默认float32，激活
没有NVFP4量化，也没有迁移GPU的代码。它是局部CPU语义参考，
不能作为完整等量化HTTP生成oracle。已有SGLang路径归并专家
down输入尺度的差异仍存在，此发现没有消除这些参考局限。
