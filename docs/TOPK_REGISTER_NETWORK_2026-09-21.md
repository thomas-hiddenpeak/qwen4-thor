# 流式 top-k 网络寄存器化候选

日期：2026-09-21。基线 f12ec90，完整 E2E、精确专项与时间线通过，已接受。

## 选择依据与改动边界

已接受的 sparse-padding 阶段 200K HTTP 时间线中，流式合并累计
约 34.079 秒，是长上下文 prefill 的主要成本之一。其后改动集中在
普通 decode 与分配策略，当前完整 E2E 的 200K TTFT 仍约 181.85 秒。
旧时间线用于选择假设，不替代本轮候选的验收与归因。

仅修改独立 `src/model/streaming_topk.cu` 的 BitonicSortAscWarp。
每 CTA 256 线程；线程持有索引 i=threadIdx.x+r*256 的元素。
原比较网络各层 k 与距离 j 的顺序保持不变，分值与 ID 一起交换：

- j>=256：伙伴 i xor j 属于同一线程，可在寄存器数组内比较交换。
- 32<=j<=128：伙伴跨 warp，仍写 shared，沿原成对比较代码执行。
- j<=16：伙伴在同一 warp，保持原 shuffle 与严格比较规则。

跨 warp 阶段结束后读取 shared，显式同步后才允许下一层覆盖；最终
所有寄存器结果写回 shared 并同步，再由原 kernel 取 top-512/合并。
候选覆盖、分值计算、top-k 大小、全局 ID、输出布局均未改动。

同分时仍使用原严格比较，源码意图是逐位及 ID 等价，不采用近似
选择或重新定义 tie-break。该意图必须由完整 E2E 后的精确专项核对。
寄存器压力与指令展开是本次权衡，资源实测见下；不能仅从源码
shared 往返减少推断收益。

## 时间线与资源

对照为已接受 sparse-padding 阶段 200K 时间线；其后 HC 等提交主要
改普通 decode，不能用两个时间线的 decode 差异归因于本次排序。
以下只比较 prefill，全部 kernel 调用数均为 2265857。

| prefill 项目 | 旧累计秒 | 新累计秒 |
|---|---:|---:|
| MergeChunkTopkWarpKernel（3888 次） | 34.078671 | 19.549222 |
| SparseAttentionKernel（300 次） | 35.408 | 35.406 |
| GatedDeltaNetRegKernel（900 次） | 33.557 | 33.552 |
| prefill 时间窗口 | 184.185 | 169.802 |

合并累计下降约 42.64%，少 14.53 秒；非目标两大 kernel 基本持平。
这支持主要 TTFT 收益来自流式合并，但累计 kernel 时间与墙钟窗口
不同，不将两者相减作为严格因果分解。

Nsight 同一 kernel 的 registersPerThread 26→48，staticSharedMemory
均 24576 字节；cuobjdump 对旧二进制/新对象均报告 STACK=0、LOCAL=0，
SHARED=25600 字节。两工具 shared 字段口径不同，原始报告均保留，
不混算；也不将 trace 的 localMemoryTotal 汇总字段当成 spill 证据。
没有采集 DRAM 计数，不能据此给出实际物理带宽或缓存命中率。
