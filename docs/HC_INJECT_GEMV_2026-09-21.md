# HC 四输出投影：形状驱动的 decode 优化

日期：2026-09-21。完整 HTTP、逐位专项与时间线核对完成，接受此改动。

## 从已接受时间线选择目标

来源：已接受 c215f74 阶段的 1K HTTP 时间线
`.q4t-work/e2e/moe-routing-slab-20260921/timeline/`。
255 次 decode 中 Bf16GevKernel 累计 9.923 秒，占 kernel 累计时间
60.92%；这是累计时间口径，不是墙钟关键路径占比。

从 gridX、dynamicSharedMemory 与源码分派核对形状：原 kernel
每 CTA 8 个输出，shared 大小为 2K 字节；N=4 由 HC 调用点确认，
其他下表形状均是 8 的倍数。

| N × K | 每步调用 | 平均 kernel 微秒 | 逻辑权重字节/时间 GB/s |
|---|---:|---:|---:|
| 10240 × 2560 | 37 | 211.354 | 248.06 |
| 248320 × 2560（输出头） | 1 | 5039.653 | 252.28 |
| 4 × 10240（HC inject） | 96 | 15.537 | 5.27 |

比值用每次 2NK 字节计算，不是 DRAM 硬件计数，不处理缓存命中或
访问放大。它与源码共同提示：大投影已经有效读取权重，小输出投影
不适合直接套满带宽假设。HC inject 每步累计约 1.49 ms，目标有界，
不能从局部改进宣称整个 decode 发生数量级提升。

## 候选实现与不变量

原 N=4 投影使用一个 256-thread CTA，其中四个 warp 有有效输出；
先把 x 协作载入 shared，再每行执行固定顺序的 f32x2 FMA 和 shuffle。
候选使用四个 32-thread CTA，每 CTA 一行，直接读取 x，取消 shared
staging 和 CTA barrier。每行 lane 对应的 K 元素、FMA 次序、两路
累加合并、shuffle 顺序、alpha 与 BF16 舍入均保留。

新 kernel 在 `src/model/gemv_hc_inject.cu` 独立编译。仅 N=4/K=10240、
x/w 都 16 字节对齐时由 Bf16Gev 分派；其余形状及未对齐输入继续
原 kernel，prefill GEMM 路径不变。权重、精度、MTP 设置均不改变。

直接读 x 与原 shared 路径的访问方式不同，四个 CTA 是否改善实际
耗时仍需 E2E 和后续时间线判断。每行累计顺序相同是源码设计约束，
不是替代逐位验证的理由；新 kernel 的数值专项在完整 E2E 后进行。

## 验证记录

证据目录 `.q4t-work/e2e/hc-inject-gemv-20260921/`。
必要构建零警告，首测 1K HTTP 三次均值 16.951 tok/s、输出一致。
随后质量 11/11、性能 15/15 通过，输出摘要一致，服务正常退出。
MTP 关闭，单流、每档三次、256 输出；未运行前置单测、bench、
数值微测试或 profile。旧二进制、候选 patch、新 CUDA 文件快照和
二进制分别保存；新文件尚未跟踪时不能只靠 worktree.patch 复原代码。

| 上下文 | TTFT 均值秒 | decode tok/s | 对固定参考 decode 均值变化 |
|---|---:|---:|---:|
| 1024 | 0.843508 | 16.937039 | +0.258% |

TTFT 包含 HTTP 与 tokenization，不等于纯 prefill。decode 用总
(output−1)/总(latency−TTFT)，不是三个速率的算术平均。各档新旧
TTFT 和 decode 重复范围重叠；未见可辨识回退，但不能宣称这些小幅
均值差是稳定 E2E 提升。完整范围见 `comparison.json`；正式速度参考
仍沿用 sparse-padding 阶段，不因这次小幅均值上升而重置。

完整 E2E 后，`tools/verify/compare_hc_inject_gemv.py` 从 e3c8225
提取原 kernel、从接受快照提取新 kernel，在本机 CUDA 比较普通随机、
小值、大值、零、正负零、抵消、BF16 subnormal 等输入和四种 alpha。
1024 组、4096 个 BF16 输出逐位相同，无非有限输出；不是全面模型精度
证明。首次工具构建因 BF16 memcpy 触发警告而停止，改为 std::bit_cast
后零警告通过，未修改运行时代码。原失败证据在 `numerical/`，成功
结果在 `numerical-fixed/`，均保留。

## HTTP 时间线与接受决定

完整验收后采集 `timeline/context-1024/trace.sqlite`，采集、导出和服务
退出均成功。256 输出对应 255 次 decode，专用 kernel 24480 次，恰为
96 次/步；其他 BF16 GEMV 151215 次。异步分配/释放仍各 554 次/步，
MoE counts D2H 仍 48 次/步，没有借此改动更换分配或同步策略。

HC 累计耗时由已接受旧时间线的 380.338720 ms 降至 342.935904 ms，
平均 15.537→14.009 微秒，减少约 9.83%，每步累计节省约 0.147 ms。
这一局部结果与很小的 E2E 均值变化规模相符，不能推导出稳定整体增益。
新 trace 的 decode 窗口 16.490 秒，旧 trace 16.412 秒；采集有开销且
其他 kernel 也有波动，不把 profile 的请求速度混入正式性能参考。

接受理由：形状专用实现范围明确、计算次序不变，完整 HTTP 未见可辨识
回退，逐位专项通过，真实请求中的目标 kernel 有局部改善。代价是新增
一个约 60 行的专用 CUDA 实现和分派；收益有限，不宣称全局瓶颈已解决。
五档 E2E 与数值专项的覆盖边界保持不变。

下一步继续拆分剩余 BF16 投影的输入搬运、权重读取与归约开销。
输入 staging 的向量化是候选假设，仍需单独完整 HTTP 验收；不因本次
结果推定其他形状适合四 CTA 或直接加载方案。
