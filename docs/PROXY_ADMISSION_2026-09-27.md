# 真实代理与准入预算验收

2026-09-27：完成本地单Nginx、单Runner的有界链路验收。运行时保持
432fc489，未修改内核/服务源码，未更换二进制或正式性能参考。
交付为可复现实验、配置模板和部署边界，不是已启用的公网服务。

## 问题与决策

Runner接受连接后才读取HTTP路由，所有请求共享至少128个线程名额。
实测128条不完整HTTP连接占满后，显式取消返回503。该直连限制仍在。

本轮采用入口准入：生成请求共享4个名额，取消/健康/指标共享另外8个，
远低于后端128连接预算。超额生成在代理返回429，不进入模型排队。
预算使用固定server_name键，不能通过换客户端地址或请求ID绕过。
它验证生成满载时控制可用，不保证控制端点自身洪泛下可用。

模板位于[tools/deploy/nginx](../tools/deploy/nginx/README.md)，仅监听
loopback；Nginx 1.24.0 Ubuntu包1.24.0-2ubuntu7.18仅解压至.q4t-work，
没有安装系统服务。后端仍绑定INADDR_ANY；生产部署必须先阻断绕过
代理的访问，这一网络隔离尚未实施，不能把模板直接视为公网配置。

请求缓冲开启以隔离慢上传，响应缓冲关闭以传递SSE，客户端断连
关闭上游；禁止自动重试生成。上游读空闲期限显式600秒，避开默认
60秒与200K首响应等待的冲突。配置依据见[Nginx代理文档](https://nginx.org/en/docs/http/ngx_http_proxy_module.html)。
这不是总请求期限；四条排队200K可能超过该预算，生产须一起设计
队列长度、应用截止时间与代理期限。

## 最终实测

| 场景 | 结果 |
|---|---|
| 128个后端直连占满 | 取消503，复现保留限制 |
| 4条代理慢上传 | 未增加后端请求线程；健康200 |
| 1条运行加3条排队占满生成预算 | 第5条429，后端请求计数未增加 |
| 生成满额时健康/取消 | 健康200，四次取消202；原请求均409 |
| 首响应前FIN/RST | Runner取消prefill，释放槽位 |
| 首内容后关闭连接 | Runner取消decode，释放槽位 |
| 200K完整代理请求 | 204800输入、7输出，全文711273及stop同参考 |
| 过载后3次短请求恢复 | 全文710003、usage与stop均正确 |
| 收尾 | 两服务退出0，Runner无遗留请求线程 |

四次显式取消受理合计约1.365毫秒，这是本地单次观测，不是延迟SLO。
FIN/RST后观察到取消分别约4.635/4.652秒，需要完成当前GPU分块，
日志确认在8192/45056处停止；不能将202受理速度当作资源释放速度。
200K完整请求约158.519秒，此处是总耗时，不能称为TTFT或纯prefill。

最终证据：`.q4t-work/e2e/proxy-admission-v3-20260927/`。
精确Runner/Nginx副本及清单：`.q4t-work/proxy-admission-control-20260927/`。
工具`tools/verify/proxy_admission/seal.py`在全部进程终态后复核四条
正常SSE全文/usage、负例状态、退出码和哈希。第一轮测试工具误把
配置检查产生的PID文件当作就绪，连接拒绝；修正为真实健康响应。
失败目录及第二轮较小范围成功记录均保留，未覆盖或删除历史。

## 接受范围与下一节点

接受本地单实例的代理传播与生成准入机制；未部署公开入口。
本轮没有生产运行时变更，也没有五档代理性能测试，不宣称代理零
性能开销。Runner此前固定11题与五档基线保持原身份，没有冒充重测。

下一节点优先把后端绑定地址/私有访问约束变成可验证的部署合同，
再评估独立控制入口与连接过载策略，随后进行长时间混合负载和重启
恢复演练。TLS、认证、租户配额、多实例路由、磁盘缓冲总配额、
代理reload和连接洪泛均未验收。[Nginx连接限制](https://nginx.org/en/docs/http/ngx_http_limit_conn_module.html)
只在完整请求头后计数，不能据本轮慢请求体检查宣称解决slow-header。
