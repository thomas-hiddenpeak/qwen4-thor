# 固定热点与动态LRU混合缓存初步分析

2026-09-28，应用户要求，使用现有数据初步判断常驻部分MoE专家是否值得。
没有新HTTP、SSD读取或运行时修改，结果只描述离线逻辑缓存。

## 输入与固定合同

复用`.q4t-work/moe-evalscope-scenarios-20260928/`的24条真实路由（六类
编写任务各四种材料规模），114–13,607输入token，全部输出128且截断。
热点排名来自此前独立冻结校准集的decode频次，不从这24条评估反向选取。
因此本轮比较的是**这份旧decode排名的固定常驻价值**，没有证明业务专用
热点、prefill专用排名或其他学习算法的优劣。样本相关、顺序固定，无生产
总体或语义质量代表性。

每层总容量64/128/256槽，固定区占0/25/50/75/100%，其余动态LRU。
固定区始终驻留，仅在初始化时按完整slot计费；动态区从空开始。
相同容量的总路由预算均为(48×容量+10)×2,765,056字节；10个共享staging
槽、scale和对齐均包含，共享专家/其他权重/KV/workspace等不包含。

每次先按组前缓存算命中，再更新状态。decode消费同层完整top-10，固定
区命中的专家不占动态槽。prefill按同层实际块内专家并集，扣除固定区后
剩余并集能放入动态区才整组接纳；放不下则保留动态区内容与LRU顺序，
缺失专家通过临时区流式消费。这是待验证执行假设，不是现有kernel能力。
动态区同组访问时间相同，按专家ID破同分。没有未来信息、预测预取或免费预热。

prefill_reset每请求同时重置固定/动态区，静态填充每次计费；continuous
只在本批次开始初始化，随后沿完整请求顺序保留。即使常驻，也不把跨进程
缓存状态当作已持久化。总量=初始填充+prefill逻辑加载+decode逻辑加载。
prefill按并集统计命中，同时保留按token路由次数加权的route_hits；不能
把块内多次选中当成同一个专家被重复加载。decode分别统计选择和整组命中。

## 初步判断

1. **长期保留：本轮旧固定热点不如把容量全给LRU。** 在三种容量下，所有
   非零固定比例的汇总总加载都高于纯LRU。256槽固定75%时，选择命中从
   94.57%降至93.58%，整组从66.61%降至62.30%，总量由863.70增至943.65GB。
   这支持当前冻结排名的固定槽位有动态容量机会成本，不证明所有热点
   学习/分层分配策略都无效。
2. **每请求冷重置：256槽混合值得作为候选。** 固定192、动态64槽时，
   decode选择命中86.64%→92.26%，整组43.51%→56.55%，总量1959.58→1779.00GB，
   约减少9.2%；18/24请求改善，最短的1–6号全部更差。64槽混合整体更差；
   128槽固定25%总量与纯LRU接近但略高，不能泛称混合总会更好。
3. **不能把prefill账面下降直接当收益。** 256槽固定75%的冷重置prefill
   加载1419.12→854.47GB，但额外固定填充611.59GB；两者相加反而比纯LRU
   prefill高约46.93GB。总量改善来自decode减少约227.52GB，抵消这部分
   初始/pre-fill开销。固定填充是付费初始化，不是免费命中或未来预测。

因此下一步应区分持续服务与冷请求的策略，不宜直接部署统一固定比例。
本轮还没有prefill专用校准排名、在线因果自适应热点、不同层的固定比例、
真实业务权重或顺序扰动。当前最佳比例经过同批数据比较，只能生成下一轮
假设；若用于策略选择，需要预先固定候选后在新业务留出请求上验证。

数据与方法在当前有界范围内可核查，结论需带以上限制使用。不会由逻辑
加载推导SSD带宽、吞吐或实际offload可行性，原性能不持平结论仍保留。
