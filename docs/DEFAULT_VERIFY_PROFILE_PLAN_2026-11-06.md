## 两个问题与固定预算

1. 当前MTP轮次中，主验证相对草稿/extend的耗时是否仍占主要部分？
   用已有MTP事件区间及host墙钟回答，不引用旧版本比例。
2. 主验证内部MoE、GDN投影/状态、QSA及HC哪一组最值得进一步优化？
   用现有layer/subtiming分组，并对照粗/细观测的扰动。不能用API
   阻塞或事件间隙证明GPU空闲、带宽饱和或某一具体kernel瓶颈。

## 计时口径与分析出口

- 普通HTTP用于记录本轮TTFT和decode；插桩HTTP只评估观察扰动，
  不能作为优化收益。单启动/单请求不支持统计非劣或跨任务外推。
- 粗计时按T=4区分主验证，T=1尾部及大T预填充单列；逐轮数与
  draft_counts核对。首轮保留，另列首次与后续轮次，不择优丢弃。
- 细分顶层ple/grread/attn/wrar/moe/write可求和；attention detail
  和MoE detail是嵌套区间，不重复加到总数。不同组观察不可直接
  相加。打印精度0.01ms/0.1ms按事件数给出最坏舍入范围。
- CUDA event记录流上的经过时间，可能含主机提交空隙与观察者
  工作，不等于纯kernel执行。细计时的事件创建、同步及销毁会扰动
  执行；必须公开相对正常/粗组的变化，不把所有残差归因于CPU。
- LAYER_TIMING的head起点在子计时Report之前，同时开启会把
  Report/Destroy空隙算入head。因此fine组关闭它，head仅看coarse。
- 对两个上下文、两个head的排序分别报告；优先选择重复出现且耗时
  占比足以支持收益的一个组，再结合源码给出具体候选与数值风险。
  若扰动/覆盖不足以选择，明确保留未决，本轮不开发通用profiler。
- 输出当前瓶颈排序、观察限制及一个下一阶段建议；本轮不实现
  优化、不做五档接受、不部署或启动长稳，不更改历史NO_GO/ENV_ABORT。
