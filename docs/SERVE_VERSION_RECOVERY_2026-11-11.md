# R06：资格迁移与有界版本回退

2026-11-11。R05已交付rev56。继续总计划，不将同版本重启或重新
发布当前包当成旧版本回退。当前缺口：已启用profile的部署只能
接受同一资格/策略；没有持久版本选择、版本故障判据和自动回退。

## 保持的合同

- 每次只登记当前及一个已经验收的恢复版本，绑定完整封包、二进制、
  模型资产、实测主/轻档资格和业务证据。不同版本仍提供当前声明的
  API、模型/精度、上下文/输出及状态能力，不能删接口换“恢复成功”。
- 运行版本与发布选择分开记录。固定恢复控制根持有租约和原Guardian
  预算；可切换payload包含模型、controller及入口实现。控制根不能
  信任payload自行宣称清理完成；仍独立核对整个旧树及设备身份。
- 原Key、客户端限额、分钟用量、对象/Batch及profile历史保持，不能
  复制历史状态备份覆盖当前状态。新资格迁移不获得停机时间奖励、
  不清预算或伪造过去的配置指纹。停止意图始终高于待回退意图。
- NVML/日志/指标/状态观察丢失、真实设备损坏、磁盘或资源不足不能
  归咎代码版本。只有绑定版本/代次的可靠执行故障符合明确条件时，
  才消费一次持久回退资格；未知信息继续隔离/等待或保留健康核心。
- 一个故障周期最多一次自动回退，不自动反复尝试两版。恢复版本也
  失败则保留故障与预算，进入保护；显式修复部署才可开启新周期。
  控制根本身退出及整机死亡后的接管由R09继续闭合，不能宣称已退出
  代码会复活；R06需保留可接管的持久选择和原停止意图。

## 连续实现子任务

1. **R06.1 资格与迁移合同**：逐项核对旧/新payload能力与状态读写
   合同，精确身份与声明分离；先实现同容量跨二进制/协议资格迁移。
   STOPPED事务持有原部署/Guardian/core锁，先持久意图再迁移，掉电
   可续办，原回执/历史/冷却/当前选择保持。已有pending必须被完整
   迁移或先完成，不能清掉。策略更新不缩短已经确认的保护期限。
2. **R06.2 容量变更与格式演进**：扩展历史记录保留原资格/容量身份，
   为显式重新配置提供版本化迁移；不能为让校验通过而改写旧历史。
   提供旧包接入适配/可读性验证，使升级及能力兼容的回退都能操作
   当前业务状态，不以当前旧格式不支持作为结案。
3. **R06.3 持久版本状态机**：独立记录候选/恢复版本、故障指纹、
   已用周期、pending目标及消费回执。复用有界隔离journal I/O；
   丢回执幂等、跨boot不复额度、状态失能不信号健康模型。
4. **R06.4 原生控制根与接线**：Guardian持有唯一启动/撤销权，
   关闭入口、排空/用量交接、清理旧payload后，按封存目标重启
   controller/入口/模型；每个角色仍消费原额度。入口独立确认
   新实际二进制/协议/容量绑定。CLI/status/发行元数据报告实际运行
   版本及回退原因，发布源版本与运行选择不可混淆。
5. **R06.5 针对性验收**：CPU覆盖篡改、能力丢失、真实journal失败/
   丢回执、各迁移中断点、原额度/停止/跨boot与角色清理；适用实际
   两个服务版本之间一次回退，核对JSON/SSE、原任务/配额及清理。
   单次GPU预算在驱动完成后冻结，初始参考2启动/6请求/900秒；确有
   必要追加时先记录累计边界，不重跑无关性能/全模型矩阵。
6. **R06.6 可用交付与接续**：保留实测能力兼容旧payload、原状态
   与恢复凭据，发布对应原生控制根；随后继续R07—R10及A/Q/G00。
   任一子任务完成都不等于R06或Serve总目标已完成。
