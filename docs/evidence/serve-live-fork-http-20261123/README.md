# 从已存储的语音资料查询创建 Live 子会话

本机 Thor 使用官方 Node SDK 7.47.0 和原生 TLS 入口，以同一客户端、同一已完成的真实资料查询，分别建立 WebRTC 和 WebSocket 子会话。使用已停止测试对象库的字节相同副本。原对象库哈希保持一致，当前默认发行仍为 rev426。

| 核对项 | 结果 |
|---|---|
| 归属和身份 | 两个入口对另一客户端均返回 404。源、WebSocket 子会话和 WebRTC 子会话的 ID 各不相同。 |
| 媒体通话 | 官方 SDK 收到 201 和新的 SDP answer。本机对端通过实际 SCTP 收到启动事件，静音被权限拒绝，获准的关闭命令正常完成。 |
| 原有内容 | 对照源会话和新录制的子会话，模型可见的前 9 条历史逐项一致，保留 ASR 来源、委派调用与结果的关联、项目记录和上次回答。子会话本地 item ID 重新分配。有效前端指令相同。子会话最后共 11 条历史。 |
| 新业务 | 客户端仅请求逐字复述已查得的 version 字段，线上请求没有版本值。模型产生一次新推理，播报 rev426，输出 107,520 字节 PCM，无新工具委派。SDK 按 1000 正常关闭。 |
| 清理 | 第三轮 55.43 秒，一次模型启动，54 次 NVML 采集正常。后续 Chat 回答 42。客户端、媒体进程、主机预算、端口和 GPU 租约均已回收。 |

保留了两轮失败。第一轮的 WebSocket 跨身份检查通过，测试对端因未加载已备好的 NICE 插件无法生成 SDP。验收驱动现先在 CPU 上检查插件身份并实际生成 offer。第二轮的传输、权限、隔离和正常关闭通过，模型只播报 rev；该回答属于失败。第三轮将请求明确为读取上一次 JSON 的完整字段，并实际核对子会话保存的历史。一次正确复述不能代表所有措辞的模型质量。[三轮记录](business.json)。

CPU 共 37 项原生检查、10 项实际入口进程检查、5 项协议检查及 36 个清单反例。测试捕获了删除旧数据通道配置后仍使用旧 JSON 成员引用，导致 WebSocket 的 8 kHz 显式覆盖失效；修复后默认 24 kHz 和显式 8 kHz 均通过。单测还验证了同一 Responses 工具结果进入显式后续请求一次、空闲时生成次数为零、私有前端说明不进入委派上下文，以及合法 Decision 项目 ID 与损坏历史的处理。[构建身份与结果](cpu.json)。

服务端 fork 需要已启用显式录制并以同一身份访问。没有历史的旧录音返回 409。已移除的私有 MCP 凭据须由新请求重新提供或移除相应工具。媒体对端使用本机已核验的 NICE 插件，核心 LLM 与 WebSocket 不需要该插件。此次证据覆盖工作分支，组合恢复、SIP、可回退发行和主线交付继续推进。[源录音业务](../serve-live-fork-state-20261123/README.md) 和[官方 fork 合同](https://developers.openai.com/api/docs/guides/live-conversations#store-and-fork-a-session)。
