# Guardian准备子进程的所有权修复

配置MCP的整包恢复在0模型/0请求时失败，原因是Guardian清理业务树
时只保护版本journal本身，将其原生策略校验子进程当成业务残留。
原失败、475次管理观察、手动提前停止说明和正常清理记录保留；
没有把这次失败记为NVML环境问题，也没有放宽journal超时。

修复按同一实际进程清单保护journal及版本探测器的存活子树，使用
PID及启动时间确认根身份。工作进程死亡后，收养的孤儿不再豁免；
停止仍须确认完整清理。模型和控制器启动授权、故障预算保持。

- 原二进制的新增回归真实复现失败，10.227秒，未启动模型。
- 修复后7项原生CPU生命周期通过，41.574秒，含首次准备、整包
  切换、工作进程死亡/超时、停止时子孙进程和设备探测清理。
- 实际原封包、注册、主轻资格和原生MCP校验在修复后的Guardian
  下完成准备，11.575秒；全部业务/探测命令显式替换成`false`，
  不是模型业务证据。首次组合夹具错误关闭quota却保留handoff的
  失败也保留，修正夹具后执行上述验证。
- 离线finalizer先固定封包命名空间再导入读文件模块。1项新进程
  CPU通过，0.264秒；包括正常隔离和预先导入仓库模块的拒绝反例。

本组9项不同检查、11次执行，另保留前期5次隔离诊断。新Guardian
`822fb3ca`构建零警告；LLM引擎、当前默认和视觉候选保持。GPU新增0。
原配置保留包和TLS/控制器业务已通过的记录继续保留，整包恢复和
确切默认策略组合尚需补验；总目标active。

原路径/权限/时间及恢复脚本在归档内，两组各实际恢复核对一次。
当前host/runtime/default、模型和reference未改。
