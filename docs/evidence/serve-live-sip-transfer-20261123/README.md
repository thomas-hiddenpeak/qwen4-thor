# Live 和 Realtime 的电话转接

官方 JS SDK 7.47.0 在 Thor 上通过原生 TLS，以两个独立签名通知中的 ID 控制同一通已接听的电话。SIP 对端使用独立的本机双向 TLS 连接。测试号码和地址只交给该对端，未拨打公网电话。

| 同一通电话中的操作 | 实际结果 |
|---|---|
| 使用其他客户的 Live 或 Realtime 凭据 | 两个入口均为 HTTP 404。所属客户提交包含换行的地址得到 400。 |
| Live 向第一个号码转接 | 中继收到携带完整号码的 REFER，回 486 后 SDK 收到 502，错误包含 486。 |
| Realtime 向带参数和百分号转义的 SIPS 地址转接 | 中继收到完整 Refer-To，在原连接上先通知振铃再回 202，SDK 得到空正文 200。此时发起第二次转接得到 409。 |
| 中继通知目标忙线，Live 再次转接 | 前一项按中继的最终 NOTIFY 记为失败。新的 REFER 得到 SIP 200，SDK 得到空正文 200，其后中继通知目标接通。运行计数为接通 1、失败 1、未知 0。 |
| 转接后继续原通话 | 加密 Opus 语音转录为“请查询当前项目版本号。”，客户端回填实际项目记录，播报 rev426。对端解密 24,000 个样本。挂断、旁路关闭码 1000、普通 Chat 回答 42 及资源清理通过。 |

严格 GPU 租约内运行 63.14 秒，1 次模型启动，1 通电话，13 次 SDK HTTP 调用，61 次 NVML 查询全部成功。二进制身份、各阶段回执和清理状态见[验收记录](acceptance.json)。私有原件位于本机 `.q4t-work/serve-live-20261123/sip-refer-business-01/`。

针对性 CPU 验证覆盖 8 个[真实信令对话](dialog.txt)、8 个[所有者用例](owner.txt)、4 个[输入与准入用例](lanes.txt)、5 个[公开合同用例](schema.txt)。包括未 ACK、过期订阅、终态先于 202、错误或过时的事件 ID、HTTP 超时后原 486 迟到、旧回执重传。最初的合同测试误把转接请求 schema 保存在原本用于媒体创建的变量中，导致既有媒体创建断言失败；拆开变量后同组通过。[原失败](schema-first.txt)。

[原生入口](native-routes.txt)与[可选 nginx](nginx-routes.txt)分别核对 82 个 HTTP 模板。来源审计核对 102 个运行时操作及含 OPTIONS 的 171 个原生路由。[审计回执](inventory.json)。

SDK 的成功回执表示中继接受 REFER；后续目标结果由 refer 订阅报告。第一笔 REFER 的 NOTIFY 可以省略事件 ID，后续必须关联本次 CSeq。未报告终态且订阅到期按未知记录。电话客户地址仅用于 Refer-To，中继仍在原认证连接传输。协议依据见 [RFC 3515](https://www.rfc-editor.org/rfc/rfc3515.html)。
