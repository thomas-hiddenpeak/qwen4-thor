# Live 来电由客户通过原生 TLS 拒接

2026-11-23，在 Thor 上从运营商模拟对端发起一次真实的 SIP/mTLS INVITE。使用同一模型进程、原生 TLS 网关、两个独立 API Key、签名 HTTPS 接收端和固定的 OpenAI JS SDK 7.47.0。四次 SDK 请求均关闭自动重试。

| 对端操作 | 实际观测 |
|---|---|
| SIP INVITE | 收到 180；SDK 从签名通知中取得此事务的会话 ID 与原始 Call-ID |
| 其他客户拒接 | 404；来电仍在等待所属客户处理 |
| 所属客户提交 299 | 400；来电仍可处理 |
| 所属客户提交 486 | 运营商模拟对端收到带原 To 标签的 486。保留 200 ms 后发送 ACK，SDK 得到空正文 200 |
| 确认后再次操作同一 ID | 404；单次通知收到 HTTPS 204，运维计数从 0 增至 1 |
| 通话结束后的独立客户 | 同一模型回答 17 + 25 得到 42，执行槽及请求资源正常释放 |

[通过记录与二进制身份](acceptance.json)对应第二轮，耗时 37.54 秒，1 次模型启动、1 次通话、4 次 SDK 调用、1 次 Chat。严格租约期间 37 次 NVML 查询正常，模型正常退出，原生入口和电话端口释放。默认包为 rev426。

[第一轮失败](original-failure.json)保留。模型已启动且能振铃，签名接收端却一直等不到来电。在同一部署所有者的 CPU 夹具上复现：启动线程退出触发 Linux 的父线程死亡信号，终止了已报告 ready 的通知进程。修复让创建该进程的线程存续到服务关闭。针对性 CPU 回归覆盖正常回调及等待 ACK、缺少 ACK 返回 504、竞争操作返回 409、迟来 ACK 后资源注销。另有 3 项原生合同/准入检查、5 项公开合同检查及可选 nginx 路由转发检查。路由清单与 36 项变异检查通过。原始目录为 `.q4t-work/serve-live-20261123/sip-webhook/` 与两个 `sip-reject-business-*` 目录，私钥及中继配置仅保存在私有工作区。
