## R1：普通日志与观察文件阻塞隔离

现状：`supervisor.RotatingLog.capture`在读取模型stdout的线程内同步
写文件；返回错误已隔离，但写入阻塞会阻断排空。恢复控制器还同步
保存自检观察，不能将它与授权账本的必要持久性混为一谈。

首项写入点核对（实现时逐项闭合）：

| 路径 | 类别与当前影响 | R1处理 |
|---|---|---|
| `controller.load` → `RotatingLog.capture/write` | 普通模型日志；文件操作堵住排空线程，stdout管道最终可反压模型 | 独立写入进程，排空不等磁盘 |
| `controller.load` → `observations.save(self-check.json)` | 自检结果观察副本；同步fsync可堵住控制器心跳 | 自检判定留内存，副本异步；丢失可见 |
| `service.launch` → `guardian.log`及继承stderr | 普通诊断文件；控制树可能直接写入该文件 | 去除对可阻塞普通文件的同步依赖，保留受控诊断出口 |
| `monitor` → `jobs.Job`的stdout | 已有有界非阻塞采集，无普通磁盘写入 | 复用，不重复改造；真设备故障保持优先 |
| `store/journal`的状态、停止意图、预算 | 安全授权账本，已有独立有界worker | 保持持久确认和失败冻结；不能按普通日志丢弃 |
| `service`配置、`controller`代次目录/网关凭据 | 启动/模型代次的必要控制输入 | 保持失败关闭准入；不因文件操作失败跳过身份校验 |

R01已实际交付，总目标active并继续R02；迁移实况见上位计划。

1. 先逐个列出当前服务包的普通日志、观察快照及授权记录写入点。
   普通写入移到独立CPU进程；主控制循环和模型输出排空只做有界、
   非阻塞传递。固定队列/单条上限、丢弃策略、确认期限及累计缺口。
2. 工作进程超时只停止自有写入进程。未确认回收时保留身份和容量，
   不创建替代线程/进程绕过限制。健康模型同PID继续处理请求；日志
   状态不能授权模型重启。控制器退场仍须确认全部自有子进程退出。
3. 必需授权账本继续走已有单worker与持久确认；写失败冻结新的
   恢复授权，不能“为可用性”跳过停止意图、代次和预算。普通日志
   也不能直接继承为Guardian的潜在阻塞stderr目的地。
4. 新包固定新来源/协议版本；已封存v1/v2和v9/v10不原地升级。
   后续旧host观察入口迁移属于R4，不能仅放开版本校验。

针对性验证：真实CPU子进程写入卡住、队列满、ENOSPC/EROFS、退出及
清理未知、重复失败资源上限；控制循环仍响应、输出持续排空、丢弃
可见且不重启模型。再做当前新包一次真实JSON/SSE短验，记录同PID、
停止与清理。内核不可中断I/O只做状态机注入，不人为制造D-state。

完成条件：所有当前运行期辅助写入点均有分类和边界；针对性CPU及
受影响业务短验通过；新包与回退、来源核对、发布元数据、文档和
阶段提交推送齐全。若只完成组件，状态必须保留“未接入/未交付”。

## R2：grammar worker有界清理

- `GrammarProcess::Stop`的阻塞`wait4(..., 0, ...)`改为单调期限与
  非阻塞回收。pidfd和未回收状态由进程级所有者持有，不保留请求栈
  回调；回收计数、报告及容量仅结算一次。
- 活跃和待回收worker共同占用固定的一个槽位。回收未知时拒绝新的
  结构化请求，返回稳定错误；不悄悄改成无约束生成。普通文本继续。
- 校验超时/取消/短读/闭端写入、真实子进程退出、注入不能回收、
  请求销毁后再回收、连续失败无FD/进程膨胀；仅执行受影响的结构化
  和XGrammar开/关合同。业务短验覆盖严格工具成功与失能后普通文本。
- 出口：清理延迟有上限、能力状态与拒绝一致、恢复后再准入；不承诺
  用户态可在规定时限内杀死任何内核D-state进程。

## R3：真实进度与卡死恢复

- 接通带服务/模型代次和序号的私有进度快照：加载、PLE读取完成、
  prefill片段完成、decode完成、媒体处理与输出等待。记录真正完成，
  不以控制器心跳、GPU利用率、日志或“很久没token”代替执行进度。
- 请求排队、客户端背压、空闲不记模型卡死；按最老未完成工作判断，
  防止别的请求持续前进掩盖单请求停滞。未校准阶段只报疑似并限制
  相关请求，不用统一超时盲目杀模型。
- 已确认可恢复故障复用关闭准入→同租约清理→有界探测/自检→配额
  窗口→重开流程。进度通道失效是观察未知，不能单独授权重启。
- CPU覆盖代次错配、陈旧/未来/乱序、空闲、背压、慢但有进度及卡死
  转移；真实短验只验证实际进度与自有模型一次受控停止/恢复。
- 出口：状态、错误码、故障原因与恢复账本一致；无请求/工具自动重放。

## R4：exporter与留存

- 为当前恢复包以及受支持的旧v10资源包分别绑定来源；v5/v6保持原
  合同。直接核对内核资源事实，普通统计未知不记零；陈旧、旧代次、
  核心readiness、能力降级、历史缺口分别投影，抓取不重复累计故障。
- exporter失败只损失观察；新日志/快照worker采用R1机制。固定指标
  标签，不记录Key、工具参数或聊天正文。
- 保留最近故障与有限轮转；按字节、数量和期限限制普通日志与运行
  目录。活动代次、授权账本、使用中的状态、唯一回退包和未归档故障
  原件禁止自动删除；清理有干运行报告及中断恢复，不按mtime猜归属。
- 针对性CPU验证版本/来源篡改、缺失/恢复/过期、无信号副作用和
  路径/符号链接/活动文件保护。本项不需要模型或GPU测试。

## R5：能力降级与轻量profile

- 显式登记已验证profile及能力差异：同模型同精度、MTP关闭、较小
  最大上下文/并发容量、媒体关闭。按实际代码可支持组合逐项登记；
  先完成最小文本fallback，不生成未经验证的参数组合。
- 内存压力/特定能力故障与暂时排队过载分开。触发有持续时间和恢复
  滞回；影响已接收请求的切换先排空或明确终止，清理后才能重载。
- 降级后的能力查询、预检、readiness、客户端错误一致；不截短用户
  提示、不丢图片、不放松Schema。恢复标准profile同样消耗持久预算。
- CPU验证状态机和权限/预算；各实际启用profile各一次定向业务短验。
  不做五档性能、全质量矩阵，不声称性能保持或某百分比改善。

## R6：版本回退

- 只允许当前版本和一个事先验证过、身份完整的回退包；故障指纹与
  版本关联后才触发。NVML缺失、磁盘不可用或真设备故障不归因软件
  版本，不进行无意义的版本来回切换。
- 单次故障周期最多自动回退一次，持久记录；失败进入隔离。停止
  意图、分钟配额和重启预算跨版本保留，拒绝不支持的状态协议迁移。
- CPU验证篡改/半安装/掉电位置/预算不清零与防振荡；真实短验验证
  两个已接受包之间一次切换及JSON/SSE服务。不改写旧包接受记录。

## R7：无NVML冷启动

- 开发显式独占部署profile，约束谁可访问设备、谁可拉起计算进程及
  授权的有效期/代次。合作flock、proc轮询或一次CUDA成功不能单独
  证明没有其他GPU用户；无法建立独占证据时保持冷启动拒绝。
- 连续租约内的已有恢复和全新冷启动分开。明确设备故障仍保护，
  探测失败不重试风暴、不reset GPU、不卸载驱动。
- CPU覆盖无/过期/冲突授权和NVML未知；条件满足后只做一次受控
  冷启动，业务内注入NVML不可用，外层严格租约继续监控。
  此测试不冒称验证了宿主真实NVML完全失能时的独占性。
- 若本机权限隔离不足，交付代码/部署检查并明确`条件待验`，记录
  缺少的可验证条件；不能用管理员一句“独占”冒充技术证明。

## R8：可选资源域与物理内存边界

- 显式启用已有委派cgroup接口，直接核对归属、限额和关键事件；
  管理器普通统计失效不停止健康核心，身份/关键保护未知仍关闭准入。
  无委派权限时按已声明的process模式启动，不能伪装硬限额存在。
- 统一DRAM下CPU、CUDA、managed、staging及页缓存按覆盖范围计量；
  请求预算、CUDA申请量和memcg均不能冒充整机物理RAM硬上限。
- 联动R5做内存余量保护、关闭准入、可控清理与fallback；CPU故障
  注入验证，真实测试只用安全限额及正常退出，不制造系统OOM。
- 先作一次有界可行性核对。若内核/驱动无法强制所需物理上限，
  保留`NO_GO_CURRENT_CONTRACT`，明确平台条件与替代保护，不能把
  无法保证的硬上限标成解决；继续实现替代保护和可验证恢复。原问题
  保持未完成，需扩大到驱动/平台工作时带证据确定路径，不能自动结案。

## R9：可选部署与外层启动

- 原生TLS/LAN、独立Key、来源限制、证书更新和浏览器接入属于
  N01—N07必做任务；本项承接外层启动生命周期。普通HTTP外部前置
  继续兼容且可选，不用外部适配代替原生实现。
- 默认Guardian处理模型/控制器/入口死亡。Guardian、整个进程树或
  主机已死不能由已不存在的代码自行复活；提供显式外层启动适配，
  有systemd可用unit，无systemd可接宿主启动器/容器管理器。
- 必须显式安装/启用；停止意图跨宿主重启保持，卸载后不自动拉起，
  不创建隐藏恢复脚本或互相复活的进程。CPU进程夹具测试这些行为。
- 实际LAN、真实证书/来源网段和主机重启只在部署时按用户选配验收；
  不因缺少现场配置阻塞可交付代码，也不声称现场部署已通过。

## R10：视觉组合与用户长稳交接

- 在已有视觉实现上验证图片JSON/SSE、受支持Schema/工具、能力关闭
  时明确拒绝以及恢复后可再用；覆盖一个真实项目资料场景。不扩展
  视频硬解码、视觉并发或重新研究模型视频时序质量。
- 故障恢复需确认旧图像/会话状态不跨模型代次串用，失败不重放工具。
  无关视觉数值/性能证据按源码身份复用，不跑完整矩阵。
- 提供冻结包、命令、检查点、故障/资源记录与停止清理说明；长时间
  稳定性运行由用户开展，结果回收后单列接受，不能用短验替代。

## 验证预算和停止规则

每项先成组实现，再运行直接相关CPU检查，必要时再做表内业务短验。
上限包含自检、失败尝试和补验；达到该项验证要求即可结束本次采样，
继续交付和后续任务，不用尽预算；这不是总计划的停止条件。
实际命令、来源、用例ID、计数和原件在各项开始执行前冻结。

| 子目标 | GPU上限：模型启动 / Chat / 租约秒 | 业务短验目的 |
|---|---|---|
| R1 | 1 / 4 / 600 | 阻塞普通写入后同PID完成JSON/SSE及停止清理 |
| R2 | 1 / 6 / 600 | 严格工具、结构化失能边界与普通文本可用 |
| R3 | 2 / 8 / 900 | 真实进度、一次受控故障恢复、不重放 |
| R4 | 0 / 0 / 0 | 观察/留存仅CPU与本地进程夹具 |
| R5 | 3 / 10 / 1200 | 初始与最多两个明确fallback；不做性能比较 |
| R6 | 2 / 6 / 900 | 已验证包间一次回退 |
| R7 | 1 / 3 / 600，满足独占前提才启用 | 冷启动合同与NVML业务内失能 |
| R8 | 1 / 3 / 600，具备委派条件才启用 | 安全资源域生命周期 |
| R9 | 0 / 0 / 0 | 外层生命周期CPU夹具；原生TLS/LAN归N组验证 |
| R10 | 2 / 8 / 900 | 现有视觉能力的恢复组合 |

- 以上是分阶段最大值，不是现在同时申请GPU或要求全部跑完。未改
  运行时身份的文档/夹具整理不触发模型测试；来源证明适用时复用。
- 不运行完整性能、全模型正确性/语义矩阵；只验证改进事项与直接
  受影响行为。测试时间记录只用于期限/资源检查，不据此宣布优化。
- 具体失败保留原件，修复后仅重验受影响项；预算耗尽如实记录缺口，
  不为了得到通过而反复扩样。真实GPU均持同一阶段严格租约，竞争
  或外层监控失败记ENV_ABORT，只清理自有进程。
- 不操作他人服务、驱动、GPU reset或真实系统OOM。新能力默认在
