# MoE 固定容量离线回放：2026-09-28

结论：值得让 **32/64 槽 LRU 与静态热点一起进入有界在线影子统计**，
优先64槽；本轮停在此决策，不实现在线统计、预取、权重加载或驱逐。
不把128/256槽或“动态总是更好”作为结论。长prefill、缓存重置和换领域
必须保留为影子阶段的检查项；这些结果不证明吞吐、NVMe读取或等待时间改善。

## 旧计划核对与本轮范围

以moe.cu、router_collector、chat_scheduler、moe_weights.h及swizzle.h为准：
受控采集已交付且部署代价已接受；所有路由专家仍按固定专家偏移整层常驻。
旧草案中的“尚未采集”、把采集成本留待接受、整机122/59 GB直接可作缓存
均不能继续作为计划前提。此前MOE_ROUTING_TRACE已修正前两项；本次更新其中
“尚无回放工具”与STATUS下一步入口。历史日志和实测性能记录不改写。

冻结四档32/64/128/256、逐层均匀分配、静态decode热点和整组LRU；无LFU、
预测器、非均匀分配、统一跨层缓存或新采集。工具/测试/报告入库，私有轨迹

## 数据、因果边界与执行合同

计划：[replay-plan-20260928.json](../tools/trace/replay-plan-20260928.json)。
源为同一3b414633的主聊天采集20份与此前五档性能采集15份；完整源重新通过
analyze+C++检查器，117个原文件与此前artifact-bindings逐个匹配。
选原seed1八条作离线校准、seed2八条作留出；排除四条重复。外部取每档第一次，
共五条独立技术输入，排除其余重复。没有根据结果挑样本或容量。
校准是预先拥有的独立离线训练集，**不是按原采集墙钟声称在线学习**；部分
校准请求实际采集晚于留出请求。静态排名在评估开始前冻结，动态不继承训练状态。
计划绑定源manifest和所选bin摘要；binary、模型index/config、workload、输入
token、CRC、帧/层/位置/终态继续由既有检查路径核对。模型index非权重全量哈希。

每请求每层只研究前64次decode，所有前置prefill均保留实际块边界。连续模式
是第64次decode后结束请求的反事实工作负载，未回放的后63/191次不提供历史。
请求序列写在计划中，heldout与external各自重置，未人为重排以提高命中。
主组依次跨Python、数学、中文、系统等材料，保留换领域结果；外部按1K至200K。
这只是一个固定序列，不证明其他到达顺序、生产分布或稳态效果。

- decode：同层10专家一次需求，在组前计算命中；LRU保护全组，消费结束后
  才容许后组复用槽位。同组访问使用同一时间戳，平局按专家ID，不按top-k序号。
- prefill：按同层forward块专家并集；每缺失专家为该块全部相关token消费一次。
  能放入容量时LRU整组接纳；超容量时保留已有缓存、不更新recency、不接纳，
  缺失专家逐组流过staging。静态miss也用staging，不改变常驻热点。
- staging：跨层串行共用10个专家槽，decode足够放最坏10个miss；prefill一个
  专家完成该块相关gate/up/down消费后复用。**这是尚未实现的分组执行假设**，
  不声称现有kernel能在中途安全替换权重或保持相同性能/求和顺序。
- cold_decode：每请求空LRU/付费静态填充，跳过prefill的隔离实验。
  prefill_reset：每请求重置后先回放真实prefill，保留至decode。
  continuous：第一次初始化后跨请求保留，包括前请求decode至后请求prefill。
- 静态每次初始化加载全部C槽，单独收费；LRU以空状态开始，前64窗口包含
  真实暖机代价，无免费预热。所有hit先于更新，普通需求补载不是预测命中。
  host在forward末尾才取得采集路由，不据此假定在线补载已经提前完成。

## 总字节预算

按当前packed权重布局，每专家gate/up=1,638,400 B，down=819,200 B，
两块swizzled scale=204,800+102,400 B，四个FP32 scale=16 B；
payload **2,764,816 B**，假设256 B对齐槽为 **2,765,056 B**。
加载计完整slot（含240 B padding）；它不是checkpoint文件读取量。

| 每层槽位 | 48层缓存+10槽staging总预算（B） | 十进制GB |
|---:|---:|---:|
| 32 | 4,274,776,576 | 4.275 |
| 64 | 8,521,902,592 | 8.522 |
| 128 | 17,016,154,624 | 17.016 |
| 256 | 34,004,658,688 | 34.005 |

两策略同预算，动态尚未填满的空槽也不转作其他用途。共享专家单独常驻，
不占路由槽；本表是**路由权重device空间及staging预算**，非整机占用。
缓存策略host元数据、host scale副本、加载器与系统空间仍须放在整机余量内，
尚无在线执行器，不能声称这张表已经完成真实硬件容量认证。

已有采集的五档输入均配置max_len=208896、max_prefill=8192、max_seq=1，
因此这五档的实际预分配状态预算相同，不按输入变短虚减KV。启动日志记录
mem_total=131.92 GB、90%预算118.73 GB；weights估算84.00 GB，fixed=94.15 GB，
state_pool=7.08 GB，per_request=8.35 GB，采集池额外75 MiB。
当前路由payload总计67,948,118,016 B；从fixed扣除它，非路由权重（含共享）、
workspace/forward缓冲/PLE/系统margin约26.20 GB；再扣state、request和采集池，
路由剩余估算约77.02 GB。这里只是**现有保守预算器口径的粗算**：其中仍保留
MTP workspace等估计项，84 GB也不是逐tensor实测常驻账；没有证明线上可分配
77 GB，更不把T4000未核实的59 GB当可用缓存。换max_len时必须重算KV/indexer、
recurrent/conv、trunk/logits、IO/host元数据与系统余量，进入真实offload前需实测。
