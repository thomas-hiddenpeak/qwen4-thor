# 已验能力升级与恢复资格连续性

状态：迁移实现与16项针对性CPU验证通过，实际新包资格及发行待完成。
此项属于R05/R06/Q02，不能通过删除profile/版本恢复配置绕过。

## 发现与修复

现有profile迁移要求能力观察逐字段完全相同。A07加入原生拒绝后，
新能力、模板版本及renderer源码身份会阻止正常升级。另一方面，自动
回退确实不能丢掉refusal、工具、schema、媒体或已配置embedding能力。

现在只有持有STOPPED部署事务的路径可以显式接受已验能力扩展：

- 两个profile的封装资格、实际观察与模型资产都先核验；原观察保持。
- 只接受对象字段增加。原字段删除、值/类型变化或列表替换拒绝；
  native embedding从enabled变为false也不能夹带在升级中。
- renderer源码hash是实现身份，单独保留绑定，不作为能力语义。
  仅已审阅的模板v4映射到不变的v3输入合同；v4必须同时声明真实
  refusal能力，未知模板版本不能自动套用这条规则。
- 新v3迁移许可绑定两个实际能力摘要、两份资格及两边容量；原
  pending/history、冷却、配额、Key和逻辑时钟不清零。失败后只恢复
  原持久事务，不生成新的资格或增加等待预算信用。
- 自动版本回退仍要求能力相同；缺少新能力的旧包不能冒充兼容回退。

CPU证据见[迁移与真实本地账本事务](evidence/serve-feature-migration-cpu-20261112/README.md)。
夹具中的模型/资格是明确标记的合成数据，不作为GPU业务证据。

## 后续完成条件

1. 为已通过业务的A07引擎构建保持原生接入、native embedding、原
   策略与容量的候选包；用实际主/轻量profile观察构造新资格。
2. 使用原已验入口与工具，补必要profile短验；复用未改数值/质量
   证据，不跑完整性能或全模型矩阵。原生拒绝的已过6请求不重跑。
3. 保留具有新能力、明确来源和真实业务证据的回退payload；不把
   只改manifest或换hash算成新的回退实现，不重标旧包为已支持refusal。
4. 核对publication的32代留存上限及现有锚点，先保护旧包、账本和
   证据，再做可回退发行；不盲删历史或放大上限代替留存治理。
5. 实际默认、协议、客户端与恢复状态一致后更新交付结论；继续全部
   剩余A/R/Q任务。当前实际默认仍为rev72。

资格驱动现在支持显式候选release：只在私有计划中替换二进制/协议
身份，原已验包、模型、策略和容量保持；实际观察通过后才封装新版。
这避免“必须先有新配置观察才能封包、又必须先封包才能取观察”的
循环依赖。3项驱动CPU通过；两次原准备失败保留，尚未运行新profile。
