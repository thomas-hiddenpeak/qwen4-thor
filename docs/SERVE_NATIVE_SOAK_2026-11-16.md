# 原生服务长稳交接：当前包、无强制systemd/nginx

2026-11-16，继续Q03而非结束总计划。原11月3日长稳入口固定旧v3
包、日期和systemd临时unit；旧证据保持，但该入口不能代表当前原生
自监护部署。新增独立原生入口，准备时选择并冻结精确已交付包，
用户显式执行day，agent只做CPU及short。没有timer或恢复服务。

## 必须保留的能力

- 原生outer/Guardian持有实际服务生命周期；默认程序/状态只读，
  使用独立验证服务，完整共享GPU租约贯穿启动、工作、清理。
- 每周期普通JSON、SSE、严格schema、真实项目文档工具及SSE续答共
  5次生成；请求ID不复用，不自动重试或重放工具。固定原模型身份。
- day为24小时/1440周期/7200业务生成，加1次服务自检；保留第1小时
  60周期/300业务生成检查点。short为60秒/3周期/15业务生成加1自检。
- 只有用户显式run day才开展长稳。short最多1启动/16Chat含自检/
  0探测/600秒。day持锁总上限87900秒，原模型/outer恢复预算不修改。
- 外层真实监控失效记ENV_ABORT，停止验证自有树，保留原始证据；
  这与生产辅助监控故障隔离的业务结论分开。不干预其他服务。
- 连续GPU监控日志轮转可重建，周期静态资源记录按实际PID身份绑定；
  资源域计量与物理RAM分开，不累加RSS和GPU重复计数。旧长期资源
  增长保护复用适用字段，短验不声称长期资源稳定或完整物理硬上限。
- 原始wire/响应/工具来源/阶段状态/预算和清理供只读report重新核验，
  不能仅凭一个PASS文件。CTRL-C或驱动丢失不产生假成功，提供原身份
  stop/status维护命令，无systemd机器也能使用。

## 实施与验证

分离纯计划/工作负载/证据判定与实际生命周期。先成组实现并冻结最多
14项直接CPU，涵盖严格计划、固定期限、计数/不重试、1h检查点、
资源/日志证据丢失与身份/篡改负控；随后精确包prepare/check和上述
short。只在具体失败后修复并补受影响项。day不由agent执行。

本次交接仅提供当前已实现能力的稳定性工具；其余A/R任务仍须实现，
后续包变更显式重新prepare，不替换旧计划或借旧证据声称新身份通过。

开发时核对当前alpha为30 RPM/6000 TPM。day固定每60秒一组5请求，
保持该原限额；short每20秒一组，共3组。没有调整生产配额，不以长稳
负载声明饱和吞吐。资源增长使用原模型进程RSS/RssAnon/FD/线程，
两内存字段重叠，不能冒充独占cgroup或统一DRAM硬边界证据。

## 首次短验后的固定补验

首轮1启动/6Chat/51.339秒完成五类业务，随后验证驱动错误指标入口
导致FAILED，原件和清理保留。复用运营入口并通过直接CPU后，只补
1启动/16Chat/0探测/600秒；累计2启动/22Chat/1200秒。新独立short
保留完整连续60秒/3周期，day未执行。此补验仅解决已定位驱动缺陷。

准备计划后，`check` 和 `run` 均会核对计划输出目录所在文件系统的可用空间。
低于 12 GiB 时会显示路径与可用字节数，在创建采集器和申请 GPU 租约前退出。
清出空间后可对同一未执行的计划重新运行 `check`。运行期间采集器继续检查同一门槛。

短验与日稳均要求 guard 对事件日志和 NVML 查询日志分别保留当前与前一份，每份最多 4 MiB。两条源日志合计最多 16 MiB，另由采集器保存完整历史。只读复核会核对两条归档的字节数、摘要、轮转次数和租约的保留设置。普通独占验证可按需选择日志上限，默认保存完整历史。

## 音频交接

在含有已验收原生 TTS 和 ASR 的发行包上，可在准备短验或日稳计划时使用
`--audio`。驱动将发行时核验的短句合成为 MP3，用同一服务转录刚收到的
全部音频，核对原句，并保存原始请求体与两份响应供报告复算。验证使用原生
回环入口和原客户配额。原有纯文本计划可继续按原命令运行。

```bash
python3 -I -B tools/serve_soak/native_stage.py prepare \
  --package build/service --output .q4t-work/audio-day --profile day --audio
python3 -I -B tools/serve_soak/native_stage.py check \
  --plan .q4t-work/audio-day/plan.json
```

日稳在第 1 轮预热，再于每个整小时所在轮次执行，全天共 25 次音频闭环。
第 1 小时应有 304 次业务请求，全天 7,250 次，另有一次模型自检。用户可在
设备窗口使用 `native_stage.py run --plan .q4t-work/audio-day/plan.json`
启动，报告核验语音回包、ASR 实际收到的字节、识别文本及核心请求计数。
短验使用独立输出目录和 `--profile short --audio`，在三轮中的首尾各执行
一次音频闭环。[校验记录](evidence/serve-native-soak-audio-20261127/cpu.json)

原生验收报告对每次租约采样读取相应 NVML 工作进程的原始回复，对照请求 ID、设备数、进程列表与内存记录。监控可在已退出进程的确认期间再采样一次。就绪区间使用服务的 PID 和启动时钟，同一 PID 出现在未就绪区间不能证明业务进程已被观测到。归档缺样会在验收命令中报错。 [双包离线回放](evidence/serve-soak-observation-report-20261128/archive.json)
