# 性能测量、统计结论与工程决定

2026-10-20用户明确原则：**非性能优化的业务推进允许小幅性能波动；
性能优化必须按规范评估优化结果。** 此原则细化此前“常规改动有界
测量后作工程决定”的选择。任务按真实目标分类，不能只看改动规模
或是否自称重构；不降低正确性合同，不设统一百分比容差，不授权
无限GPU采样或超出当前会话范围的部署。

## 为什么过去会卡住

1. 最低五档、每档三请求能产生描述性对照，但过去只有每身份/模式
   一次服务启动，却反复要求它回答跨启动微小差异的统计问题。
2. EVALUATION旧“分辨带”同时用于表达测量能力与接受边界，容易让
   “噪声多大”变成“允许损失多大”；两者必须分开。
3. “证据不足”被当成整个任务阻塞，甚至已明确接受并部署后仍担心
   统计保留；应只描述统计结论，工程决定另记。
4. 缺测量时先要求接受未知风险，或者预算用尽后继续找有利结果，
   都没有完成一次有界决策。753d案例已补测并接受，不能再次重开。

## 默认路线和硬边界

非性能优化的业务推进采用工程路线：冻结业务目标和必要验证范围
→ 直接合同与适用HTTP质量 → 有界性能影响检查 → 记录工程结论
→ 按授权交付。小幅观察波动可以接受，不以严格统计非劣为默认
门槛，不为小幅波动本身重复要求专项风险确认。纯文档/工具变更仍
不运行模型；运行时检查依受影响范围确定，不把每次业务改动都扩大
为完整优化研究。需要声明性能保持时，仍完成规范要求的五档对照。

性能优化采用EVALUATION的优化流程：HTTP E2E优先，完整适用五档
父候选对照，分别评估收益目标、保护项、复杂度成本及证据有效性。
业务推进允许小幅波动不能用于自动放行优化结果；既有有限工程
接受的适用范围和条件保持。用户明确要求统计证明时另用事前设计。

混合任务分别记录业务完成与性能优化是否通过，不以其中之一替代
另一个。局部简化、所有权加固或调度改动按实际目标分类；实际目标
是提速时不能以“常规改动”为名绕过性能优化规范。算法、精度或
重大调度变化另明确额外合同，不凭任务名称豁免。

当前任务已授权的必要测试，在冻结具体范围和预算后执行，不把历史
某一实验的零采样预算解释成永久禁测；当前任务确有禁止采样约束时
仍遵守。没有实测时先补齐有界测量方案，不默认要求用户接受未知风险。
不为已通过且身份/依赖不变的证据重复运行整模型。

工程接受必须有明确业务收益、直接/质量合同、适用实测记录、有效
环境、无未解决的关键正确性问题及回退方式。业务小幅波动按用户
本原则处理；确实超出已授权范围的风险或发布决定才另行确认。
这是可审查的权衡，不是自动把统计不足判为通过，也不是全项目允许
任何百分比退化。小幅观察差值不能直接等同于已确认退化；已确认的
退化按规范处理，不用其他档收益抵消，也不把必要正确性修复的代价
伪装成“优化成功”。

## 四个字段分开记录

| 字段 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 证据有效性 | 身份、环境、预算、请求及退出记录是否可信 | ENV_ABORT不是候选性能失败 |
| 测量完整性 | 适用模式/五档/请求是否真的测齐，原值是否保留 | 没测不能写成“已测但统计不足” |
| 统计结论 | 所选设计是否支持指定性能主张 | 不显著不是相等，证据不足不是实现缺陷 |
| 工程决定 | 在收益、实测、限制与回退能力下是否接受本身份 | 接受不伪装成统计非劣，也不自动包含部署授权 |

预算执行完后不得自动扩样。工程路线完成全部证据后记录具体
接受/拒绝结论；按已有任务授权推进，只有超出授权的实际决策才问。接受后同身份、
同范围的统计保留不再触发确认或自动继续目标。拒绝则保留基线并
归档这次决策；不能称原改进已达成，也不能为了改变决定继续采样。
统计路线证据不足则结束本轮统计实验并保留基线，或另行明确转换
工程路线；不能把统计证明目标偷偷缩成工程接受。

只有新身份、依赖变化、实际合同失败、有效环境改变，或出现足以
改变已接受风险判断的新证据，才重新评估相应范围。普通新日志的一次
微小波动先核对身份和口径，不自动重启整个验收。

## 确需统计证明时如何设计

先确定估计对象和实际可接受损失界限δ，再确定测量预算；δ来自用途
与性能要求，不从候选结果、A/A极差或测量噪声反推。各保护项分别
规定，禁止用平均收益抵消任何一项。严格零真实损失和有限置信结论
不是同一承诺；δ=0会要求数据支持更严格的单侧界限，不能保证未来
每次执行都不变慢。

以同模式相邻父/候选启动为一个配对块，在多个块中事前平衡或随机化
AB/BA顺序。每次均新服务启动，每个启动内保留固定五档及首请求标记；
不要用普通模式AB、MTP模式BA冒充同模式内平衡。启动是重复层级，
不意味着天然独立，仍需处理时间漂移、缓存与相关性。不得把同启动
内请求当成独立启动，也不能用请求级bootstrap凭空制造启动重复。

若缺方差依据，先冻结一次有界先导（可包含同身份A/A）来检查测量
能力和预算可行性，而不是宣布“已得到永久噪声带”。完整模式五档
每次启动至少15请求；例如两模式各2个AB/BA配对块为8启动/120请求，
只是可计费的设计示例，**不是已授权实验或足够样本量保证**。不能凭
如此少的块承诺可靠尾部或非劣结论。本次不执行该示例。

正式阶段预先固定：身份/模式/保护项、δ、配对/随机化、重复层级、
冷态处理、区间方法及假设、整体结论规则、样本数与时间上限、有效性
和不足出口。20个保护项的整体主张及单项报告要明确；不能事后挑
显著项。改变统计方法或追加样本需新的有界设计，不能边看边采直到
得到想要的结论。若不愿投入足够预算，统计出口就是不足，而不是
把阈值放宽到通过。

## 纯CPU决策检查工具

`tools/evalscope/performance_decision.py`读取已审计的决策账本，输出
下一步状态；不会运行GPU、计算置信区间、验证统计分析本身或批准
部署。账本中的判断与引用必须由实际审计提供；字符串“accepted”
不是用户授权来源。它检查信息是否完整、优先级是否冲突，不能代替
真实证据审查。示例为已部署753d的真实记录：

```bash
python3 -B tools/evalscope/performance_decision.py \
  docs/evidence/performance-protocol-20261020/metadata-batch-ledger.json
python3 -B -m unittest discover -s tools/evalscope \
  -p test_performance_decision.py -v
```

结果应同时为ENGINEERING_ACCEPTED与statistics=inconclusive；这是
允许存在的组合，不是需要继续补测的程序错误。工具输出的
`deployment_authorized=false`表示该工具不颁发部署许可；部署仍查
具体接受记录，753d已有单独授权及健康交付证据。

## 方法参考与本次边界

NIST说明通过分块控制可控干扰，并在块内比较处理因素；这支持配对
和随机化设计思路，不提供本项目的损失容差或采样量。
[NIST randomized block designs](https://www.itl.nist.gov/div898/handbook/pri/section3/pri332.htm)。
Kalibera/Jones针对软件基准讨论不同重复层级及如何有效分配实验时间；
不能从“多跑几条请求”推导已覆盖所有变异来源。
[Rigorous Benchmarking in Reasonable Time](https://kar.kent.ac.uk/33611/)。

本次完成规则和决策工具，验证包括真实753d记录的离线重放及host
回归；新增GPU请求0，默认753d保持。没有完成或声称完成跨启动方差
校准、通用非劣计算器、统计性能证明或未来候选自动接受。
