# 同一 token 的路由专家 gate/up 与输入量化参考

## 结论

原4K请求最后一个prefill token（4095），覆盖48层选中的全部480个
路由专家。正式源码和接受二进制2392f6b1未变，原任务错误未修复。

| 核对对象 | 范围 | 结果 |
|---|---:|---|
| 实际gate/up权重、尺度、输入 | 480个专家调用 | 全部匹配checkpoint及该层MoE输入 |
| 按实际尺度的FP4输入编码 | 1228800个元素 | 与独立最近偶数FP4重编码全部相同 |
| 实际NVFP4 gate/up投影 | 614400个BF16元素 | 与独立FP64参考经FP32→BF16舍入全部位同 |
| 实际输入尺度编码 | 76800组 | 同接受版设备编码；70组不符独立最近偶数参考 |

70组错误来自6层的7个不同输入分组，各在十个选中专家中重复。
涉及层3、17、22、25、40、45，全部位于[248,432)高值提前饱和区。
不将70次重复使用当成70个独立输入事件或全模型发生率。

## 首项 HTTP 与采集

扩展只读观测库零警告构建后，第一项测试为tools/evalscope原4K
无观测→有观测→无观测HTTP。三次全文仍600440，应为360284；
输入4096、输出7、stop，三服务退出0，质量驱动均1。只证明观测
未改变此请求全文，不是质量通过或性能验收。

复用实际router的十个expert id，在GatherQuantKernel中查找专家
token列表内唯一满足flat/10=4095的行；读取源BF16输入及逐专家
输入尺度，再在相应cuBLASLt调用读取该行FP4、实际激活尺度、
完整权重/权重尺度和该行gate/up输出。共480份成功记录，专家
集合逐层与router所选十个id相同；形状、转置、主机alpha/beta和
vec16 E4M3尺度描述符检查通过。记录compact行号，未假设它等于
原prompt索引，也未假设不同观测的compact行序相同。

## 独立参考

只读checkpoint中每个专家的gate_proj/up_proj，分别640×2560，
合并为1280×2560。实际打包权重与checkpoint逐字节相同，设备
swizzle还原后的尺度全部匹配；两支路input_scale和weight_scale_2
相同，实际alpha符合FP32两尺度相乘。480份源输入均同对应层
MoE输入快照。

FP4参考枚举E2M1有限值，最近距离并按偶数编码处理中点；使用
实际捕获的E4M3尺度和逐专家input_scale，全部输入码一致。
投影独立解包权重/激活，乘各自E4M3块尺度，用FP64矩阵乘和
实际FP32 alpha计算，再经FP32与BF16最近偶数舍入，输出全部位同。
这是实际量化值上的计算核对，不是未量化BF16模型质量证明。

## 设备尺度复核

CPU初筛得到70组差异后，冻结接受版format.h（SHA24c37223…），
独立诊断工具零警告编译。对全部76800组真实BF16输入重建设备
max、除6、除input_scale及现有编码，同时保存实际ratio和CUDA
原生E4M3编码。重放退出0，全部旧编码同实际捕获；原生编码全部
同独立枚举127个有限非负E4M3值的最近偶数参考。

70组差异全部保留，确认不是仅CPU除法造成的差异。此前已证明的
高值格式缺陷不仅在SwiGLU后的down输入出现，也在gate/up前的
输入量化中被本请求实际触发。此轮未运行修正版模型，未把局部
参考匹配或编码错误当成最终答案的因果证明。

## 范围与下一步

只覆盖一个prefill token的选中专家gate/up链，不覆盖其他token、
decode、所有未选专家或完整上游attention/GDN/PLE/残差。
先前down采样不是这480个专家同一token的完整链路参考；下一步
把当前gate/up输出与同token的SwiGLU量化、down投影连接起来，
再接已核对的路由加权合成，明确完整MoE边界的剩余差异。
不重新启用已拒绝的格式修正候选，不放宽质量或性能门禁。
