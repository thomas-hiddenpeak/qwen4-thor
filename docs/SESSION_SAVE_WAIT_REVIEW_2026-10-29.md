# 私有快照保存 8.63→19.82 秒：离线定位与有界方案

2026-10-29。本次只读旧证据和源码，新增模型加载、HTTP、GPU fixture、
SSD 压测均为 0；没有修改推理程序、缓存实现或原验收结论。

## 已能回答的问题

**主要增量指向同步存储写入路径的等待，不是模型锁竞争，也不是多做了
11 秒 CPU 拷贝/哈希。** 现有证据尚不能拆开 `pwrite` 内部的文件系统
分配、块设备排队与 SSD 固件/SLC/GC；这些不能直接写成已证实根因。

对象是 C 首块 `repeat-code-8192` 的两个主请求：相同 c0ed 程序、full
head、131071 输入/256 输出、四槽、suffix 和私有缓存均开启，区别是
公共 prefix OFF/ON。不是 c0ed 对 6f37 的评分回归比较。

| 口径 | 公共 OFF | 公共 ON |
|---|---:|---:|
| 日志私有 Save 墙钟 | 8.633636 s | 19.816510 s |
| 快照 prefix / 逻辑字节 | 131323 / 4,159,963,136 | 相同 |
| 全请求累计模型锁等待（显示值） | 0.000 ms | 0.000 ms |
| 覆盖写入的采样窗口 | 10.002389 s | 21.001900 s |
| 窗口进程 CPU：user + system | 3.12 + 0.52 = 3.64 s | 3.30 + 0.39 = 3.69 s |
| 推定保存线程已观察 CPU | 3.397035 s | 3.409701 s |
| 同线程运行队列等待 | 0.117 ms | 0.255 ms |
| 同线程 D 状态采样数 / 有效点 | 3 / 9 | 17 / 20 |
| 窗口 `wchar` 增量 | 4,159,964,540 | 4,159,964,541 |
| 窗口 `write_bytes` 增量 | 4,159,971,328 | 4,159,971,328 |
| 窗口写系统调用计数 | 627 | 627 |

这不是精确分段计时表。窗口从第一笔大写入之前的采样起，到 HTTP 结束
之后的第一点止，包含普通 decode 尾部和少量日志；它覆盖整笔写入，
但不等于 Save 的精确起止。进程 CPU 包括所有线程和驱动调用；保存线程
按窗口内主要 CPU 活动推定，最后一个存活采样早于线程退出。
`wchar` 比快照多 1404/1405 字节，`write_bytes` 多 8192 字节，与日志等
少量附带写入相容。没有把这些计数当成物理 NAND 字节或 SSD 写放大。

保存墙钟多 **11.182874 s**，而覆盖写入窗口的进程 CPU 只多 **0.05 s**。
ON 的逐秒写入出现约 84～228 MB/s 的长段；OFF 开头两段约 1.03 GB/s，
随后也降到约 193～220 MB/s。采样的 D 状态是不可中断等待的线索，
不是等待时长，也不单独证明线程正停在哪个 syscall。结合写入不断推进、
CPU 随字节增加、没有并发子请求/模型锁等待，存储写入等待是主要解释。

## 代码如何界定锁、拷贝和写入

- `src/server/chat_generation.cpp:1206` 开始计时，再通过
  `RequestDiagnostics::Lock` 获取 `model_mu_`。该封装确实只累计获得锁
  之前的等待，不把持锁执行时间算作锁等待。两主请求的累计值都舍入到
  0.000 ms，因此不支持秒级模型锁等待解释。
- `SessionCache::Save` 再持有缓存池 mutex，构造 range、预算/淘汰及
  `O_TMPFILE | O_DIRECT` 临时文件，然后同步 Transfer。两次都是该服务
  第一份私有快照，没有旧 entry 淘汰；子请求在主 HTTP 完成后才启动。
  公共种子早在 prefill 内同步保存完毕，而且公共/私有池各有自己的 mutex
  和 staging。缓存 mutex 没有独立计时，但这里没有另一缓存使用者可解释
  11 秒竞争。并发子请求的 Save 则会含重叠锁等待，不能套用这个结论。
- Transfer 每块最多 **8 MiB**：同步 `cudaMemcpy(DeviceToHost)` 到一个
  4096 对齐的普通主机 staging → 末块对齐补零 → SHA256 → 同步 `pwrite`。
  同步 copy 的调用墙钟可能包含 GPU/驱动等待，旧 CPU 计数不能将其与
  hash、驱动 CPU 单独拆开。不存在另外复制一整份 4.16 GB host 快照的代码。
- SHA256 已有 ARM SHA2 分派，本次两侧代码一致；不能再把“换硬件 SHA”
  当作尚未实现的修复。布局、块数、数据量也没有因 prefix ON 翻倍。
- 快照 Save 没有 `fsync`、`fdatasync` 或文件 rename。文件是本进程内
  临时对象，成功 HTTP 后才通过 lease 发布；这不是跨重启持久化承诺。
  不存在可以删掉的每块 fsync。`model_mu_` 目前覆盖整个 I/O，确实可能
  阻塞其他请求，但解锁本身不会缩短此例主请求先完成、子请求才开始的事务。

## 旧日志的反证与限制

同两次完整服务的主请求控制项如下，所有主请求模型锁显示值均为 0：

| 材料 / 公共边界 | OFF 私有保存 s | ON 私有保存 s |
|---|---:|---:|
| code / 8192 | 8.634 | 19.817 |
| text / 8192 | 16.767 | 16.351 |
| code / 32768 | 20.334 | 16.620 |
| text / 32768 | 14.671 | 18.039 |

OFF 自己也能达到 20 秒，所以不能从第一对断言“共享必然令私有保存翻倍”。
两个服务按 OFF→ON 顺序执行，存在存储状态与顺序混杂；一次固定 64 GiB
预处理不会证明稳定态。它自己的 4 GiB 写入段已在 **14.906～30.455 s**
之间变化，且循环中无逐块 CUDA copy 或 SHA，进一步支持直接 I/O 路径
存在明显变动。预处理的末尾 `fdatasync` 不包含在这 16 个分段计时内。

原监控约 1 Hz，窗口单次采集最多约 24 ms；有进程/线程身份、stat、
schedstat 和进程 io，没有 syscall 计时、设备 diskstats、NVMe 温度/GC，
也没有归属完整的其他进程 SSD I/O。因此还不能区别文件系统分配与 SSD
内部慢写，更不能将所有 D 状态时间称作已测得的 `pwrite` 时间。

完整事务原分解保留：主请求 +11.343 s，客户端间隔 −0.072 s，子请求组
−8.252 s，合计 **+3.020 s / 慢 1.179%**。公共 8K 种子本身只花 0.384 s。
本次加强归因，没有删去保存时间，也没有把原正式 NO_GO 追认为通过。

## 下一步有界修复方案（提案，尚未执行）

只做一个存储路径候选：**一次显式文件预分配，替代随每次 pwrite 增长时
逐步分配空间的方式**。这针对的是尚待确认的文件系统分配成本；若慢的是
SSD 内部持续写入，它未必有效，不承诺把 19.82 秒恢复为 8.63 秒。

1. 在 Save 的原总计时内增加聚合分段：模型锁等待、缓存 mutex 等待、
   ranges/预算/淘汰、open/预分配、D2H 调用、补零、SHA、pwrite、安装 entry。
   每段同时记录 steady-clock 墙钟和当前线程 CPU，记录调用次数、有效/
   对齐字节、错误、最长块及超过 50 ms 的写次数。每请求一行；不用逐块
   文本日志或 Nsight。D2H 墙钟标作 API 等待，不能命名为纯 GPU 执行时间。
   分段加总与原总计时闭合，记录余项；观测开关相同地用于对照两侧。
2. 唯一候选在完成原预算/淘汰检查、open 后调用一次
   `fallocate(FALLOC_FL_KEEP_SIZE, 0, entry_bytes)`。预分配和失败清理均计入
   Save/HTTP，固定原 8 MiB staging、同步拷贝、哈希、写入与发布顺序。
   不支持时显式记 fallback；空间不足/真实 I/O 错误导致缓存保存失败、
   不发布 entry，延续原缓存失败合同。预分配空间计入磁盘预算。无异步
   写队列、整份 RAM 镜像、压缩、丢弃快照或放宽数值合同。
3. 先通过首组真实 tools/evalscope HTTP 输出核对，再做针对新增分配路径的
   CPU 合同：跨块/非对齐字节完整恢复、取消不发布、copy/短写失败、
   ENOSPC、不支持回退、清理与预算归还。逐字节校验 snapshot，保留 d0/
   pending、checksum、slot 覆盖后恢复合同。新 CPU I/O 总写入不超过 2 GiB。

执行前将以上实现 SHA、输入和驱动冻结到独立计划，建议**总墙钟 60 分钟、
4 次服务启动、40 HTTP、0 新 GPU 数值 fixture、最多 1 个候选**：

- 配置保持 1 个 208896 长槽＋3 个 65536 短槽、max-prefill=4096、greedy
  k3、suffix、私有/公共缓存；完整与 65536 行子集 head 分别比较。
- 每个 head 各一次原路径/预分配启动；每启动用原失败的 8K code 材料做
  公共 OFF 和 ON 各一个主＋3子事务（8 HTTP），再按原事务顺序各恢复一次
  主会话（2 HTTP），使每次恢复前长槽均被另一个主会话覆盖。
  共 32 事务请求＋8 恢复请求。
  full：原路径 OFF→ON，候选 ON→OFF；subset：候选 OFF→ON，原路径 ON→OFF。
  各事务使用新私有 ID/公共 scope，恢复请求使用对应主 ID；启动时空池。
- 若保留旧存储条件，只进行一次原有固定 64 GiB 预处理，时间和写入均计入
  预算，不增加“预热到稳定”为止的循环；总应用逻辑写入上限 192 GiB
  （含预处理、快照和 CPU 合同），文件、RAM峰值与释放成本都记录。
- 此为定位候选的局部验证，不是整套发布重验。首先核对两 head 全部输出、
  恢复 prefix、d0/pending 合同；性能目标事前固定为两 head 的保存总墙钟
  中位数各改善至少 1 秒、各公共模式事务不变慢，候选的公共 ON/OFF 净收益
  均为正。分段必须能解释改善，不能把等待挪到计时外。
- 超预算、正确性失败或环境竞争立即停止；监控失败记 ENV_ABORT，只清理
  自有进程。性能未达目标、不支持预分配或分段显示收益不足，按 NO_GO
  收尾，不重跑、不换第二种队列深度/块大小/文件系统策略。全阶段驱动持有
  同一 GPU 独占锁。小样本只给描述性结论，不声明统计非劣。

若证实大部分额外时间在 SSD 等待且预分配无效，本轮结论应是“存储瓶颈，
这个局部软件候选不能解决”。双缓冲最多重叠约数秒 CPU 工作，不能据此
承诺消掉 11 秒差额；放开模型锁主要帮助并发请求，也不能替代本例净收益。
降低快照字节或改变缓存保存策略属于另一状态/业务合同，本方案不扩展进去。
