# E4M3缺陷在真实4K请求中的命中

## 结论

原4K筛选求和请求确实产生了错误的E4M3组尺度。本轮保存首次四个
prefill SwiGLU量化调用，共17920组；其中7组实际编码与独立参考不符，
均为正常数高值区提前饱和。不是只有人工边界用例才能触发的缺陷。

仍未证明这7组导致最终600440错误答案，也未证明修正后全模型质量
提高。正式运行时未修改，已拒绝的修正候选不因此重新获得接受。

## HTTP先行与观测隔离

使用原接受二进制2392f6b1，普通greedy、MTP关闭、单流、
max_prefill=8192、max_len=208896。输入是原冻结4096-token错题，
独立正确答案360284，输出上限32；不改提示词或期望答案。

独立诊断库必要构建退出0、零警告；第一项测试是tools/evalscope
HTTP。无观测→有观测→无观测三组各一次请求，均输出600440、
实际输出7token、finish=stop。请求字段、输入长度、SSE全文、
二进制摘要均核对，三个服务正常退出0。质量驱动均退出1，来源是
保留的既有错题，不能写成模型质量通过。

三组回答一致只支持本请求的观测前后输出一致。该诊断不修改接受
版本，不重新接受候选，也不是新性能矩阵；包含同步/复制的时延
完全排除在正式性能比较之外。原接受版本的HTTP门禁绑定见
[参考合同](QUANT_REFERENCE_CONTRACT_2026-09-23.md)。

## 观测做了什么

`tools/verify/e4m3_http_observer.cpp.in`不链接正式程序。通过LD_PRELOAD
拦截本地CUDA 13.3的__cudaGetKernel/__cudaLaunchKernel，识别
GatherQuantKernel和SwiGLUQuantKernel。只在首次四次SwiGLU量化
调用后，同流复制BF16 gate/up输入和实际swizzled尺度输出到主机，
同步完成后落盘；不写设备输入或输出。记录同线程前序Gather中的
expert索引、形状及实际down input_scale。

上限4份，rows限制1–8192、width固定640、tiles固定10；不支持
其他形状/版本。实际行数2/24/21/401，expert索引0/1/2/3。启动阶段
未发生采集，四次采集日志均位于真实请求阶段且copy/sync/落盘成功。
没有覆盖后续专家、层或decode；不能由此估计全模型发生率。

这依赖当前CUDA内部入口及当前kernel签名，是绑定版本的诊断工具，
不能直接用作常驻生产观测设施。额外同步可能改变调度，即使本次
回答一致，也不代表对所有请求无影响。

## 快照重算与独立参考

三组HTTP核对完成后才编译/运行
`tools/verify/replay_e4m3_http.cu.in`，必要构建退出0、零警告。
只使用接受版header快照，不链接残留候选库。

重算保留BF16输入和原SwiGLU的float32/__expf计算顺序，重新求每组
max/6/input_scale；按原编码器得到的17920个代码与实际输出逐项
相同。这验证当前快照/索引/重算在这些组上自洽，不是独立证明
SwiGLU或swizzle的完整正确性。

同一float32尺度再分别用CUDA原生有限饱和转换、CPU独立枚举127个
可表示值的最近偶数参考编码，两者17920组全部一致。与实际输出
对比的结果如下：

| expert索引 | 行数 | 量化组数 | 实际代码≠旧规则重算 | 实际代码≠独立参考 |
|---:|---:|---:|---:|---:|
|0|2|80|0|1|
|1|24|960|0|0|
|2|21|840|0|6|
|3|401|16040|0|0|

例如expert0局部行1/组13的尺度为368.6727294921875，实际代码126
表示448；CUDA与独立参考代码124表示384。expert2局部行10/组33
尺度262.4053039550781，实际448，正确量化尺度256。这里的行号
是该专家紧凑输入的局部行，不是原prompt token位置。

两份有格式错误的重算进程退出1，其余退出0；不能把错误退出改为
通过。全部快照重算对应一致，无操作错误退出2。未观察到次正规
不一致，仅限四份快照，不能推断其他调用不触发次正规问题。
