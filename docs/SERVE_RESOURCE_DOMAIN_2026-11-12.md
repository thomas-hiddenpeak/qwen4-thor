# R08 / R09：原生资源域与新监护者核验

原生资源安装、前后台进入、旧域清理、跨boot续办与冷许可组合已
完成针对性CPU验证。创建/运行路径直接使用Linux能力，systemd
适配是显式选配。当前继续统一DRAM与memcg压力观察/合格profile
切换组合、适用模型业务和可回退发行；R08尚未完成。

## 已确定合同

- 显式管理员安装本项目命名的资源层级，目录/限额控制文件保持root所有，
  不移动、停止、改限额或接管任何既有进程/资源域；普通服务不隐式
  安装。管理状态须持久绑定原服务、部署和内核域，初始化/升级/
  跨boot/卸载不能丢失原停止意图或恢复额度。
- `outer`与`service`分叶，内存及任务限额分别生效；回收旧业务域
  不包含外层监护者。辅助观察失能不能据此杀掉健康业务。
- 子进程在执行Guardian及任何业务前进入已选域；迁移接口只写0，
  只移动调用者自身，不提供任意PID迁移API。root入口FD在降权前关闭；
  普通UID打开service入口，内核共同祖先权限限制迁移在自有安装内。
  不把API只写0称为内核仅允许当前PID，不引入setuid安装
  或外部守护程序。新进程取得完整外层实例/原状态权限后，才可
  对其持久绑定的旧域执行回收；JSON、单次/proc扫描不能提供授权。
- 实际cgroup2文件系统、boot、命名空间、目录inode及控制限额须
  一起核验。内核`populated=0`证明该域无活任务，不等于原GPU设备
  已可用；新模型仍须原设备准入/探测合同。被删换的域不能冒充
  原域，域不存在不能默认为已经完成全部清理。
- memcg不包含所有Thor驱动/物理分配，不能宣称硬物理RAM上限。
  CPU/统一DRAM全局观察与设备计量须分别记录，不能将两者峰值相加
  或把host分配称为SSD卸载。完整压力/降级/恢复组合仍在R08内。

依据：[Linux cgroup v2文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)
及[Linux 6.8 cgroup实现](https://github.com/torvalds/linux/blob/v6.8/kernel/cgroup/cgroup.c)。
仅学习系统接口与权限合同，没有复制外部实现。实际Thor权限行为
由下述CPU检查确认，不能只从上游源码推断已验。

## 持久安装与卸载（针对性 CPU 接受）

`q4t service resource-domain init/init-resume/status/remove` 显式管理
root命名空间。private安装意图先持久，再创建实际内核域，最后发布
只读能力回执；原域/服务/UID/限额保持。首次写入中断可续办，已
发布的private历史丢失不能重新bootstrap，ready回执丢失只修复副本。
卸载先撤新准入，不杀业务；确认outer/service均空后先写empty
检查点，再删原inode。中断可续办，换域拒绝，保留removed历史。

冻结12针对性CPU：8安装管理（真实新内核域、原子写入/发布/删除
故障、活动业务不被终止、原身份/权限/锁）+2直接内核权限/身份
回归+2封包库存/搬迁导入。无GPU、无宿主设备策略变更。当前仍须
实现运行接线、跨boot原历史继承及模型业务，不将管理接口当交付。

## 原资源绑定与启动接线（针对性 CPU 接受）

`resource-domain enter --directory DIR -- /绝对路径/q4t service outer-run …`
是显式管理员入口。调用者自身先进入outer，再释放安装管理锁，设置
no_new_privs并清除root UID/GID/附加组，exec普通用户外层命令。
公开ready回执与实际cgroup身份必须一致。service迁移FD在永久降权后
打开；接收者再按普通UID重新打开。每次子启动先核对原回执，
只写0进入service，然后关闭该FD再exec Guardian。普通run路径
不能静默忽略已给出的资源能力。

原资源回执、实际inode/boot/服务ID随原启动ticket一起先持久，再
允许fork。新观察者必须先取得实际独占guardian实例锁，原启动
记录须匹配所持资源域；仅此时可对原service叶执行cgroup.kill。
先完成内核空域核验，再取原核心账本写锁，避免遗留journal进程
持锁阻塞回收。按原ticket退休slot，保持停止、设备保护、代次、
失败/冷却及额度；写入中断继续，丢回执不重复扣减。新空域、错
部署、仍存活的原实例均不能取得清理授权。

本组冻结28 CPU：10新实际root进入/降权/FD关闭及新实例原域回收
用例（含真实孤儿、旧writer持锁、丢出生回执、换域/部署、活实例、
core写入中断和外层回执丢失），2直接内核、8原策略、4原存储、
2连续运行、2封包。只操作新建自有CPU域，不使用GPU、NVML或
设备规则。跨boot资源再建立、宿主适配及R07组合仍必须继续。

## 跨 boot 再建立（针对性 CPU 接受）

新增 `resource-domain renew`，显式enter也续办该原安装。实际boot
改变且旧路径不存在时，先持久保存原record和新boot的renewing
检查点并撤公开准入，再建立同一服务/域UUID/UID/限额的新内核域。
完成后保留previous_record，公开新的inode/boot与递增revision。
不重置核心、外层、设备预算或人工意图；未选配置不会自动安装。
同boot域消失、其他进程创建同名域、撤销/removed安装均不重新
初始化。中断后只能续办原目标；再次boot必须仍满足旧路径消失。
旧boot卸载可以直接留removed历史，不为了删除而创建新内核域。

冻结13项针对性CPU：8历史boot数据+实际新内核域，覆盖重建、
同boot丢域/新boot同名域拒绝、部分写入、ready回执失败、再次boot、
旧boot卸载与显式进入；2直接管理、1实际Guardian角色、2封包。
不执行宿主重启，不查询GPU/NVML，不把历史夹具称为实机重启验收。
原资源绑定的跨boot未知出生slot核验仍须接续实现。

2026-11-12。资源跨boot再建立[13 CPU首过](evidence/serve-resource-renew-cpu-20261112/README.md)，累计4.722秒；明确历史boot夹具+实际自有内核域，0宿主重启/0GPU。原身份保持、中断续办、同boot丢域/同名域拒绝、撤销不复活与显式进入通过；域全清/默认保持。继续跨boot未知出生slot组合、宿主适配和全部任务。


## 跨 boot 未登记出生与重复重启（针对性 CPU 接受）

原启动必须在fork前持久记录原资源域。新实例持独占实例锁，实际
进入同一管理员安装的新epoch，并确认新service叶为空后，可以
核验原boot的未登记出生slot；来源/目录/域UUID/UID/限额及递增
安装revision必须连续。仍有已知当前boot owner时拒绝，不把它
归入旧资源证明。普通服务启动会在取GPU租约前拒绝未核验的旧
outer attempt，不能从process路径绕过原资源核验。

原ticket/generation/owner先持久写检查点；若核验中再次宿主
重启，只能保持这份检查点并推进实际目标boot。不能重新选择
当前slot、清空停止/设备保护或返还模型/外层额度。资源绑定的
旧记录必须经实际资源入口核验，不能退回仅看JSON的路径。

冻结31针对性CPU：6新增历史资源绑定+实际root域、8跨boot（含
新增检查点再次boot）、8策略、4存储、3运行（含新增绕过拒绝）、
2封包；不执行宿主重启、不用GPU。后续宿主适配、冷准入组合与
真实模型业务/发行继续。

2026-11-12。跨boot原资源核验[31 CPU首过](evidence/serve-resource-reboot-cpu-20261112/README.md)，累计6.995秒；历史boot数据+实际新域能力，0宿主重启/0GPU。出生回执缺失、重复boot检查点续办与原停止/设备保护/额度保持通过；错域/新boot owner/普通启动绕过拒绝。自有域全清、默认保持，继续统一后台/宿主适配、冷准入与全部计划。


## 迁移权限修复（针对性 CPU 接受）

Linux 6.8按cgroup.procs打开时的凭据核验共同祖先权限，原root打开
再传递的方案权限过大。未发行候选改为kernel/installation v2，旧v1
拒绝使用；没有已发行v1资源安装需要迁移，旧证据保留来源身份。
只委托安装根与service的cgroup.procs、service的cgroup.kill给运行UID；
outer入口、所有threads入口、限额/层级控制保持root。父域memory/pids
控制器持续启用，禁止进程进入父域。首次进入outer后关闭root FD、
永久降权，再打开service FD；接收/子启动也重新打开以固定实际凭据。

内核权限按域划界，不按目标PID的UID划界。运行UID可在已委托安装内
向service迁移进程；它不能拉入安装外的进程或逃回root拥有的outer。
同UID服务进程本来共享信号/私有状态信任域，不把它宣称成相互安全隔离。

冻结20 CPU：5新权限负控（实际继承FD针对本次新建的同UID/root域外
进程、业务逃逸、外部自进入、root打开拒绝、控制权限漂移/旧格式）；
4直接内核（自进入/清理、pids、OOM、错误FD），3安装（部分创建、
活动卸载、普通用户读取），4实际启动（降权/关闭FD、完整Runtime旧
writer回收、原生四角色、后台四角色），1跨boot显式进入、1原资源
跨boot核验、2封包。只新建自有CPU进程/域，不设置GPU规则、查询NVML、
操作既有服务或宿主开机项。验证后继续宿主适配/冷准入及全部任务。

controller配置v6绑定外层实际安装回执；CPU采集worker须确认自身
位于原service叶，分别读取memcg、memory.events/pids.events及

和持久预算提出light；历史high事件本身不能当当前压力。全局低

有容纳已合格primary/light差值的余量；该保守约束是额外准入，
不是把物理内存与memcg相加，也不是GPU分配的计量保证。

新启动仍由现有全局容量、Guardian设备准入与内核已配置限额保护；
新观察不能发放启动权限、抹除保护或覆盖人工STOPPED。硬memcg
