# 每层Top-N曲线与指定目标的最小名单

2026-09-28。复用48个去重聊天输入；prefill、decode分别统计，每层专家为
独立实例。先按当前样本频次降序、ID升序破同分，再扫描N=1..512。
本轮“最小N”是**沿这条固定频率排名路径达到指定目标的最小名单大小**；
不是时间/空间最优缓存，也不保证是整组概率目标下所有可能专家组合的最优解。
所有名单为同样本描述性选择，不承诺新业务请求的表现。

## 可见结论

1. prefill达到90%选择覆盖，各层需要N=171–321；达到95%需要243–384。
   层0/17/47分别需312/321/171（90%目标），373/382/243（95%目标）。
   最后几层更集中，但不是所有层都随深度单调变化。
2. prefill若要求80%的token路由全部10个都落入名单，各层需305–423个；
   要求90%则需365–461个。它比“覆盖90%的专家选择”严格得多，两者不可互换。
3. 同层不同阶段的需求不同：层15达到90%选择覆盖，prefill需291、decode
   只需160；层47则prefill需171、decode需197。不能用统一阶段排名或容量。
4. decode达到90%选择覆盖，各层需160–342；层0需342，层15需160，层31
   需165。若目标改为80%整组概率，三层分别需422、226、242。
5. 可以由表建立分层候选名单，但不能直接安装为驻留配置：没有总预算、
   初始化/保留生命周期、prefill块并集、真实I/O耗时与并行争用约束。
   当前prefill是token级路由概率，绝不等价于完整prefill块的专家需求覆盖。

## 怎样用这张表

先明确要描述选择覆盖还是整组概率，然后按层读取最小N。比如可把“每层
90%选择覆盖”作为一份对照画像；它不是默认上线策略。需要进一步设计
缓存时，再在独立业务校准/留出数据和同总字节预算下比较，不能据这次
同样本结果直接声称容量最优或实际时间收益。
