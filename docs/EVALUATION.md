# 评估与变更验收规范

本规范以用户2026-09-27补充为准：E2E前置主要约束性能优化，
Bug修复应选择适合缺陷的验证方式。代码决定行为，测试结论应
严格限定在其覆盖范围，不以局部通过代替整模型验收。

## 按任务目标选择验收路线（2026-10-20）

用户明确原则：非性能优化的业务推进出现小幅性能波动可以接受；
进行性能优化时，必须按本规范评估性能优化结果。

- **业务推进、功能开发、可靠性加固、正确性修复**：在正确性、业务
  要求和适用质量检查满足后，以有界实测作工程决定。小幅观察波动
  本身不阻塞交付，不要求证明严格零性能损失，也不为这种波动重复
  要求专项风险确认。记录原值与影响，不凭事后差值虚构统一百分比
  容差；缺少必要测量、合同失败或不满足业务要求的问题仍须处理。
- **性能优化**：按下述性能优化流程及接受条件执行，保持HTTP E2E
  优先、适用五档父候选对照、目标收益与各保护项评估。不能以业务
  推进允许小幅波动为理由宣布优化通过。有限工程接受只在其既定
  条件满足时使用；统计主张必须有对应证据。
- **混合任务**：分别说明业务目标与优化目标，分别给出交付/评估
  结论。业务完成不等于优化成功；不得把实际优化改名以降低门槛。

采用[性能决策协议](PERFORMANCE_DECISION_PROTOCOL.md)分别记录证据
有效性、测量完整性、统计结论和工程决定。先按真实任务目标分类，
再选路线；performance_decision.py的engineering字段不能代替这一
分类或性能优化评估，工具不批准部署。

未测量先补齐获授权的必要有界测量，预算用尽不自动扩样。已有同
身份接受决定不得因相同统计保留反复确认。新算法、精度、执行映射
或重大调度变化须事前明确额外合同；部署范围仍遵循当前会话授权。
下述历史单项决定保留，不追改既有结果。

## SSD专家卸载的资源与读取前提（2026-10-21）

本项目的容量offload仅指SSD后备。Thor的CPU/GPU分配共用DRAM，
host staging、L2、mirror、文件页缓存和库内部缓冲均占统一RAM；
降低device分配或提高CPU缓存命中率不等于降低总RAM。
默认全驻留健康、热缓存启动和单独memcg限额不能代替SSD容量验收。

按[SSD offload合同](SSD_OFFLOAD_CONTRACT.md)冻结工作集与缓存条件，
持续观察缓存，区分逻辑checkpoint读取和实际存储I/O及归属，明确
漏计/重叠范围。不将独立峰值相加，不把未测量项记0。GDS/cuFile
成功也不证明原生直达或减少复制，须记录实际路径与内部缓冲成本。
这一前提不改变上述任务分类、HTTP优先顺序及有界测量原则。

## 执行顺序

按用户2026-09-28补充，一轮工作先冻结范围与出口，成组修改后统一
测试；只对真实失败定位或消融，重验受影响部分。未受改动影响且
身份可核对的证据复用，记录首次失败与修复，不覆盖失败或反复采样
寻找有利结果。必要正确性修复的性能代价与优化接受结论分别记录。

### 性能优化

1. 实施明确、可回退的改动，必要构建不算测试。
2. 第一项测试为tools/evalscope真实HTTP E2E；此前不跑单测、
   kernel微测、bench或profile。现有bench不作为性能验收依据。
3. E2E质量/性能失败时保存请求、响应及日志，修复或回退。
4. E2E通过后才做阶段计时、profile及必要细分析。

### 简化改动的有限工程接受（2026-10-18）

仅删除重复计算、重复元数据获取或冗余同步，且精度、实际计算形状、
kernel分派、状态与输出合同保持不变的局部可回退改动，可申请工程接受。
新增算法、精度变化、执行映射或调度策略变化不适用。声称提速、统计持平
或性能非劣，仍须提供相应测量和统计依据，不能用本途径替代。

工程接受须同时满足：

1. 明确实现身份及变更依赖，零警告构建；逐项审查受影响计算、状态、
   终止合同，必要直接验证通过，没有未解决的关键正确性缺口。
2. 保留真实HTTP优先顺序、质量验收和单流五档E2E；MTP与普通decode
   分组报告精确父版本与候选的同配置对照，公开全部TTFT/decode结果。
   身份和依赖未变的证据可复用，不能用局部测试代替整模型质量。
3. 环境及证据有效，没有已确认的可归因性能退化。质量、计算合同失败
   或可信可归因退化仍否决；不能用其他档收益抵消失败档。
4. 具体说明简化价值、回退方式、测量的限制和未排除的退化风险。
   “未发现退化”本身不构成通过，必须结合前三项、变更范围及回退能力。
5. 项目负责人明确认可本次列出的计时不确定性后，标记
   ENGINEERING_ACCEPTED_WITH_TIMING_UNCERTAINTY。不得标记统计持平，
   不得把点估计当作真实退化上界、噪声带或通用容差。

未来候选须在采样前冻结适用路线、合同、指标、预算和停止条件。
预算用尽后，在已披露风险下明确工程接受或不接受；不自动启动校准，
不为取得有利结果重复采样。有具体关键缺口才提出针对该问题的固定预算，
执行需另有授权。已确认缺陷/可归因退化时回退；普通运行记录出现疑点时
先核对身份和记录，不把单次微小计时波动自动判作真实回归。

## 基线配置

- 单请求并发 1、服务 max_seq=1，greedy decode；MTP 自 2026-10-14 起默认
  开启（k=3），--no-mtp 回退普通 greedy decode（性能基线侧）。
- serve 默认开启 MTP；--mtp 显式开启（与默认相同），--no-mtp 明确关闭。
  MTP 使用独立结果组，不与普通 decode 混算。启动日志必须确认实际模式。
- 保持 checkpoint 和当前精度；禁用 Q4T_FP8_* 实验开关，记录实际环境。
- 服务容量必须容纳 prompt 加输出；max_prefill 是分块大小，**不是最大上下文**。
  固定分块策略。容量被预算器缩减、输入截断或退化路径变化必须报告。
- 固定质量题与同输入重复性能使用 tools/evalscope/run_acceptance.py，
  入口说明和参考边界见 tools/evalscope/README.md。run_baseline.sh 保留
  每档三条不同输入的初始采集用途，两类矩阵不混算；部分结果不能声明
  整个矩阵通过。两个入口均不发送额外连接测试请求。
- 所有生成产物放 build/ 或 .q4t-work/；模型目录与 reference/ 只读。

## 模型加载等待

`tools/evalscope/run_acceptance.py --startup-timeout SECONDS`只控制服务
启动、模型加载阶段的等待，默认仍180秒，必须为正整数；实际配置
写入server-command.json。仅在服务日志出现监听就绪后发送HTTP请求。
该参数不改变请求超时、输出质量判断、五档性能要求，也不把模型
加载时间混入请求TTFT。加载超时须保留原失败记录，明确原因后用
新证据目录重跑；延长等待本身不能证明加载性能或资源问题已修复。

## 五档上下文

长度按实际服务端分词后的输入 token 数计算，不以字符数或文件大小代替。
K 在本矩阵按 1024 计；历史 44002-token 等结果单独标注，不视为同一输入。

| 档位 | 目标输入 token 数 | 输出上限 | 并发 |
|---|---:|---:|---:|
| 1K | 1024 | 256 | 1 |
| 4K | 4096 | 256 | 1 |
| 8K | 8192 | 256 | 1 |
| 44K | 45056 | 256 | 1 |
| 200K | 204800 | 256 | 1 |

固定输入、seed、greedy 和输出上限；保存请求内容与实际 usage。
输出目标为 256 token，但不得假设服务支持 min_tokens/ignore_eos。
提前 EOS、生成不足、长度不匹配必须显示，不能当作等长结果比较。
每档至少 3 次正式请求；服务加载后的首请求与后续请求分别列出。
这只是最低重复数，不能用 3 个样本宣称稳定的尾延迟或微小提速。

## 指标与证据

- E2E：成功/失败数、HTTP/SSE 完整性、实际输入输出长度、总耗时与错误。
- TTFT：客户端发送请求到首个有效内容 token；含接入、排队、分词和 prefill，
  **不是纯 prefill 时间**。input_tokens/TTFT 只能称有效输入处理速率。
- Decode：首 token 到末 token 的时间、(输出 token 数−1)/该时间、TPOT；
  记录 ITL P50/P95。SSE chunk 可能含多个 token，不得把 chunk 间隔冒充 ITL。
  工具未提供准确 token 时间戳时标明限制，不编造分位数。
- 全程吞吐：输出 token 数/整个请求时间，单列，不能称为 decode tok/s。
- 纯 prefill/内部 decode 阶段时间：E2E 通过后才进一步采集，并保留客户端指标。
- 当前 evalscope 将无 choices 的 SSE usage 写入数据库 token 列，不保存在
  response_messages；脚本依据计数列验收，不假设响应列表末尾存在 usage。
- 保存 commit、未提交 diff、二进制摘要、构建参数、模型标识、evalscope 版本、
  全部启动与请求参数、实际 MTP 路径、精度开关、服务器日志及工具原始报告。
  首次建立同口径基线前，历史数字全部仅供参考。

生成内容及已接受版本的 greedy 输出作为 E2E 对照。Bug修复的数值
检查可以先于HTTP；性能优化仍按E2E前置。不能用near-tie泛化解释所有差异。

决定，不据此宣称统计性能条件通过。两条路线均保留质量、计算合同、

### 两类合入通道

- 简化型：说明删除的分支、重复实现、状态或维护负担，保留行为与
  数值合同，性能持平即可接受；不要求正收益或统一最低收益率。
  代码行数减少本身不证明复杂度下降，须说明实际维护/执行影响。
- 提速型：新增专用内核、调度分支或维护成本时，事先说明目标收益
  与成本是否相称；最低值得投入的收益按任务冻结，不设全项目门槛。
  未达到投入目标可停止，即使尚未证明发生性能回退。

两类均不得以复杂度收益交换已确认的性能回退。测量能力不是允许
真实回退的预算；工程可接受不应改写为统计持平或精确零差。

### 执行前冻结的判定卡

每个阶段记录以下内容，缺项先离线补齐，不先启动试验：

1. 基线/候选代码与binary身份、构建依赖、输入、运行参数、环境范围；
   已通过且身份/依赖未变的证据及其复用范围。工具变化单独记录。
2. 改进类型、复杂度变化、目标指标与全部保护项；逐档分别判断TTFT
   与decode，不用平均收益抵消单档回退。
3. 分别记录各指标的测量能力（重复层级、变异来源）与实际损失
   界限；后者只有统计非劣路线需要事前明确。列出证据、适用条件、
   比较统计量和不确定性计算方法。只能使用可比的未插桩、原配置同身份重复证据估计，
   不拼入降频、profile、污染或不同请求位置的数据扩大容忍范围。
   历史三次极差只是有限观察，不等于完整噪声上界；不能把TTFT波动
   百分比直接用于decode。无充分依据的分辨带标为未建立，禁止
   随意填0.5%/1%或用本候选结果倒推。小样本不能硬套置信结论。
4. 固定请求总数、顺序、环境有效性要求，以及下面三种出口。
   默认五档各3次不因微小差异自动增加。比较区间可由预先说明且
   适合已有数据的方法给出；若无法可信估计，结论只能是证据不足。

工程接受路线仍冻结上述身份、全部指标、预算与停止出口；第3项
如无法可信估计测量不确定性，须明确记为未建立并披露风险，不以此
自动转为通过，也不为常规工程决定编造统计损失界限。
第4项中“只能是证据不足”及下表用于统计结论；独立工程决定按有限
路线要求记录负责人认可或拒绝，不能改写统计结论。首次B1a采用须
单独认可已观察证据下的风险，不追认旧判定卡通过。

统计路线统一将差值换算为“正值表示变慢”，事前冻结估计对象、
实际损失界限δ和区间方法；δ不是同身份噪声带，不能由候选结果倒推。
按所有保护项的预定整体规则判断，以下为单项区间的含义：

| 统计出口 | 证据要求 | 动作 |
|---|---|---|
| 非劣条件满足 | 有效设计下，单侧上界不超过该项事前δ | 整体保护项及合同均满足后才可作预定统计主张，部署另查授权 |
| 明确回退 | 有效区间下界超过该项事前δ，或独立证据确认真实退化机制及影响 | 拒绝或修复，不以其他档收益抵消；δ不掩盖独立确认的退化 |
| 证据不足 | 区间跨界、δ/有效设计未建立或样本不足 | 结束该轮统计阶段，不自动扩样；工程路线的独立决定另记 |

非劣不等于等效或精确相等，δ>0的非劣也不代表零损失。双侧等效或
提速主张需自己的事前判据。工程路线不强制虚构δ或区间；完整实测
与负责人决定齐备可工程交付，统计结论保留不足。区间重叠、不显著、
输出相同或未调用新内核均不能单独证明持平；三次范围分离或一次
方向一致也不能单独证明回退。所有数值合同失败仍独立处理。

### 诊断预算与停止条件

先审查已有身份、日志、调用路径和测量边界，不新增采样。不是每个
微小差异都需要定位根因；拒绝/归档候选不以根因解释完成为前提。

默认每候选最多一次有界诊断阶段、最多两个具体机制假设；执行前
列出区分预测、干预、固定请求数、有效性条件和停止出口。请求预算
未填写即不执行；零新增请求的离线分析也不得无限扩展工具范围。
此预算是资源上限，不要求把两个假设做满，也不授权重复采样。
已冻结为禁止新增采样的任务继续遵守该限制。

满足任一条件即停止并记录未决或拒绝：

- 没有能区分候选解释的预测/观测，只能再采一次看方向。
- 预定请求或机制预算用尽，结果仍不足；不能追加同类样本、改阈值、
  选择性丢弃失败或将多个不同实验拼成一次通过。
- 观测工具能力不足，下一步变成通用工具研发而非验证具体机制。
- 候选收益不抵新增复杂度或后续诊断成本；简化型不因缺乏提速被拒绝。

ENV_ABORT不作为性能失败；修复明确环境/工具缺陷后，只重做不可用
部分并保留原记录。发现具体代码缺陷后，形成新的修复身份，冻结
受影响重验范围；其他已通过项复用。上述修复不成为无限重试入口。
预算外重启须有新的可验证机制、实际实现变化，或用户明确要求的
独立统计设计，并另立有界阶段。统计设计须解释如何解决原重复层级/

## MTP vs plain 近 tie 合同（2026-10-12）

MTP 开启时 verify 用一次 T=k+1（默认 k=3 → T=4）batch 前向计算 k+1 个
token 的 logits，plain greedy 用 T=1 顺序 decode。两条路径在精确算术下
逐 token 相同，但 BF16 下 GEMM/GEMV tiling 不同，logits 存在累积舍入差。
合同如下：

1. **允许分歧的唯一来源**：某 decode 位 top-2 logits 相距 ≤ N ULP（N=4，
   ULP 取该侧 top-1 量级处的 BF16 单 ULP，量级 ~24 处为 0.125）。此类
   近 tie 分歧是舍入级，允许 MTP 与 plain 选不同 token。
2. **不可解释分歧（缺陷）**：top-2 相距 > N ULP 且两侧均 confident 的
   argmax 翻转，或 causality 负控失败（row0 跨 filler 非逐位一致），或
   状态差无界增长。此类必须定位修复，不得以近 tie 泛化解释。
3. **验收测试**：`mtp_verify_numerics`（全模型、1K prompt、256 步、plain
   T=1 vs batch T=4 差分，判据 ULP 感知）。PASS 条件：causality 负控通过
   且无 > N ULP 双侧 confident 翻转。2026-10-12 结果：flips=4/256 全部
   1–2 ULP 近 tie、confident_both_sides=0、PASS（证据
   .q4t-work/verify-nums-ulp-rerun2/run.log）。
4. **边界**：本合同界定 MTP 与 plain 的 token 级分歧来源，不替代五档 E2E
   的质量与性能验收；MTP 默认部署前仍须完成五档 E2E（质量不回退 +
   decode 提速 50–200%）。局部 PASS 不等于整模型质量通过。

### 近 tie 合同与主流引擎对照（2026-10-16 来源复核）

对照对象是同一逻辑输入在不同 batch/算术路径下的差异，不是任意错误的豁免。

- [vLLM speculative decoding 文档（v0.7.1）](https://docs.vllm.ai/en/v0.7.1/features/spec_decode.html)
  区分算法无损与浮点数值稳定性，明确 batch 大小变化可能改变 logprobs。
  [当前 batch invariance 文档](https://docs.vllm.ai/en/latest/features/batch_invariance/)
  提供 `VLLM_BATCH_INVARIANT=1` 显式启用方式；默认模式不能据此宣称 batch 不变。
- [NeurIPS 2025 论文](https://proceedings.neurips.cc/paper_files/paper/2025/file/f80094a824ba5912d4a2de169c404a40-Paper-Conference.pdf)
  研究有限精度、浮点非结合性导致的系统配置敏感性；BF16 greedy 的
  DeepSeek-R1-Distill-Qwen-7B 在不同 GPU 数/类型及 batch size 下，报告最高
  9% 准确率与 9000 token 响应长度差。这是特定实验结果，不是本模型的容差。
- [Microsoft LLM-42（2026，v2）](https://arxiv.org/abs/2601.17768v2)
  同样指出浮点非结合性、动态 batching 和归约顺序的作用，但它通过固定形状
  verifier 与 rollback **强制确定性**，并非提倡无限制接受 token 翻转。

据此，本项目合同**比 vLLM 默认非 batch-不变模式有更严格、可检验的显式边界**：
N=4 BF16 ULP、双侧 confident 翻转拒绝、causality 负控；每个数值 PASS
仍限于实际测过的输入与步数。不能推导为所有输入上的误差上界，也不能声称
比 vLLM 的 batch-invariant 模式或 LLM-42 的确定性保证更强。
来源解释了差异机制，不替本项目证明正确，更不授权放宽 N=4 或忽略状态缺陷。
五档 HTTP 的重复确定性、输出合同、任务质量与性能分别记录。
