# 评估与变更验收规范

本规范以用户2026-09-27补充为准：E2E前置主要约束性能优化，
Bug修复应选择适合缺陷的验证方式。代码决定行为，测试结论应
严格限定在其覆盖范围，不以局部通过代替整模型验收。

## 执行顺序

按用户2026-09-28补充，一轮工作先冻结范围与出口，成组修改后统一
测试；只对真实失败定位或消融，重验受影响部分。未受改动影响且
身份可核对的证据复用，记录首次失败与修复，不覆盖失败或反复采样
寻找有利结果。必要正确性修复的性能代价与优化接受结论分别记录。

### 性能优化

1. 实施明确、可回退的改动，必要构建不算测试。
2. 第一项测试为tools/evalscope真实HTTP E2E；此前不跑单测、
   kernel微测、bench或profile。现有bench不作为性能验收依据。
3. E2E质量/性能失败时保存请求、响应及日志，修复或回退。
4. E2E通过后才做阶段计时、profile及必要细分析。

### Bug修复

1. 明确缺陷合同、最小复现和预期值，选择相应单测、边界数值、
   差分或集成测试；允许这些测试先于HTTP。
2. 验证修复直接消除了缺陷，同时保留反例与失败记录。HTTP任务
   分数变化不能单独判定格式/算术修复错误，也不能被局部测试掩盖。
3. 涉及运行时行为时，再做对应HTTP质量回归；任务质量与实现
   符合性分开报告。按用户最新责任划分，语义分数下降不单独否决
   已证明的数值修复，更不能以保留错误计算来维持答案。出现差异
   仍需检查接入、模型合同与测试完整性；局部通过不自动批准发布。
4. 需要接受性能不回退或优化结论时，仍完成本规范五档E2E矩阵；
   不能用局部速度、相邻一次结果或未完成矩阵宣称通过。

### 结构整理、构建与测试工具

先冻结受影响范围，成组修改后运行构建、直接合同及工具自身检查。
仅修改文档、测试或独立host构建入口，且运行时代码/部署身份不变时，
不运行模型HTTP或五档性能。公共CI只证明实际执行的host检查。
运行时结构整理先跑受影响的直接测试，再做对应HTTP质量、取消/失败
等集成回归；阶段交付需声明性能保持时统一做五档E2E，不按文件拆分
重复全套验收。若改动目标包含提速或执行映射优化，仍按“性能优化”
顺序，不通过改名为重构绕过E2E前置。已通过且身份/依赖未变的证据
明确复用；发现具体失败后只重验受影响部分。

每次有意义变更更新STATUS与当天日志，明确通过、失败、未运行及
证据位置。纯文档治理不运行推理测试，也不宣称运行时通过E2E。
已冻结HTTP证据可以复用；无须为纯离线分析反复启动HTTP。

## 当前MoE Router分析阶段的收敛顺序（2026-09-28用户补充）

先完成工具、采样和分析，再统一做质量与性能验收；过程中不随中间改动
反复测试。直接合同成组完成，发现具体失败才定位并重验受影响项。
已经通过且身份/依赖未变的质量、性能与直接合同证据复用，不为文档、
报告或路径整理重跑推理。正在执行的检查保留原始记录；不因调整顺序
删除或挑选结果。此约定限定当前MoE Router分析阶段，不自动放宽后续
真实加载/驱逐及其他性能优化的门槛。

## 基线配置

- 单请求并发 1、服务 max_seq=1，普通 greedy decode，MTP 关闭。
- serve 默认关闭 MTP；--mtp 显式开启，--no-mtp 明确关闭。MTP 使用独立
  结果组，不与普通 decode 混算。启动日志必须确认实际模式。
- 保持 checkpoint 和当前精度；禁用 Q4T_FP8_* 实验开关，记录实际环境。
- 服务容量必须容纳 prompt 加输出；max_prefill 是分块大小，**不是最大上下文**。
  固定分块策略。容量被预算器缩减、输入截断或退化路径变化必须报告。
- 固定质量题与同输入重复性能使用 tools/evalscope/run_acceptance.py，
  入口说明和参考边界见 tools/evalscope/README.md。run_baseline.sh 保留
  每档三条不同输入的初始采集用途，两类矩阵不混算；部分结果不能声明
  整个矩阵通过。两个入口均不发送额外连接测试请求。
- 所有生成产物放 build/ 或 .q4t-work/；模型目录与 reference/ 只读。

## 模型加载等待

`tools/evalscope/run_acceptance.py --startup-timeout SECONDS`只控制服务
启动、模型加载阶段的等待，默认仍180秒，必须为正整数；实际配置
写入server-command.json。仅在服务日志出现监听就绪后发送HTTP请求。
该参数不改变请求超时、输出质量判断、五档性能要求，也不把模型
加载时间混入请求TTFT。加载超时须保留原失败记录，明确原因后用
新证据目录重跑；延长等待本身不能证明加载性能或资源问题已修复。

## 五档上下文

长度按实际服务端分词后的输入 token 数计算，不以字符数或文件大小代替。
K 在本矩阵按 1024 计；历史 44002-token 等结果单独标注，不视为同一输入。

| 档位 | 目标输入 token 数 | 输出上限 | 并发 |
|---|---:|---:|---:|
| 1K | 1024 | 256 | 1 |
| 4K | 4096 | 256 | 1 |
| 8K | 8192 | 256 | 1 |
| 44K | 45056 | 256 | 1 |
| 200K | 204800 | 256 | 1 |

固定输入、seed、greedy 和输出上限；保存请求内容与实际 usage。
输出目标为 256 token，但不得假设服务支持 min_tokens/ignore_eos。
提前 EOS、生成不足、长度不匹配必须显示，不能当作等长结果比较。
每档至少 3 次正式请求；服务加载后的首请求与后续请求分别列出。
这只是最低重复数，不能用 3 个样本宣称稳定的尾延迟或微小提速。

## 指标与证据

- E2E：成功/失败数、HTTP/SSE 完整性、实际输入输出长度、总耗时与错误。
- TTFT：客户端发送请求到首个有效内容 token；含接入、排队、分词和 prefill，
  **不是纯 prefill 时间**。input_tokens/TTFT 只能称有效输入处理速率。
- Decode：首 token 到末 token 的时间、(输出 token 数−1)/该时间、TPOT；
  记录 ITL P50/P95。SSE chunk 可能含多个 token，不得把 chunk 间隔冒充 ITL。
  工具未提供准确 token 时间戳时标明限制，不编造分位数。
- 全程吞吐：输出 token 数/整个请求时间，单列，不能称为 decode tok/s。
- 纯 prefill/内部 decode 阶段时间：E2E 通过后才进一步采集，并保留客户端指标。
- 当前 evalscope 将无 choices 的 SSE usage 写入数据库 token 列，不保存在
  response_messages；脚本依据计数列验收，不假设响应列表末尾存在 usage。
- 保存 commit、未提交 diff、二进制摘要、构建参数、模型标识、evalscope 版本、
  全部启动与请求参数、实际 MTP 路径、精度开关、服务器日志及工具原始报告。
  首次建立同口径基线前，历史数字全部仅供参考。

## 精度与接受条件

HTTP 200 或 evalscope perf 跑完只证明链路和性能采集可用，不能证明模型精度。
当前矩阵使用 prepare_inputs.py 生成的固定技术文本负载，并保存 requests.jsonl。
它不是生产语料或质量基准；随机 token 数据也不承担语义正确性验收。保留固定真实文本请求、
生成内容及已接受版本的 greedy 输出作为 E2E 对照。Bug修复的数值
检查可以先于HTTP；性能优化仍按E2E前置。不能用near-tie泛化解释所有差异。

接受条件：保持当前精度，五档均无超出基线重复波动的性能回退。基线波动尚未
测出时，不先发明一个固定容忍百分比。复杂度下降且性能持平也可以接受。
短上下文的收益不能抵消长上下文回退；未完成的档位不能标为通过。

## 2026-09-27 最新责任划分与验收

Runner必须忠实执行模型计算合同，不能用实现错误补偿模型任务分数。
保持精度指遵守约定格式、舍入、累加与状态语义，不指维持错误输出。
正确实现不要求无限精度或所有路径逐位相同；近似与差异须有事先定义
的合同和证据。历史错误版本仅作兼容/性能对照，不是正确性oracle。

近期工作按四项独立标记：缺陷合同、运行时数值接入、HTTP任务质量、
性能。格式通过可以接受为局部修复；不得扩大为整模型或商用发布通过。
质量下降保留并调查，但不能仅据分数恢复已知错误；性能变化如实测量，
不以错误实现更快为理由拒绝必要的正确性修复。性能优化自身仍须遵守
E2E前置及五档无回退要求。具体重验结论见
[近期工作验收](NUMERICAL_ACCEPTANCE_2026-09-27.md)。
