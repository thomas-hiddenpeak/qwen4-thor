# 评估与变更验收规范

本规范来自 2026-09-20 用户决定，覆盖历史文档中的旧测试顺序与性能口径。
代码决定实际行为；本规范决定开发与验收要求。未实现的要求必须标明待实现。

## 执行顺序

1. 实施一个明确、可回退的改动；运行所必需的编译不算测试。
2. **第一项测试必须是 tools/evalscope 的真实 HTTP E2E**。不在此前运行
   单元测试、kernel 测试、bench、数值微测试或性能 profile。
3. E2E 失败或出现回退时，保存失败请求、响应与服务日志，修复或回退，
   再跑 E2E。不得用低层测试通过来覆盖 E2E 失败。失败处理所需日志排障
   不等于开始 kernel 性能细分析。
4. 只有 E2E 通过，才针对仍有疑问的问题进行阶段计时、profile 或必要的
   正确性细分析；它们不能替代 E2E 验收。现有 bench 不作为本轮评估工具。
5. 更新 STATUS 与当天日志，写清通过、失败、未运行及证据位置。

纯文档治理不运行推理测试，也不能据此宣称运行时已通过 E2E。

## 基线配置

- 单请求并发 1、服务 max_seq=1，普通 greedy decode，MTP 关闭。
- serve 默认关闭 MTP；--mtp 显式开启，--no-mtp 明确关闭。MTP 使用独立
  结果组，不与普通 decode 混算。启动日志必须确认实际模式。
- 保持 checkpoint 和当前精度；禁用 Q4T_FP8_* 实验开关，记录实际环境。
- 服务容量必须容纳 prompt 加输出；max_prefill 是分块大小，**不是最大上下文**。
  固定分块策略。容量被预算器缩减、输入截断或退化路径变化必须报告。
- 使用 tools/evalscope/run_baseline.sh 的五档矩阵，支持指定部分档位续跑；
  部分结果不能声明整个矩阵通过。脚本不发送额外连接测试请求。
- 所有生成产物放 build/ 或 .q4t-work/；模型目录与 reference/ 只读。

## 五档上下文

长度按实际服务端分词后的输入 token 数计算，不以字符数或文件大小代替。
K 在本矩阵按 1024 计；历史 44002-token 等结果单独标注，不视为同一输入。

| 档位 | 目标输入 token 数 | 输出上限 | 并发 |
|---|---:|---:|---:|
| 1K | 1024 | 256 | 1 |
| 4K | 4096 | 256 | 1 |
| 8K | 8192 | 256 | 1 |
| 44K | 45056 | 256 | 1 |
| 200K | 204800 | 256 | 1 |

固定输入、seed、greedy 和输出上限；保存请求内容与实际 usage。
输出目标为 256 token，但不得假设服务支持 min_tokens/ignore_eos。
提前 EOS、生成不足、长度不匹配必须显示，不能当作等长结果比较。
每档至少 3 次正式请求；服务加载后的首请求与后续请求分别列出。
这只是最低重复数，不能用 3 个样本宣称稳定的尾延迟或微小提速。

## 指标与证据

- E2E：成功/失败数、HTTP/SSE 完整性、实际输入输出长度、总耗时与错误。
- TTFT：客户端发送请求到首个有效内容 token；含接入、排队、分词和 prefill，
  **不是纯 prefill 时间**。input_tokens/TTFT 只能称有效输入处理速率。
- Decode：首 token 到末 token 的时间、(输出 token 数−1)/该时间、TPOT；
  记录 ITL P50/P95。SSE chunk 可能含多个 token，不得把 chunk 间隔冒充 ITL。
  工具未提供准确 token 时间戳时标明限制，不编造分位数。
- 全程吞吐：输出 token 数/整个请求时间，单列，不能称为 decode tok/s。
- 纯 prefill/内部 decode 阶段时间：E2E 通过后才进一步采集，并保留客户端指标。
- 当前 evalscope 将无 choices 的 SSE usage 写入数据库 token 列，不保存在
  response_messages；脚本依据计数列验收，不假设响应列表末尾存在 usage。
- 保存 commit、未提交 diff、二进制摘要、构建参数、模型标识、evalscope 版本、
  全部启动与请求参数、实际 MTP 路径、精度开关、服务器日志及工具原始报告。
  首次建立同口径基线前，历史数字全部仅供参考。

## 精度与接受条件

HTTP 200 或 evalscope perf 跑完只证明链路和性能采集可用，不能证明模型精度。
当前矩阵使用 prepare_inputs.py 生成的固定技术文本负载，并保存 requests.jsonl。
它不是生产语料或质量基准；随机 token 数据也不承担语义正确性验收。保留固定真实文本请求、
生成内容及已接受版本的 greedy 输出作为 E2E 正确性对照；数值路径有改动时，
E2E 通过后仍需相应精度分析才能接受，不能用 near-tie 泛化解释所有差异。

接受条件：保持当前精度，五档均无超出基线重复波动的性能回退。基线波动尚未
测出时，不先发明一个固定容忍百分比。复杂度下降且性能持平也可以接受。
短上下文的收益不能抵消长上下文回退；未完成的档位不能标为通过。
