# 真实NVFP4块与down投影的独立参考

## 结论

在原4K错题的首四个专家调用中，确认格式缺陷会改变FP4重编码，
并传播到down投影，而不仅是一个孤立的尺度代码差异。正式运行时
仍为2392f6b1，未应用修正，未重新接受此前拒绝的候选。

本轮实际输出核对：286720个FP4元素与独立参考相同；1146880个
实际down输出BF16位模式与FP64参考舍入结果相同。离线仅替换
不符合规范的7个E4M3尺度组，重新量化后7个FP4编码变化，最终
16655个参考投影输出的BF16位模式变化。

这是局部计算影响，不是最终答案因果。未执行修正后的完整模型，
不能宣称修复4K错误、提高任务质量或满足运行时精度/性能门禁。

## 新观测的HTTP顺序

扩展独立诊断库后必要构建退出0、零警告，首项测试仍为evalscope
真实HTTP。原4K题无观测→有观测→无观测各一次，配置同前报告，
三次均600440、4096输入/7输出、stop，三个服务退出0。
质量驱动均因原题应为360284而退出1，保留这个失败。

所有新增观测有界为四个调用，不写设备数据、不修改正式二进制；
本次回答一致不证明观测对所有请求无影响，观测时延不用于性能。
HTTP核对完成后才编译/运行快照重算和参考分析，没有前置低层测试。

## 实际捕获及绑定

沿用SwiGLU输入/尺度快照，在其紧接的cublasLtMatmul结束后捕获
实际FP4激活、权重字节、权重尺度、GEMM激活尺度和BF16输出。
先核对矩阵描述符：A为列主640×2560并转置，B为列主640×M，
D为列主2560×M/BF16，两侧vec16尺度、host alpha、beta=0。

实际矩阵权重和反swizzle后的尺度逐字节匹配checkpoint第0层的
expert0/1/2/3 down投影，激活input_scale也精确匹配。实际alpha
等于float32(weight_scale_2×input_scale)，未漏乘或重复乘全局尺度。
这绑定了本轮四份样本的层/专家身份，不推广到所有层或decode。

GPU上的实际GEMM激活尺度与量化后所保存的尺度逐项相同。
各专家行数2/24/21/401，总计448行、17920组。行号只表示该次
专家紧凑缓冲中的局部行，不能直接跨采集映射成prompt token位置。

## 独立参考的组成

1. 按原float32/__expf公式重建SwiGLU值；旧规则尺度重算与实际
   17920组全同。此部分复现原算术，不宣称SwiGLU公式独立验证。
2. 用独立E2M1数值集合及最近偶数选择，按实际尺度重新编码，
   与全部286720个实际FP4元素相同，不调用项目E2M1编码函数。
3. 独立解码实际FP4激活与权重、E4M3组尺度，使用FP64矩阵乘法
   和实测alpha构成参考。参考舍入为BF16后，与1146880个实际
   GPU输出位模式全同，包括符号位核对。
4. 只将错误的E4M3组尺度换成独立最近偶数结果，再按同样规则
   编码FP4、乘同一权重，形成离线反事实对照。CUDA原生FP8转换
   与独立枚举参考也逐组一致。

FP64参考不模拟cuBLAS的FP32累加顺序。本样本BF16位同是观察结果，
不是一般形状下逐位相等的保证；没有为差异发明容忍阈值。

|---:|---:|---:|---:|

没有尺度变化的行，两个FP64投影参考完全相同。变化行集合的投影
相对L2差异为expert0的0.267343、expert2的0.089852，分母为这些行
旧规则投影的L2范数；不是全模型误差或输出质量指标。

相对于同一批未量化SwiGLU值，expert0全部2行的激活量化相对L2
误差从0.176916降至0.055232；expert2全部21行从0.096243降至
0.067115。其余两专家不变。这只证明本批局部重建更接近原输入，
不能外推为最终答案更准确。

两份仍发现旧编码格式错误的GPU重算退出1，另外两份退出0；所有
参考脚本核对完成退出0。不能混淆“分析完成”和“旧格式正确”。
