# 资源控制面依赖隔离：CPU阶段

2026-11-07，按用户继续推进要求，复用当前分支。属于可靠性修复，
只开发和针对性CPU验证，不追加GPU、模型、真实NVML或生产服务操作；
默认、旧包与视觉候选保持，不自动重启模型或服务管理器。

## 冻结范围

- 新v10包仅在同时选择degrade与host资源隔离时生成；其他配置保持
  v9或原严格包版本。v1至v9封存包不改写，v10继续要求零模型重启。
- 初始化、后端加入cgroup、最终scope清理确认仍要求systemd身份
  与内核合同。运行期直接检查原cgroup路径/目录身份、监督器进程
  身份/成员关系、内核限额及资源事件，不再每轮调用systemctl/D-Bus。
  状态明确标记管理器NOT_QUERIED，不伪称管理器可用或已恢复。
- memory.current/peak、swap.current和pids.current作为资源统计，
  运行期缺失记未知并累计缺口；memory/pids事件、cgroup人口、身份
  与限额是保护依据，读取失败仍停止自有后端。OOM、任务上限事件、
  限额漂移保持终止，不使用重启预算。纯统计恢复不清除历史缺口。
- 系统MemAvailable未知5秒、持续临界低内存2秒、父进程死亡及
  不可中断I/O边界保持；不将资源安全观察与一般监控一并放宽。
- 最终manager不可用仍记录清理未确认，不因此自动重启、接管或
  触碰其他服务；内核硬限制不等于Thor统一物理RAM硬限额。

运行期直接观察的依据是内核cgroup接口；其进程继承/成员关系与
资源控制语义见[Linux官方文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。
本项目仍须验证原目录身份与有效限额，不能仅从服务管理器失联
推断资源隔离继续有效。

## 冻结验证与出口

先成组实现，再以临时文件模拟cgroup接口、真实CPU子进程模拟业务。
验证manager查询异常不进入运行期路径、统计缺失仍推进同一PID、
统计恢复保留缺口、OOM/任务超限/身份改变/限额漂移/关键事件缺失
仍终止、初始化与最终清理不伪造成功。复核v9/v10及严格包兼容、
辅助隔离、监控恢复与监督器期限；仅实际失败重验受影响项。

本轮不创建真实cgroup、不改变systemd/D-Bus，不证明真实资源故障
业务验收或部署健康；CPU结果与生产接受分开，完成后提交推送收口。

所选通过记录共196次，按规范用例ID去重**167项**；期限模块重复
导入监督器29项，逐项ID已封存。9份Python语法零警告，CPU CMake
登记、serve清单124锚点/3负控与生成合同检查通过。没有C++代码变更，
未重编译推理程序或重复GPU/整套host验收。

组合故障场景以临时文件模拟cgroup内核接口，并启动真实CPU业务
子进程；运行期间管理器查询会抛错、memory.peak文件缺失，同一
PID完成64步，单次启动、零重启。管理器与统计恢复后正常停止，
当前统计恢复、历史缺口保留，三次管理器查询仅在初始/最终严格
检查中发生。另一个真实CPU进程在模拟OOM事件后停止且未被替换。
这些场景没有模拟实际内核OOM或实际服务管理器崩溃。

身份/成员关系改变、目录替换/符号链接、control/payload限额漂移、
关键事件/成员文件缺失、OOM/任务上限、非空/外来scope及最终查询
失败分别有负向保护用例。最终采样首次出现统计缺失也进入历史
计数；未增加在线资源控制写入。

旧host观测工具首轮16项通过、1项权限检查失败：本次直接unittest
入口未设置其原驱动`tools/serve_host/cpu.py`的`umask(077)`，导致
nginx语法检查生成的空PID文件为非私有权限。保留首轮原件，按原
驱动条件只重验这1项后通过；没有修改权限校验或产品代码，也没有
重跑已通过项。实际共197次CPU执行，其中该项首次失败仍保留。

当前显式degrade、不启用host资源隔离的prepare仍生成v9；两者
组合才生成v10，仍禁止模型重启。v9/v10清单兼容及客户端/运维端口
组合通过夹具验证，真实旧v7包`f69cb406…`只读verify有效。默认
`ea1b474d…/3eb46385…`与视觉`34e7ceef…/982bba07…`逐一核对未变。

## 尚未扩大与后续边界

- 0真实cgroup创建/资源压力、0模型、0真实模型HTTP、0 GPU测试、
  0真实NVML查询、0生产服务操作；CPU结论不能代替v10真实业务接受。
- 初始资源建立、后端入组仍检查管理器和完整合同；最终控制面
  不可用时不声称scope已退出，不自动重启或接管旧运行目录。
- 新v10运行状态报告`runtime_verification=CGROUPFS`、
  `runtime_manager_observation=NOT_QUERIED`，不推断管理器的实时健康。
  统计缺失用null及`statistics_errors`表示，`statistics_gap_samples`
  仅计采样有缺口的次数，不是故障时长；恢复不清零。
- 独立host exporter的prepare仍只接受旧v5/v6资源包，未自动迁移
  到v10；其原监控失败只影响观察结果，不能据本次兼容回归宣称新
  组合部署接受。开发GPU验证继续使用原严格guard，本阶段不作
  性能验收结论。
- MemAvailable未知/临界低内存、关键cgroup安全证据缺失仍按原保护
  退出；控制器死亡、语法worker有界回收、不可中断文件I/O待后续
  独立设计。当前仅隔离管理器查询路径，不保证systemd停止scope或
  实际终止controller后模型继续存活，也不把memcg当统一物理RAM硬限额。

本轮开发和CPU验证收口；视觉候选继续HOLD，真实短业务及长期稳定性
验证保持待办，不自动追加GPU测试。
