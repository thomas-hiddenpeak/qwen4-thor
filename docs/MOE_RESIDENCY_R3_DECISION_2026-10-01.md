## 为什么需要第三轮

- 第一轮（C=256 均匀 + hot-256，无 L2）：六档 decode 22.0–29.8% 基线，全 FAIL
  <50% 门槛。根因：decode 阶段逐 miss 逐层串行 NVMe 补载。
- 第二轮（C=256 + L2-128 + 常驻补载池）运行中。离线预测 ~30% 基线，仍 FAIL。
  实测在途证据：L2 命中率极低——4096 档 l2h≈316–488 / l2m≈50k（~0.7%），
  45056 档 l2h≈721–760 / l2m≈418k（~0.17%）。L2-128 对该工作集基本无效，
  与离线预测（L2-128 只接 ~6% GPU miss）一致。
- 结论：C=256（无论是否加 L2）大概率无法达到 decode 50% 门槛，需增加每层
  常驻专家数，或改走补载管线优化路线。

## decode 瓶颈定量（第一轮 45056 档反推）

- 基线 decode ≈ 256 tok / 16.9 tps ≈ 15.1 s。
- 候选 dmiss≈6500（decode 阶段总补载次数），单 miss 有效 ~6.2 ms（串行），
  附加加载 ≈ 40 s → decode_tps 掉到 ~4.7 tps ≈ 28% 基线，与实测 22–30% 吻合。
- 达标条件：附加加载 ≤ 15.1 s → dmiss ≤ ~2400（需把 decode miss 降 ~2.7×）。
- 两条降本路径：(A) 增加每层常驻专家（降 dmiss，增内存）；(B) 并行/加速补载
  （降单 miss 时延，GEMM 冻结但补载管线非 GEMM，可动）。

## 关键机制澄清（2026-10-01 06:35，代码核验）

运行时 256 槽是**热启动的 LRU 动态缓存**，不是固定热点表：
`moe_hot_protect` 默认 false（r2 候选未传 `--moe-hot-protect`），
`SetHotProtected()` 不调用，热点表只作初始态，之后按 LRU 逐出/补载
（45056 档实测 evictions==loads==418662，槽常满、持续换入换出）。
因此稳态 miss 率由「LRU 容量 256 vs 逐层 decode 工作集(~250 专家)」决定，
与热点表选择几乎无关。静态 top-256 覆盖（combined 63.6% / decode-only
84.5%）远高于稳态实测 miss（5.3%），正是动态加载抹平了冷启动差异。

**推论：decode 导向热点表（原备选 B）只改善冷启动、不改善稳态，对
decode 50% 门槛基本无效，降级为不推荐。** 有效路径只剩两条：
- **A（第三轮，增 C）**：直接扩大 LRU 容量，降稳态 miss。需新增内存超支。
- **C（补载管线优化，不增内存）**：把单 miss 有效时延从 ~6.2 ms 压到
  ~2 ms（并行 NVMe 读 + 消除 ~4 ms 管线开销；GEMM 冻结但补载管线非 GEMM）。
  定量：45056 档 dmiss≈6539，6.2 ms→40 s（decode≈28% 基线）；2 ms→13 s
  （decode≈54% 基线，**可达 50% 门槛**）。语义不变（全部专家仍计算，仅
  加载更快），符合"不靠减少专家/降精度达标"。

## 补载管线静态分析（2026-10-01 07:00，代码核验，GEMM 冻结未动）

为路径 C 定位 ~4 ms/miss 管线开销，静态复核 decode 热路径（moe.cu
MoEForward 驻留段 + moe_residency.cpp）：

- **每层一次 D2H + 全流同步**（moe.cu:418–434）：router top-k 后把
  expert id + router weight 异步 D2H，随后 `cudaStreamSynchronize(stream)`
  阻塞到该层之前所有 GPU 工作完成，host 才能读 id 做槽位映射。48 层 ×
  每 decode 步一次。基线（C=0）与候选（C=256）都有此开销，故非候选
  减速之源，但它是路径 C 可优化的串行点之一（若能把 id 映射与 GEMM
  重叠）。
- **每层 host 端 token 聚类 + 分块**（moe.cu:440–540）：decode T=1 时
  近乎零成本（单 token）；prefill 分块时是 host 开销，但不影响 decode
  50% 门槛。
- **每 miss 的 Resolve = Plan + Phase1 + Phase2**：Phase1 用 8 个常驻
  load worker 并行（NVMe read + scale merge + swizzle，阻塞），Phase2
  在 stream 上 H2D。单 miss 有效 ~6.2 ms = NVMe read ~2 ms（实测
  3.28 MB 随机 pread 未命中页缓存中位 1.44 ms / p90 2.07 ms）+
  ~4 ms 管线开销。~4 ms 的构成（页缓存压力 / 单流同步 / L2 victim
  互斥往返 / worker 调度）**尚需逐 miss 计时定位**。
- **逐 miss 计时已就绪**：`Q4T_RESIDENCY_TIMING=1` 开启
  stage/pread/swz/phase1/d2h 五段计数（moe_residency.h TimingStats +
  chat_generation.cpp 每请求 delta 输出 `stage_n=...`）。此前所有矩阵
  均未开启（无 `stage_n=` 记录）。已备好
  `.q4t-work/moe-residency-20260930/timing-collect.sh`（候选同配置
  C=256+hot-256+L2-128，单条 45056 请求，~5 min），**待第二轮矩阵
  释放 GPU/NVMe 后立即运行**（两服务并存内存 ~155 GB > 122 GB RAM，
  不可与矩阵并行）。
- **路径 C 优化点（GEMM 冻结，均非 GEMM）**：(a) 并行 NVMe read 已存在
  （8 worker），瓶颈更可能在单 miss 的页缓存未命中 + 单流 H2D 同步；
  (b) 消除 ~4 ms 管线开销（待计时定位后定向优化）；(c) 若 d2h 同步占比
  高，可评估把 id 映射与 GEMM 重叠（需保持数值合同不变）。定量目标：
  单 miss 6.2 ms → ~2 ms，C=256 下 decode 达 ~54% 基线（过 50% 门槛）。
