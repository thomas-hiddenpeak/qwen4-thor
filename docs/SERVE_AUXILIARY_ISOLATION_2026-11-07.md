# 辅助依赖故障隔离：CPU阶段

2026-11-07，用户授权先修复NVML采集器错误、日志写入失败和指标缺失
导致停服的路径，完成针对性CPU验证。复用当前分支，默认程序、旧包
及视觉候选保持；不启动模型、不查询真实NVML、不追加GPU测试或部署。

## 冻结范围

- 新v9显式degrade托管包绑定辅助I/O隔离代码；继续要求restart-limit=0。
  旧v1至v8按原封存源码运行，严格验收guard不开放容错。
- NVML采集器Python/协议错误只暂停观测，不解释为空GPU；明确设备
  故障仍停止自有服务。启动前未知仍拒绝启动，锁/竞争保护保持。
- 普通日志与运行期观测快照写入返回错误时降级，保留内存故障计数，
  每通道60秒内不反复尝试；后端输出管道继续排空。日志有容量上限，
  丢弃量与历史缺口不因恢复清零。启动身份、租约及恢复授权属于
  控制记录，不能借容错绕过；恢复授权保存失败拒绝本次查询。
- v9监督循环读取livez/readyz及配置/身份合同，不再依赖metrics完整性。
  metrics继续通过独立观察入口提供；真实不健康、配置/身份不符、
  停止请求及核心HTTP不可用的保护保持。
- 不扩展内存/cgroup失联、控制器死亡、语法worker回收或设备自恢复。
  本项处理I/O已返回错误，不宣称解决内核不可中断的文件I/O阻塞。

## 验证与出口

成组修改后运行CPU故障矩阵和真实CPU子进程/私有锁闭环：模型替身
在采集器/日志/指标故障时保持PID并持续推进；明确设备故障终止，
无替代启动；旧worker未回收不增殖、历史缺口保留、控制写失败拒绝
恢复。复核旧包、严格guard、监督器时限与包来源；只有具体失败才
重验受影响项。结果只接受CPU范围，不代替真实NVML/模型业务验收。

`dropped_bytes`计入失败或退避跳过的日志输入字节；部分写入可能
已落盘，因此是未确认写入量上界，不能当作精确丢失量。快照恢复后
保留故障历史，超过30秒或时间异常的快照不报告当前READY/已知GPU
PID。磁盘持续不可写时台账只在内存中，意外退出可能无法持久保存；
当前隔离不解决内核不可中断write/fsync，也不接入模型重启或设备reset。

复核新增的修复前失败原件全部保留：

- 末次监控快照/guard事件首次写失败时，退出回执漏记缺口；现在
  最终回执在关闭及最后事件之后、仍持锁时冻结。第一次事件夹具
  只匹配继承锁事件，遗漏直接锁事件，修正选择器后复现了实际故障。
- 监督器末条STOPPED事件首次写失败时，状态快照漏记；v9先尝试
  事件再保存含故障历史的快照，旧严格流程保持。
- 采集器最终状态与完整设备错误记录矛盾时，设备故障被协议分类
  遮蔽；现在独立保留完整错误字段，明确设备故障优先于状态异常。
