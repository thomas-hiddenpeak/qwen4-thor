## 明确问题，按优先级排列

### P1：decode故障被伪装成正常完成（真实HTTP复现）

代码：[chat_server.cpp](../src/server/chat_server.cpp)，调度器在约1196行
将失败传成负token；2249–2273行在调度/回退失败时只设置`stop`；
2301行只仲裁取消，2314–2358行继续正常响应及增加成功计数。

用现有LD_PRELOAD工具对单序列decode的4字节D2H返回错误。
1024-token输入、max_tokens=16、MTP关闭，流式和非流式各一个新服务：

| 检查 | 两种请求实际结果 |
|---|---|
| 第一个请求 | HTTP 200，只输出`7`，completion_tokens=1，finish_reason=stop |
| 流式终态 | 正常stop、usage、[DONE]，没有error事件 |
| 指标 | success=1、error=0、aborted=0 |
| 随后健康与生成 | 均503，GPU不健康；槽位已归还 |
| 停机 | 两个服务均退出0 |

这是合成CUDA返回码故障，不是实际损坏设备；它直接证明已检测错误未
传递到请求终态。此前496640字节prefill注入500/503结论仍成立，
但不能推广到decode。MTP accepted_count<=0也有类似代码分支，未本轮实测。

修复验收：正常完成、取消、计算失败有明确不同终态；非流式失败返回
5xx，已发流式头后发送明确错误而非正常stop；成功计数不得增加。
分别覆盖prefill/decode、copy/sync、活动批次及槽位回收/后续拒绝。

### P1：JSON解析不具备服务级输入边界（独立进程复现）

代码：[json.cpp](../src/io/json.cpp) 52–105行递归下降没有深度限制。
在本机使用实际源码、8MiB进程栈、禁用core，100000层嵌套数组
（200001字节）导致SIGSEGV，32/1024层正常返回。
这是解析器进程复现，未向真实模型服务发送崩溃请求；服务使用同一
解析器且允许16MiB正文，因此现有体积上限不能保护线程栈。

238–260行数字解析也接受`1e`、`01`、`1e999`；字符串接受未转义tab，
本轮均复现。GetInt/AsInt直接将double转int64，没有范围验证；
max_tokens再窄化到int并静默夹限，缺少字段级整数合同。

修复验收：解析深度/节点/字符串预算、严格数字与字符串语法、非有限
值拒绝、整数范围和请求类型检查；畸形输入返回4xx，服务和下一请求正常。
必须避免仅在完成递归解析后检查深度。

### P1/P2：HTTP framing与API参数合同不完整

代码：[chat_server.cpp](../src/server/chat_server.cpp) 130–178行，
Content-Length使用全文子串搜索加无尾部检查的strtoul。
抽取原函数作socketpair测试，确认下列输入被接受：
`X-Content-Length: 2`被当作正文长度；`Content-Length: 2junk`；
两个相互冲突的Content-Length（2与99）。chunked头被接受但正文视为空。
这是后端解析缺陷，尚未证明经过Nginx可形成请求走私；两者不能混称。

HTTP接入应采用成熟解析实现或明确严格的受限合同，并覆盖重复长度、
TE/CL冲突、非法请求行和连接关闭行为。代理不能替代后端的输入正确性。

服务实际为greedy。未实现temperature/top_p/stop/response_format等
参数处理，不能把“接受请求”宣传为这些语义已支持。首版无需补全所有
OpenAI能力，但必须明确支持表、合法中性参数与非默认不支持值的拒绝策略。
静默忽略会让客户端误认为约束生效。

### P2：内存预算没有覆盖所有输入引发的分配

代码：[processor.cpp](../src/vision/processor.cpp) 304行先完整解压，
之后320行SmartResize才执行像素预算；视频也先解码再缩放。
压缩正文16MiB不等于解压后内存16MiB；大量媒体与主机缓冲不由GPU
启动预算自动覆盖。SmartResize还存在先int乘法再转换的尺寸计算。
这是代码级资源风险，本轮没有用大图片制造OOM，未声称实测OOM。

需要解压前尺寸/帧数/总像素检查、检查过的乘法及单请求/全局预算。
若首版只验收文本，可显式禁用媒体入口，把视觉验收作为独立发布范围。
`任何配置不OOM`没有证据支持，也不可能由单一启动预算推出。

### P2：测试退出码不等于所需检查确实执行

[tests/test_main.cpp](../tests/test_main.cpp) 中筛选匹配0项仍返回0；
[model_forward_test.cpp](../tests/model_forward_test.cpp) 等测试在没有CUDA
或模型/sidecar时打印skipped并返回true，框架把true计为PASS。
这不否定已经保存原始证据的Thor验收，但破坏“一条命令全绿即发布”的合同。
部分等价测试显式设置Q4T_GDN_REG=0，也不能直接替代默认路径验证。

需区分PASS/FAIL/SKIP、规定必跑清单及身份、缺少fixture/空筛选非零退出；
同时将构建、数值合同、HTTP质量与五档性能分别记录，避免混成一个绿灯。
本轮未执行全套q4t_tests，不报告全套通过或失败数。

### P2：文档与交付身份仍存在误导

根[README](../README.md)声称“任何配置不OOM”“76项全绿”“48层全量
OVERALL PASS”“无跨序列污染”，明显超过当前证据范围，还推荐bench
作为吞吐基准；[ARCHITECTURE](ARCHITECTURE.md)称JSON有界，代码并非如此。
[dataflow-engine/STATUS](../dataflow-engine/STATUS.md)仍有旧入口问题和
旧执行节点；主STATUS也混有历史“下一步”。

当前build/q4t已部署，但默认构建树静态库未同步（监听交付报告已注明）。
因此现有部署可追溯，并不等于默认增量构建就是同一候选。
仓库有本地构建/验证工具，但未发现已跟踪的.github发布流水线、
服务单元或容器发布文件；并不要求必须使用GitHub CI或容器，Thor上
可重现的统一发布命令和监督恢复合同即可满足相应需求。

## 性能与架构判断

复用当前正式参考，本轮未重测：

| 输入token | TTFT秒 | decode tok/s |
|---:|---:|---:|
| 1024 | 0.797 | 18.577 |
| 4096 | 2.627 | 17.885 |
| 8192 | 5.170 | 18.124 |
| 45056 | 30.451 | 17.860 |
| 204800 | 159.311 | 17.109 |

每档三次、输出256、单流、MTP关闭。TTFT包含接入与分词，不是纯prefill。
上一运行时对照decode均值低0.02%–0.36%，各档重复范围重叠；不能据此
宣称严格零回退。静态约10.24GB/token配260GB/s所得25.4tok/s只是理想
参照，当前没有足够流量/缓存/指令/串行时间账支持将差额全部归因于带宽。

现有数值kernel、PLE读取、状态和资源合同值得保留。服务文件2364行，
同时承担解析、请求管理、调度、视觉接入和响应收尾，增加了错误传播的
审计成本；本次发现的状态丢失正说明需要明确计算结果和请求终态接口。
可逐步演进为模型专用数据流执行引擎，无须为命名推倒重写。

   支持参数、必跑检查、配置/模型/二进制身份、安装与回滚、失败退出码
   形成一个可复现发布包；同步修正公开文档。
3. **受控业务试运行验收**：在明确请求长度/并发/队列/错误率和延迟
   目标后验证真实负载、持续运行和监督重启。若业务目标尚未确定，
   交付前两项并标注“受控试运行候选”，不能以此无限拖延明确缺陷修复。
4. **之后恢复性能和数据流演进**：以冻结候选为基线，先补实际时间/流量
   账，再选择模型形状驱动的执行计划改动。保持数值合同与五档性能；
   能降低复杂度且性能持平的改动仍可接受。
