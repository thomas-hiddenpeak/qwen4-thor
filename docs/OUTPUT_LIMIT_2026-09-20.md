# 普通生成输出上限收尾（2026-09-20）

状态：候选构建无警告；构建后的第一项测试为真实 HTTP limits E2E，
流式 1/2/8 输出与旧版一致。随后质量 11/11 通过，包括 44K/200K。
实际流式/非流式边界重采六条、性能 15/15 全部通过；未见可分辨的性能
回退；E2E 后的时间线确认 256 输出仅执行 255 次 decode 前向，本次改动接受。

## 改动

普通生成先把当前 token 计入 generated，并处理 EOS，再发出流式文本
（非流式则留待最终响应）。之后若已到输出上限，直接走现有退出收尾，
不再向 scheduler 注册下一步，也不再调用普通 fallback 的下一次前向。

实现将 step == max_tokens - 1 加入已有的长度退出条件，删除此前仅设置
finish_reason 却继续前向的分支。EOS 仍优先 stop；上限退出仍为 length。
请求移除、调度器唤醒、序列结束和 usage 统计沿用现有收尾路径。
MTP 有独立循环，本次没有修改。没有改变模型数学或已消费 token。

此前五档时间线均证明 256 输出触发 256 次普通 decode 前向，而首 token
来自 prefill，实际只需要 255 次后续前向。详见 HTTP_TIMELINE_2026-09-20.md。
本次预计只节省这一步；不以带 profiler 的耗时预测无采集时的具体增益。

## 验证顺序与首轮工具修正

1. 保存修改前二进制并用 evalscope HTTP 建立 limits 对照。
2. 候选必要构建完成后，直接运行 HTTP limits；无前置单测、bench/profile。
3. 固定质量题 11/11 精确正确，输入长度达标、正常 stop、与参考文本一致，
   服务退出 0。
4. 重采实际流式/非流式边界，再进行五档各三次的同输入性能比较。
5. 只有以上通过，才核对新的执行次数；控制流程改动不靠无关数值单测验收。

首版 limits 模式仅省略 --stream 以表示非流式，但 evalscope 默认 stream=true。
检查原始数据库后发现 limits-before/limits-after 实际全部是流式；这些结果
仅支持流式边界，不作为非流式覆盖。工具已显式传 --stream/--no-stream，
并保存和检查原始 request.stream。重采目录为 limits-control-verified
（旧版）和 limits-verified（候选），每组各六条；原始误标记录保留。

边界使用固定 1024-token prompt，流式/非流式分别 max_tokens=1/2/8，
核对实际输入输出计数、length、stream 字段与旧版逐字一致。它不是语义
质量基准；非流式的 TTFT 字段不用于 decode 速度计算。

本地证据：.q4t-work/e2e/output-limit-20260920/。构建、旧二进制、版本、
请求响应、数据库与退出状态保留；性能对照快照为 performance-before.json。

重采后，六条均与旧版逐字一致，实际 request.stream 分别为 true/false，
实际输出分别为 1/2/8，全部 length、服务退出 0。流式 max_tokens=1 的
单次观测中，首内容到请求完成的间隔由约 59.72 ms 缩至 0.02 ms；
这说明尾部等待减少，不将单次结果当作稳定性能结论。非流式 TTFT 等于
完整响应到达，不能对其差值套用 decode 吞吐公式。

## E2E 之后的执行次数核对

全部质量、边界和五档性能通过后，才用同一候选二进制采一条 1K 请求，
继续由 evalscope 发送并核对 256 输出与参考摘要。Nsight 正常退出并完成
SQLite 导出，分析核对 embedding、argmax 和结果 D2H：decode 前向为
255 次，旧版同请求为 256 次；MoE 专家 counts D2H 为 12240 次，恰为
255×48，旧版为 12288 次。证据位于 count-check/。

这证明 scheduler 普通路径少做了最后一次无消费者前向。没有用 profiler
计时宣布加速，没有运行无关数值单测、整套测试或 bench。fallback 共享
退出条件已静态核对，本轮未强制触发其运行；MTP、并发和多模态不属于
本次运行验收范围。固定语料结果不代替全面业务质量基准。

下一步可独立研究 200K prefill 的精确 top-k 合并，保持候选覆盖和精度；
不把该项与已闭合的输出上限修复混成一个改动。
