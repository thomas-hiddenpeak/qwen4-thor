# SRV-12d本机通知缺失与恢复短验冻结

本批是独立接收端可靠性验证，**零模型启动、零生成、零工具执行**。
已有真实模型通知恢复证据保留，但不作为本批新模型结论。
生产runner/网关/原通知代码不改；新接收器适配器/观察器先完成CPU。

## 执行边界

- 原GPU锁66305/3294067，同一外层`gpu_exclusive.py`/NVML覆盖所有
  HTTP组件与清理，最长420秒，业务窗360秒，保留60秒清理预算。
  正常不创建GPU上下文；竞争/观测失败仍ENV_ABORT，不干预外部服务。
- 固定官方Prometheus3.5.0/Alertmanager0.34.2，现有notify生成器和
  托管器不改，新私有包/状态；两角色各2次显式启动，共4次，无自动
  重启。真实规则心跳仍每分钟，接收端静默门限仍180秒，均不加速。
- 独立watchdog共2次显式启动，同state；自有TLS夹具1次，绑定loopback
  19446。Prom19097/AM19098，runner18128只作为未运行的合成监控目标，
  不假冒真实业务质量。其他告警由本机夹具保留并单列，不刷新心跳。
- 直接验证HTTP最多16次（计划3次拒绝/非心跳请求），回调尝试≤64。
  自动抓取每15秒/3目标，通知重发与自动回调分别记录，不能把显式
  驱动3次当作总网络流量。静默观察样本<1050，每0.2秒一次。
- 主驱动与子进程parent-death绑定；6个直接子进程退出后WNOWAIT保留
  身份到新guard扫描再回收。4个监控实际工作进程由既有manager清理；
  使用其原LISTENING/STOPPED/cleanup证据交叉核对，无未知PID清理。

## 验收序列

1. 真实Prom→AM→HTTPS→Bearer/合同/持久化接收得到PRESENT。
2. 未授权401、错误deployment422、合成非心跳202均不刷新ledger。
   202只代表测试夹具收存，不代表生产普通告警接收器已实现。
3. 停止自有Prom及AM，观察器继续运行；完整保留静默采样，真实
   最后到达+180秒至+183秒内判MISSING，下一周期投影也为MISSING。
4. 停独立观察器20秒，指标文件不再变化、时间戳超过15秒；外部
   规则的CPU官方时序证据复用，不声称此时已向正式人员发通知。
5. 显式重启观察器，仍MISSING且原投递时刻不变。再恢复AM/Prom，
   80秒内新的真实回调恢复PRESENT。无源采样新鲜度保证或重放保证。
6. 清理所有自有进程/监听，guard完成/原锁可用，GPU空；vLLM恢复
   服务仍masked，容器无新增；默认pair/新旧day计划不变且day未执行。

若失败保留原目录、原次数与预算；明确原因后只定向修复/重验，
不覆盖失败或自动扩长/加样本。退出仍核对底层guard与实际工作结果。
长时间运行归用户，实际跨主机接收/采集/通知渠道待配置和部署验证。
