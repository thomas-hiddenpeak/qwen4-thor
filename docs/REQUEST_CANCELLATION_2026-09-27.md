# 请求级取消合同与实现

本阶段从上游调研提出的请求生命周期机制出发，不复制分布式框架。
2026-09-27完成本轮有界验收并部署432fc489。模型目录/reference只读。

## 合同

- 请求在等待GPU槽位之前注册，取消状态跟随请求，不依赖它所在队列。
- 活动状态只能变成取消或完成；Cancel与Finish竞争只有一方获胜。
  重复取消不会重置状态、原因或重复释放资源。
- 自动ID在单进程内唯一，保留前缀chatcmpl-auto-；显式可取消请求
  提供request_id（1–128个字母/数字/下划线/连字符）及cancel_token
  （64个小写十六进制字符）。调用方应每次用安全随机数产生新token，
  即使重用request_id也不能重用token。ID重复且仍活动时409。
- POST /v1/requests/cancel，JSON为request_id和cancel_token。
  202只确认取消已接受，不保证GPU/资源已回收。未知请求、错误凭据、
  已经完成均404。输入格式错误400；接口不能取消没有凭据的自动ID。
  token是取消能力凭据，不能记录/泄露真实业务token；本地测试token
  仅绑定合成请求。该机制不替代服务入口认证、TLS或租户授权。
- 可选request_timeout_ms为1–86400000整数，从HandleChat接收请求起
  使用单调时钟计算；包括槽位排队，未包含此前接收HTTP请求体时间。
  省略则不设置该期限。截止在安全观察点生效，不强制抢占GPU/CPU算子。
- 完整请求体读取后，EOF/RDHUP代表HTTP请求生命周期结束。
  明确不再支持TCP写半关闭后等待生成结果；FIN和RST都触发取消。
  这是对此前RST补丁兼容合同的有意修改，不称为识别了TCP半关闭意图。
- 取消发生在SSE头之前返回409；流式响应开始后发送error事件并结束，
  不将部分结果包装为正常stop/length。期限取消沿用409/error合同，
  具体原因记录在服务日志。正常完成抢先成功时，后来的取消返回404。

最小调用示例（凭据通过安全随机源生成，不把真实凭据写进日志）：

```python
import secrets
request_id = "application-attempt-001"
cancel_token = secrets.token_hex(32)
# 与原有 model/messages/stream 等字段一起提交生成请求。
request_fields = {"request_id": request_id, "cancel_token": cancel_token,
                  "request_timeout_ms": 60000}
# 需要取消时 POST /v1/requests/cancel；必须路由至原请求所在进程。
cancel_body = {"request_id": request_id, "cancel_token": cancel_token}
```

## 所有权与执行边界

RequestRegistry只持有活动请求；请求线程的RAII登记对象负责移除。
取消接口检查ID+token，旧对象的延迟清理不能删除同ID的新对象。
不保留无限增长的完成历史；202不是release完成回执，404也不提供
历史状态查询。客户端可从原请求的结束获知此次处理已结束。

等待槽位每100ms检查EOF/截止时间，显式取消可唤醒等待。排队取消
不获取GPU槽位。预填充队列在收集请求时过滤取消；分块前和块完成后
检查同一状态。decode在循环边界检查，已经提交的step完成后才退出。
网络写失败也设置同一取消状态。计数只记一次aborted，不能再记成功。
GPU错误仍优先沿原不健康处理路径，不因取消伪装为设备恢复。

请求线程等待调度器交接结束后才移除调度记录、释放槽位；取消端点
不从其他线程直接释放GPU资源。完成与取消用原子状态仲裁后才发布
最终正常响应；这不保证最后一次网络写必定送达客户端。

关闭服务时先取消登记请求、shutdown全部仍受拥有权保护的连接，
唤醒阻塞读写；停止调度器，再等待活动请求线程数归零。删除此前
15秒后仍可能返回并释放模型的行为。不提供GPU硬挂时的进程内强杀
保证，外部监督进程的最终终止策略属于独立运维边界。
