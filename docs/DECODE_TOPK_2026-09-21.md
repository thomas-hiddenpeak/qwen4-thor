## 实现边界

原 OnePassScore 保持不变。固定 2048 候选窗口、top-512、T<=4、
组数超过 2048 且不超过 65536 时，调用独立 decode_topk.cu 的
SelectDecodeTopk，封装局部选择、多级窗口归并与最终 token 扩展。
其他窗口/预算保留原路径。没有改变 FP32 分数、可见历史或块预算。

三个阶段采用同一个严格比较网络，k/j 次序与同分 ID 的设计目标不变。
线程内比较放在寄存器，warp 内用 shuffle，跨 warp 保留 shared 与
barrier；最终扩展保持槽顺序、invalid sentinel 和不完整组尾 token。
完整 E2E 后精确专项已核对，生成文本一致本身不替代数值检查。

bitonic_topk.cuh 是私有公共模板，streaming_topk.cu 也改为包含它，
避免维护两套寄存器网络。因此 prefill 仍需完整性能验收，并在门禁
之后运行原 streaming_topk_exact，而不是假设模板移动不会影响产物。

## 既有容量与执行依赖

调用者继续拥有所有 scratch，host 只提交各级 kernel，无新分配、
回读或跨 stream 协议。每级 kernel 边界保证下一阶段读取前写入完成。

每 token 候选容量 ceil(groups/2048)*512<=16384；每项一个 FP32
分数和 int32 ID，两套 ping-pong 合计 256 KiB/token，T=4 为 1 MiB。
分数输入至多 groups*T*4 字节，T=4 为 1 MiB，均为既有分配。
排序窗口的 shared 数组仍为 2048*(4+4)=16384 字节。完整 E2E 后
cuobjdump 记录三级旧/新寄存器分别为 Slice 26→40、Window 31→40、
Final 40→45；三者 SHARED 均为 17408 字节，STACK/LOCAL 均为 0。
这是编译工具口径，不与源码数组容量混算。streaming merge 的
REG=48、SHARED=25600、STACK/LOCAL=0 未变。局部耗时见下方时间线。
