# SRV-12c通知与真实恢复的冻结短验

在任何HTTP/模型启动前，将首版开发合同的1启动/3生成细化为本文件的
**2模型启动/4成功生成**，用于直接证明真实停服及恢复通知，避免仅用
合成resolved payload代替后端恢复。首版CPU16项仍按原来源保留；
生产实现、17条既有规则及CPU输入合同不改。本文件是实际执行预算。

- 整个阶段由外层gpu_exclusive持同一锁，直接运行已接受v3包的原ELF/
  固定参数，两次显式启动间不释放锁。无需另取锁或复制描述符，不
  改生产controller。模型普通1次+真实资料工具/引用2次，停止；真实
  TargetDown经原1分钟for触发，再显式恢复模型普通1次并收到resolved。
- Prometheus1启动，Alertmanager2显式启动，共3监控代次；同一私有
  状态跨AM正常停止/重启，验证已确认的合成probe重发在20秒内不重复
  送达。只证明该窗口，不冒称4小时或宕机零丢失。
- 自有HTTPS接收器1个，最多64回调；首次心跳及首次TargetDown各返回
  503，其后204，验证标准发送重试与接收确认。合成probe首次307，
  不允许跟随到/redirected；接收器恢复后发送成功，再发resolved。
  合成probe只验证通知路径，与真实模型告警分别标记。
- API控制最多256次，生成4次，接收64次；监控采样15秒，抓取最多
  3×(ceil(360/15)+2)=78，规则计算不改原15秒/for。Prometheus向AM
  的发送由固定规则/15秒resend和队列100控制，不伪报精确HTTP次数；
  保留发送/失败计数及所有接收回调。不让通知重试触发模型或工具重放。
- GPU/HTTP租约360秒，驱动主业务300秒、留60秒清理，总420秒；没有
  自动补样或延长限额。必要cleanup不受业务计数耗尽阻断，只处理
  本阶段PID/start/boot及其组；异常保存FAILED或ENV_ABORT原件。
- 最终所有HTTP/GPU进程与监听退场、GPU空、原锁释放；单组件终态与
  guard均核对。默认pair及day来源保持，不装常驻unit或向外部发消息。

验收还包括实际LISTENING后的ready HTTP、同包锁继承、私有配置身份、
业务无误报、通知失败metrics存在、原始payload关联/去重/恢复与
真实工具读文档及引用。不把同机fixture接收等同生产渠道/人员处理；
TLS生产CA、心跳接收方超时检测、跨代次磁盘保留和实际部署独立待办。
