## 已确认的 4K 证据

固定原基线的第一条 4096-token 请求，输出 256 token，单流 greedy。
服务 max_seq=1、max_prefill=8192、max_len=208896，禁止实验 FP8 开关。
两次启动，各连续发送三次相同请求：

| 实现 | 同进程重复 | 两次启动合计 |
|---|---|---|
| 与原基线 SHA 相同的旧二进制 | 每组三次均不同 | 六种不同输出 |
| 固定 TopkSelectKernel 的展开位置 | 每组三次相同 | 六次输出全部相同 |

旧二进制 SHA-256：
16a67b3615db8e2f7635e18f1da82aa49b8bf1c42e01ddc7dd890d0e8496a687。
固定短路径后输出 SHA-256：
7379b9adbe70dc9c26a26ad81885c5801398095948d253442e46305126581708。

已核对数据库中实际发送的十二份请求 JSON，SHA 全部相同；不是数据准备
或请求顺序造成的输入变化。服务普通 decode 调用 ArgmaxBf16Rows，没有
随机采样。证据 short-comparison.json。

原断连补丁的五档 E2E 已证明仅修传输层仍有输出变化；本次固定索引顺序
使同进程和跨重启的该组 4K 请求恢复确定性。无需重启即可复现旧问题，
因此不能把它仅描述为跨进程差异。

## 代码机制

src/model/full_attention.cu 原三条 top-k 展开路径均通过
out[atomicAdd(&s_n, 1)] 写入选中的 token。原子操作保证槽位唯一，
但不保证不同线程取得槽位的先后顺序。

SparseAttentionKernel 每 16 个选中 token 做在线 softmax，并把局部
概率转成 BF16 参与 PV，累积量还会随新的最大值缩放。列表顺序改变会同时
改变分组、舍入和累积顺序。因此“所选集合相同，所以顺序无关”的旧注释
只适用于理想实数运算，不能作为当前浮点实现的正确性依据。

短路径当完整压缩块数超过 512 时进入稀疏分支；compress=4 时，首个
稀疏 query 的位置是 2051（从零计）。1K 输入加 256 输出不触发该分支，
与旧记录中 1K 稳定、4K 及以上不稳定的现象吻合。

这里已定位的是实现引入的非确定性。尚未逐层测量它如何影响最终路由或
首个不同 token，不能把所有差异泛化为量化噪声，也不能宣称排除了其他
输入、并发或配置下的非确定性。

## 修复范围与不变量

- TopkSelectKernel：按排序后的块名次展开，块内按 token 位置写固定槽位。
- ExpandRunTopkKernel：保留有序结果中的有效后缀，跳过空槽前缀后固定展开。
- FinalTopkExpandKernel：长 decode 最终归并结果用同样方式固定展开。
- 当前组未被选中时，其可见尾部固定追加；尾部空槽仍填 -1。

排序、打分、top-k 预算、KV 内容和数据类型未改变。选中块来自完整可见
压缩块，块内展开均满足因果边界；单独补入的当前组仍检查 p <= pos。
每个有效 token 拥有唯一可计算的槽位，不再用原子计数决定顺序。

新输出不必与旧版某一次随机展开顺序的输出逐字一致；但确定性恢复本身
也不能证明模型精度维持。完整接受仍需精度证据与同口径性能回归。

对后续数据流引擎的约束：执行计划不能只规定读哪些数据，还应明确有序
索引、归约分组、数据类型和舍入位置。线程调度不应隐式决定模型的数值路径。

## 扩展验证

三条展开路径修复后，第一项测试是五档 E2E：每档使用原基线第一条输入，
原样重复三次，输出上限 256。这是确定性实验，与原基线每档三条不同输入
的性能矩阵不等价。五档各三次完整输出全部一致，15/15 请求成功，实际输入长度及 256-token
输出全部达标，均正常以 length 结束。服务正常退出 0。
1K 输出与原基线第一条完全相同；4K 与前述两次重启的结果相同。
8K 的生成跨过短/长路径边界，44K/200K 覆盖多块 prefill 和长 decode。

| 输入 token | 相同输入完整输出一致 | 平均 TTFT（秒） | decode（tok/s） |
|---:|---:|---:|---:|
| 1024 | 3/3 | 0.876 | 15.55 |
| 4096 | 3/3 | 3.244 | 14.05 |
| 8192 | 3/3 | 6.524 | 14.54 |
| 45056 | 3/3 | 39.859 | 14.23 |
| 204800 | 3/3 | 235.587 | 13.72 |

TTFT 为客户端首 token 延迟，不是纯 prefill；decode 以总生成间隔时间
加权，即 sum(output−1)/sum(latency−TTFT)。1K 首请求包含冷启动效应，
原始逐请求计时保存在 results.json。

这些结果只支持本轮配置和负载下的确定性恢复。不能与旧版三个不同输入
的均值直接比较来宣称无回退；生成内容变化也会改变后续计算路径。完整
精度验证及相同负载、重复波动下的性能对照仍未闭合。未运行低层测试或
性能 profile。构建无警告，末尾仅更正了不影响可执行代码的注释。
