# 数据流优化：当前预算与决策边界

评估和开发顺序以 [EVALUATION.md](EVALUATION.md) 为准：改动后第一项测试是
真实 HTTP evalscope E2E，通过后才做细分析。五档初始 E2E 测量见 [BASELINE_2026-09-20.md](BASELINE_2026-09-20.md)，
固定原生模板质量题和重复性能矩阵已建立，最新已接受阶段见
[STATUS.md](STATUS.md)。这些固定题的通过不等于全面模型质量验证。

## 目标与约束

现有 runner 是模型专用数据流引擎的演进基础。优化对象是完整请求和状态转换，
同时关注权重、激活、持久状态、host 调度、GPU 执行与 PLE SSD IO。
保持当前精度，五档性能不回退；复杂度降低且性能持平也可接受。
默认普通 decode，MTP 单列；FP8/其他量化不能混入同精度基线。

## 单序列普通 decode 静态预算

2026-09-20 从 checkpoint 张量头与默认源码路径核算；GB 使用十进制。
前提：B=1、每步 1 token、MTP 关闭、FP8 实验路径关闭，所需权重读一次。
checkpoint 是混合格式：路由专家 NVFP4，主干和 lm_head 默认主要是 BF16。

| 权重部分 | 每步读取约值 GB |
|---|---:|
| 36 层 GDN 投影 | 4.170 |
| 12 层完整注意力及 indexer 投影 | 1.235 |
| HyperConnection，含最后 mixer | 1.279 |
| 共享专家及 router | 0.598 |
| PLE 投影 | 0.066 |
| top-10 路由专家，含每 16 权重一个 FP8 scale | 1.327 |
| lm_head | 1.271 |
| norm、卷积权重等 | 0.005 |
| 合计 | 9.951 |

A6B 主干约 3.676B BF16 参数 + 2.359B NVFP4 活跃专家；另外输出头约
0.636B BF16 参数。输入 embedding 只查一行，输出头读整个矩阵。
NVFP4 权重和块 scale 共约 0.5625 byte/参数，不能按全模型 0.5 byte 算。
PLE 51.2 GB 查表文件不逐步全读，随机 IO 延迟需另行考虑。

在 8K 上下文，另有 GDN FP32 状态读写约 0.2265 GB、卷积历史约 0.0048 GB、
QSA 选中 KV 约 0.0503 GB、压缩 index key 扫描约 0.0063 GB。
必要流量约 10.24 GB/token。index 扫描约为 768×上下文长度 byte，长上下文
仍增长，但不能据此解释 4K 后吞吐突然减半；需确认请求实际执行模式。

- 273 GB/s 标称预算：约 26.7 tok/s，37.5 ms/token。
- 260 GB/s 校准预算：约 25.4 tok/s，39.4 ms/token。
- 使用 260 GB/s 的前提是 kernel 测量代表可持续 DRAM 带宽，未混入缓存命中。

以上是静态必要流量，不含全部临时激活、重复读取和访问放大，也不是 DRAM
计数器实测。缓存复用、计算与同步会影响实际结果。不能从个别 kernel 接近
峰值推出整个 decode 已到极限。MTP/批处理改变每输出 token 的权重摊销，
不适用这个逐 token 上限。

## 下一步决策依据

1. 已有固定原生模板质量题、输出摘要和五档各三次基线；真实业务语料、
   多轮及并发质量仍需独立覆盖，不能把固定矩阵当作全面精度结论。
2. 已接受 HTTP 时间线可用于选择下个候选；新改动仍先过 HTTP E2E，
   再做其专项与 profile。decode 投影要按形状拆分，不能只看 GEMV 总占比。
3. 以真实请求的收益和复杂度决定改动顺序。MoE 合并分配已接受，线性
   六区合并因 TTFT 信号撤回；调用次数或纸面字节减少都不是收益证明。
4. HC 四输出投影专用实现已接受，整体稳定增益尚未确立，依据与验收状态见
   [形状分析](HC_INJECT_GEMV_2026-09-21.md)。其中逻辑权重字节/时间
   不等于 DRAM 硬件计数，局部 kernel 累计时间也不等于整请求墙钟。
