## C=512/C=256 非逐位根因：staging 缓冲复用竞态，分块 stage+commit 修复（2026-09-30 晚）

bitexact-c256 复验（19:32 二进制）仍 BIT-EXACT=False（1024/8192，首字符
即分歧）；二分 C=512+hot-512-full（全专家预载、零按需补载）同样 char 0
分歧，8192 候选输出退化为常量重复（100000000000000000000000000000000000
00000000000000000000000000000），而 det-c0 双跑逐位一致（C=0 自身确定
性成立）。bytecmp/slotmap（新增，层0、512 专家、全常驻 vs 驻留布局逐
字节）：512 槽数据均为真实专家数据（无损坏），但 504/512 槽含错误专家
——slot→expert 簿记与实际槽内容失步。根因：LoadPhase1 的 8 个 worker
各自把同一 plan 的多个专家依次 stage 进自己的单个 pinned 缓冲（覆盖前
一专家数据），全部 stage 完才 LoadPhase2 commit；commit 时缓冲里是该
worker 最后 stage 的专家，每个槽实际含至多 8 个专家之一，而 forward 按
簿记取"正确"专家 → 错误权重 → 退化输出。修复（GEMM 未动）：Phase1/
Phase2 改分块语义——Phase1 每次至多 stage 一个 chunk（≤load_threads_
条，entry off+t → worker t → buffer t，每缓冲至多一个专家）；Phase2
commit 已 stage 的 chunk；调用方（Resolve/InitHot/prefill 循环）按块交
错；prefill stage-ahead 重叠保留（sub-chunk j+1 的块在 GEMM j 期间
stage+commit，其 H2D 在 GEMM j 之后 stream-ordered，槽位驱逐安全依赖
stream 顺序）。验证：bytecmp2（512/512 专家逐字节一致，bad_regions=0）；
q4t_tests 104 项全过（含 residency_load_matches_reference、
moe_forward_residency_bitexact）；c512full BIT-EXACT=True（1024/8192，
loads=24576 misses=0 evictions=0）；bitexact-c256 BIT-EXACT=True
（1024/8192，misses 20833/80807、evictions 活跃）。20:24 二进制
（md5 be1c54c5）为新口径。下一步：同一 20:24 二进制重跑全矩阵（基线
C=0 + 候选 C=256+hot-256，六档×3）→ 冻结口径对比。

## 分块簿记漏计跨 chunk 共享专家：C=256 容量失败根因与修复（2026-09-30 晚）

bitexact-c256 复验（19:26 二进制，含 PlanResolve 去重）1024 档仍 500
"no residency slot available"。新增诊断日志定位：去重已生效（层2
distinct=257 而非 n=2970 的重复计数），但分块器 flush 行 book=256
actual=257——MoEForward 分块在 flush 后只把"对旧 chunk 新鲜"的专家
计入新 chunk，与前一 chunk 共享的专家未重新计入 in_set/distinct，
chunk 真实 distinct 可超过 D，PlanResolve 按真实 top-k 规划时容量
耗尽。修复（仅 moe.cu 分块器，GEMM 未动）：flush 后对空 in_set 重新
探测 fresh，保证 book==真实 distinct 且 ≤D；不变式检查从层0/in_set
口径改为全层、按 ids_h 重算 chunk 真实 distinct，同时校验与 book
一致及 ≤D（原检查比较 in_set 计数，恰好漏掉本缺陷）。零警告重建
（19:32，md5 见 build/q4t）。复验：8144 诊断服务 C=256+hot-256
1024 档 finish=length in=1024 out=256（wall 42.6s 含冷加载）；全部
flush book==actual、max actual=256=C、INVARIANT BROKEN=0。原因：
分块容量保证必须按 chunk 真实 distinct 集合成立，跨 chunk 共享专家
是排序聚类的必然产物。下一步：bitexact-c256 正式复验（C=0 vs C=256，
1024/8192 逐位）→ 同一 19:32 二进制重跑基线+候选全矩阵。
## 候选 500 根因：补载去重修复未编译入 19:03 二进制，重建后复验（2026-09-30 晚）

bitexact-c256 复验（19:00，18:55 构建）候选首请求 HTTP 500：
"no residency slot available (needed set exceeds dynamic capacity)"。
根因：PlanResolve 对同一 needed 列表中重复出现的专家（每 token
top-k 一条）不去重，每个重复都按 miss 预留一个槽位，子块内
非驻留条目数远超 C=256，容量耗尽。修复：PlanResolve 增加调用内
去重表 planned[e]（首次 miss 预留槽位，同专家后续条目直接命中
该槽）。另发现 19:03 重建只重新编译了 chat_scheduler.cpp
（调度失败日志），moe_residency.cpp 的去重修复未入二进制
（.o 仍为 18:55），19:03:48 启动的 8141 诊断服务因此仍 500。
