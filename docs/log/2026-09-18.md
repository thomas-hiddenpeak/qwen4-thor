## 2026-09-18 — decode 性能: FP8 W8A16 投影 (单流 decode 1.31×)

**背景**: 用户"参考 vllm 一次性完成工业化剩余 + 开始 decode 性能优化, 暂不碰 MTP,
API E2E 测试, 分析权重流量+kernel 开销, 目标单流 decode 达 273 GB/s 上限 (之前连
240 都没到)"。

**profile (先测后投)**: nsys decode 80-tok:
- `Bf16GevKernel` (M=1 BF16 投影 GEMV) = **61.6%** (3.09s/5.0s), 55120 calls,
  max 7.4ms (=lm_head 读 1.27GB/步)。
- **GPU 满载** (kernel busy 5.0s ≈ wall 5.02s) → **非 launch-bound**
  (cudaLaunchKernel 1.6%, 与 GPU 重叠隐藏) → **CUDA Graph 无用**。
- proto (fp8_gemv_proto.cu) 复测: **BF16 GEMV 大投影已 244-252 GB/s** (近 273
  spec/超 241 copy)。**认知修正: 273 GB/s 非"提高 GB/s"而是 FP8 减字节** —
  W8A16 (e4m3 权重 1B + per-channel scale, BF16 激活) 减半权重流量 → 大投影 2×。

**做了什么 (FP8 W8A16, 即既定"计划 C", 双存零风险)**
- **gemv.cu/.h**: `Fp8GevKernel` (16 e4m3/iter via uint4 + 行 scale, BF16 激活) +
  `QuantizeFp8RowKernel` (per-output-row absmax/448) + `Fp8Shadow` +
  `BuildFp8Shadow` + `Fp8ProjEnabled` (`Q4T_FP8_PROJ` gate)。
- **linear.h `ProjGemm`**: M=1 有 shadow → Fp8Gev, 否则严格 = Bf16Gemm。
- **接入**: attn q/k/v/o + GDN in_proj_qkv/z/out_proj + lm_head + MoE
  shared_gu/down。保 BF16: attn index_qk (合并行偏移) / GDN a/b (N=48 微+递归敏感)
  / router gate (top-k 精确) / HC 低秩+小 k/v (latency-bound, 转了收益微)。
- **双存**: BF16 权重不动 → prefill/M>1 (cuBLASLt) bit-identical 零风险;
  FP8 shadow 纯附加, 仅 M=1 decode GEMV 用, 默认 gated off。

**结果 (Q4T_FP8_PROJ=1)**:
- **decode 17.9 → 23.4 tok/s (1.31×)** (attn+GDN 1.22× → +lm_head+MoE-shared 1.31×)。
- **质量**: greedy 输出对事实 prompt (前 10 质数) 与 BF16 **逐字一致** —
  lm_head FP8 未扰动 confident token 的 argmax。
- **serve API E2E** (FP8): 3 请求全连贯, gpu_healthy 1, 无 error, 稳态 ~22.7 tok/s。
- 71 测试无回归 (FP8 off), 零警告。prefill 不变 (147→151 tok/s)。

**默认**: `Q4T_FP8_PROJ` 默认 OFF (opt-in), 保 BF16 精确路径为默认 (测试+
tools/verify 参考对比不受 FP8 噪声影响)。翻默认 ON 待更广质量验证后由用户定夺。

**FP8 后新分解** (nsys, attn+GDN FP8 阶段): Bf16Gev 61.6%→31.3% / Fp8Gev 21.4% /
MoE FP4 18.4% / SwiGLU+GatherQuant 11.2% / GDN reg 6.2%。下一杠杆 (未做): MoE
quant kernel 融合 (SwiGLUQuant+GatherQuant 11.2%)。

## 2026-09-18 — PLE page_reader io_uring exact-recovery (从 ds4 借鉴)

**背景 (用户加的 ds4/tokenspeed 参考对标)**
PLE SSD Stream 对标 ds4 (DwarfStar, 同模型 Qwen4 + 同硬件类 DGX Spark) 与
tokenspeed (datacenter, n-gram 全驻 HBM, 无 SSD stream)。**结论: 我们 PLE 核心
机制领先/对齐** —— io_uring registered pool (QD256) + page 级 dedup (4 KiB) +
sglang-ssd-stream 权威参考; ds4 用 pread (+macOS 并发线程), tokenspeed 无 SSD
stream。唯一实质借鉴 = ds4 磁盘读失败 exact-recovery (我们此前 fail-closed)。

**做了什么**
page_reader 从 fail-closed (任何 cqe->res<0 → 永久 broken, 一次瞬时 NVMe 抖动即
杀死整个进程生命周期的 reader) 升级为 exact-recovery: 每 wave 跟踪 per-page 已读
字节, 对短读 (res<valid) 或瞬时错误 (EAGAIN/EINTR/EBUSY/ECANCELED) 从未完成 offset
重提交, 上限 kMaxReadRetries=8 轮; 持久 errno + 意外 EOF 仍 fail-closed (绝不
scatter 脏页字节)。正常路径 (首次读满有效长度) 退化为原单次 submit+reap →
成功读逐位一致。

**验证**: env-gated 故障注入 (Q4T_PLE_FAULT_INJECT) + 新测试
ple_page_reader_fault_recovery (8 注入短读跨 12 页 → 重试补齐 → 数据正确 + reader
仍可用)。正常路径 ple_e2e_gather l2_rel 0.000e+00 + working memory 75.17 MiB 不变。
71 测试全绿。对齐 ds4 的 test_qwen4_ngram_state (failed disk reads → exact recovery)。
