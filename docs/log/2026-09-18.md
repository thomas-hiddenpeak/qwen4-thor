## 2026-09-18 — serve/scheduler 工业级能力审计 + 加固 (DoS/健壮性)

**背景 (用户)**
"对 API 服务调度部分进行工业级的能力审计"。系统通读 chat_server.cpp (1651 行) +
HTTP 层 + 调度器。

**审计结论: 已具备的工业能力 (保留)**
- HTTP: header guard 1 MB + body guard 16 MB + malformed 检测 + base64 图片
  (无网络获取, 安全)。
- 背压: conn_cap (max_seq*8, 超限 503 shed load) + AllocSeqId 排队 (阻塞非拒绝,
  有界 max_seq, 绝不 OOM) + 共享 prefill buffer (防 per-req ~1 GB d_logits OOM)。
- 并发: model_mu_ 序列化 forward + seq_id 池隔离 + tok_mu_ (ICU 非线程安全串行) +
  lockstep 调度 (无饥饿批处理) + MTP 分支。
- 关闭: scheduler drain + seq_stopping 唤醒等待者。SO_REUSEADDR。

**发现的缺口 + 已修**
| 缺口 | 严重 | 修复 |
|---|---|---|
| 无 socket 读写超时 (slowloris: 慢客户端永久占线程+slot) | P1 | SO_RCVTIMEO/SO_SNDTIMEO 30 s (accepted fd) |
| max_tokens 无上界 (huge 值长期占 slot + host buffer 增长) | P1 | cap 到 max_len (999999→249 实测) |
| 无客户端断开检测 (断开后仍生成, 浪费 GPU + 占 slot 到 max_tokens) | P2 | stream WriteAll 返回检查 → 断开即停 |
| listen backlog 16 偏小 | P3 | → 128 |

**剩余建议 (未修, 供决策 — 更侵入/策略性)**
- P2 信号处理/优雅关闭: main.cpp RunServe 无 SIGINT/SIGTERM 处理, Ctrl-C 直接
  kill 无排空 (析构不触发因 Run() 阻塞)。需 signal handler → 停 accept + drain
  in-flight + StopScheduler。
- P2 CUDA sticky error 无恢复: 一个 forward 的 cudaError 是 sticky, 会污染所有
  后续 forward, 服务永久损坏且无自愈 (类似 PLE broken 但波及整卡)。需检测 +
  healthz 反映不健康 / 主动退出让 orchestrator 重启。
- P3 可观测性: 无 metrics endpoint (吞吐/延迟/队列深度/错误率); healthz 是浅检查
  (仅 "ok", 不反映 scheduler/GPU 健康); 无 HTTP keep-alive (Connection: close)。

**验证**: 71 测试全绿; serve normal max_tokens=12→completion=12 连贯; huge
max_tokens=999999→completion=249 (cap 生效); 编译零警告。

## 2026-09-18 — PLE page_reader io_uring exact-recovery (从 ds4 借鉴)

**背景 (用户加的 ds4/tokenspeed 参考对标)**
PLE SSD Stream 对标 ds4 (DwarfStar, 同模型 Qwen4 + 同硬件类 DGX Spark) 与
tokenspeed (datacenter, n-gram 全驻 HBM, 无 SSD stream)。**结论: 我们 PLE 核心
机制领先/对齐** —— io_uring registered pool (QD256) + page 级 dedup (4 KiB) +
sglang-ssd-stream 权威参考; ds4 用 pread (+macOS 并发线程), tokenspeed 无 SSD
stream。唯一实质借鉴 = ds4 磁盘读失败 exact-recovery (我们此前 fail-closed)。

**做了什么**
page_reader 从 fail-closed (任何 cqe->res<0 → 永久 broken, 一次瞬时 NVMe 抖动即
杀死整个进程生命周期的 reader) 升级为 exact-recovery: 每 wave 跟踪 per-page 已读
字节, 对短读 (res<valid) 或瞬时错误 (EAGAIN/EINTR/EBUSY/ECANCELED) 从未完成 offset
重提交, 上限 kMaxReadRetries=8 轮; 持久 errno + 意外 EOF 仍 fail-closed (绝不
scatter 脏页字节)。正常路径 (首次读满有效长度) 退化为原单次 submit+reap →
成功读逐位一致。

**验证**: env-gated 故障注入 (Q4T_PLE_FAULT_INJECT) + 新测试
ple_page_reader_fault_recovery (8 注入短读跨 12 页 → 重试补齐 → 数据正确 + reader
仍可用)。正常路径 ple_e2e_gather l2_rel 0.000e+00 + working memory 75.17 MiB 不变。
71 测试全绿。对齐 ds4 的 test_qwen4_ngram_state (failed disk reads → exact recovery)。
