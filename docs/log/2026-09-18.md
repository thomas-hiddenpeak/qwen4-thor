## 2026-09-19 — decode argmax 两段式并行 + 关键发现: plain decode 不随上下文变慢

**背景**: 继续推 44K decode (17.7 tok/s, 目标 18+)。单步 nsys 里
ArgmaxBf16Kernel 523us (248320 vocab 单块 256 线程扫描, 只用 1/20 SM,
latency-bound, 带宽极限 ~2us 的 260×)。

**做了什么** (src/model/model_head.cu): 两段式 argmax — Stage 1
(ArgmaxBf16ChunkKernel, grid=(970,B)) 每块扫 vocab 的 1/970 连续切片,
块内 shared reduce 出局部 (max, lowest-index) → partial [B,970]; Stage 2
(ArgmaxBf16ReduceKernel, grid=B) reduce 970 个 partial。lowest-index
tie-break 保持 (chunk c 覆盖 [c*per,(c+1)*per), 等值最低索引必在最早
chunk, 两级都向低索引 tie-break)。persistent partial buffer (static,
按需增长)。~523us → ~20us。

**关键发现** (4K plain vs 44K plain 单步 nsys 对比): **plain decode 单步
时间几乎相同 (4K 57ms ≈ 44K 56.6ms)** — Fp8Gev 17.9/17.7, Bf16Gev
8.2/7.8, SparseAttention 6.5/6.7, nvjet 10.0/10.0, indexer 5.2/3.8。
**用户的架构直觉正确: plain decode 不随上下文变慢** (36/48 线性层 O(1) +
QSA 稀疏 O(1) + indexer 已 one-pass 并行)。实测 4K=30 vs 44K=17.7 的差距
**纯粹是 MTP gate**: 4K < max_prefill(8192) 不 chunked → 走 MTP 投机解码;
44K > 8192 → chunked → MTP 被禁用 (draft-extend 需全 prompt trunk, 按
262K 最坏 5.3GB+26GB 算超 headroom; 但 44K 实际只要 ~1GB, 远小于 22GB
headroom — gate 对中长上下文过于保守)。

**验证**: 76 测试全绿零警告。44K 17.7 (argmax 0.5ms 收益在噪声内), 4K
30 无回归 (MTP 路径, argmax 也用于 MTP verify)。

**下一步**: 实现 chunked MTP (chunked prefill 期间累积全 prompt trunk →
prefill 后跑 MtpDraftExtend), 让 44K 也吃到 MTP 投机解码 (主模型验证,
精度安全), 预期 17.7 → 35+ tok/s。



## 2026-09-19 — 长上下文 decode 性能: one-pass 全块打分 + 多级并行 top-k (44K decode 14.4→17.7 tok/s)

**背景**: 块并行 indexer (0ae1304) 后 44K decode 14.4 tok/s, 用户要求推回
18+ 且不改精度 (全块打分召回必须保留)。干净单步 nsys 显示剩余长上下文退化
项: MergeChunkTopk 13.6% (6 chunk × 12 层 × 132us 流式 merge) +
IndexerLogitsBlockPar 10.6% (grid 仅 8 块, 只用 8/20 SM)。

**关键洞察**: 流式 top-k 是为 prefill (T=8192, [T,n_groups] 太大) 设计的。
decode T≤4 时 [T,n_groups] 才 ~180KB (44K token), **根本不需要流式** —
一次打完所有块 + 多级并行 top-k 即可。

**做了什么** (src/model/full_attention.cu, 4 新 kernel):
- `OnePassScoreKernel`: 单趟给全部 n_groups 块打分, warp-per-block
  (coalesced 读 idx_comp), grid=ceil(n_groups/8) 铺满 20 SM。替代 6 次
  chunk 打分 (原 kernel 每线程读 1 块 128 维, 32 路 cache-line 分散)。
- 多级并行 top-k (替代单块串行流式 merge): `SliceLocalTopkKernel` (2048
  窗口局部 top-512, 多块并行) → `WindowMergeTopkKernel` (逐级 1024→512
  收敛, 每级多块并行) → `FinalTopkExpandKernel` (最终 2048 排序 + 展开 +
  当前 group 尾部)。数学保证: 全局 top-512 ⊆ 各窗口 top-512 的并 (反证:
  若某全局 top-512 块 x 不在其窗口 top-512, 该窗口有 512 块比 x 大, 加上
  其他窗口的 511 个全局 top 块, 共 1033 块比 x 大, 矛盾)。
- 分支: T≤4 且 n_groups>kMaxBlocks 走 one-pass; 短上下文 (≤8192 token)
  走原 single-shot 不变; prefill (T>4) 走原流式 GEMM 路径不变。
- workspace 加 d_op_logits [T,n_groups_max≤kMaxGroups=32768] f32 +
  d_cand 两级 [T,2048] (val f32 + idx i32)。

**验证** (先测后投): 临时自检 (env 开关, 测完删) host 暴力全部块 top-512
vs one-pass 多级归约 → id_diff=0 (n_groups=10966, 多 chunk 路径)。76 测试
全绿零警告。4K 无回归 (30-34 tok/s, 走原 single-shot 路径)。

**结果** (FP8, B=1, 精确 tokenizer 44000 token prompt):
- 44K decode 14.4 → **17.7 tok/s** (1.23×, 全块召回不变)
- 单步 nsys: indexer 总开销 24% → 7% (OnePassScore 1.3% + top-k 5.5%);
  瓶颈转移到 Fp8Gev 31.2% (权重带宽地板, 短上下文也有, 非退化项)
- 4K: 30-34 tok/s 无回归

**运维事故**: 测试期间机器重启 — 两个模型实例 (q4t serve 37.6GB +
q4t_tests 27.7GB) 并发加载超 122GB 统一内存 → 全局 OOM。规则: 同一时刻
只允许一个模型实例 (已记 repo memory)。

**下一步候选**: 17.7 距 18 差 0.3; 剩余退化项已很小 (indexer 7%), 大头是
Fp8Gev 权重带宽 (方向: FP8 计划 C 的 GEMV 优化, 短/长上下文都受益)。



## 2026-09-18 — 长上下文 decode 性能: 块并行 QSA indexer (30K decode 9.2→14.4 tok/s)

**背景**: 用户要求"性能优化必须推进, 理论上不应随上下文变慢"。验证注意力在
262144 最大上下文正确 (needle @240K 召回, 4K/30K 输出确定) 后, 测得 decode
随上下文退化: 4K=25.4 / 30K=9.2 tok/s。根因定位: 36/48 线性层 O(1) 不随
上下文变, 12 层 QSA 注意力 O(1) (只 attend top-512 块), **唯一 O(上下文)
的是 QSA indexer 打分** — 必须给全部 ~n_groups 块打分才能选 top-512 (这是
设计使然, 参考 vllm/sglang/tokenspeed 都全块打分)。

**瓶颈**: 流式 top-k 用 token 并行 `IndexerLogitsKernel` (grid=T)。decode
T=1 时只有**单个 256 线程块**给 2048 块打分, 19/20 SM 闲置。30K 实测
704us/chunk × 15 chunk × 12 层 ≈ 127ms/步, 把 decode 拖到 9.2 tok/s。

**做了什么** (src/model/full_attention.cu, 镜像 vllm decode QSA indexer):
新增 `IndexerLogitsBlockParKernel` — grid 按块 tile (8×T), 每线程打一个块
(全部 n_iq 头), 2048 块用 2048 线程铺满所有 SM。小 T (≤4, decode/MTP
verify) 用它, 有无 d_seq_id 都支持 (T≤4 时 d_seq_id[t] 每 token 固定, 每块
选一次 per-seq idx_comp 切片)。大 T (prefill) 保留 tensor-core GEMM 路径。
顺带修了初版 block-parallel 的索引 bug (因果掩码把局部 chunk 索引和全局
可见数比较, 写到 g-block_off 负索引/OOB) → 现读 cks[local]、掩码
global_g=block_off+local<n_groups、写局部列, 与已验证的 token 并行路径
bit-identical。

**验证** (先测后投): 多 chunk decode 路径 host 暴力自检 (全部块精确 top-512)
vs block-parallel 流式 run_idx → id_diff=0 (n_groups=10966)。76 测试全绿零
警告。

**结果** (FP8, B=1): 30K decode 9.2 → **14.4 tok/s** (1.57×); 4K 25.4 无回归。
干净单步 nsys (30K, ~69.7ms/步) 显示剩余长上下文成本: Fp8Gev 25.6% (权重
带宽, 短上下文也有, 非退化) / MergeChunkTopk 13.6% (15 chunk×12 层×132us,
流式 merge 的 O(n_chunks) 开销) / Bf16Gev 12.3% / IndexerLogitsBlockPar
10.6% (块并行后从 ~50% 降到 10.6%) / SparseAttention 9.6%。下一步候选:
MergeChunkTopk 合并优化 (减少 15 次 512 元 bitonic-merge)。

## 2026-09-18 — QSA 长上下文召回修复: 流式 top-k (移除 8192 硬上限)

**背景**: 用户真实场景是 agent 开发 (40K-200K token prompt)。发现 QSA 稀疏
注意力只 attend 前 8192 token: `kMaxBlocks=2048` (=kMaxT 8192/compress 4)
把候选块上限锁死在前 2048 个压缩块, `TopkSelectKernel` 的 `s_val[2048]`
bitonic 硬编码。8192 之后的近期上下文**从不被打分**, 长上下文召回直接断裂
(needle 测试 13.5K prompt 末尾密钥答不出)。这是**我们的不完整实现 bug**,
非 SGLang 设计 — 参考 (tokenspeed/vllm/sglang-ssd-stream) 都对**全部**
num_blocks 打分, 无上限。

**为什么不能直接调大 kMaxBlocks**: 打分全部块需 `d_S[T×n_iq×n_blocks]` /
`d_logits[T×n_blocks]`。decode T=1 时 [1×4×50000]≈400KB 可行; 但 prefill
T=8192 时 [8192×4×50000]≈3.3TB 不可行 → 必须**流式** (像参考, 从不
materialize [T,all_blocks])。

**做了什么** (src/model/full_attention.cu, 镜像 tokenspeed split+merge-tree):
- 常量: `kMaxBlocks` 语义从"块上限"改为"打分 CHUNK 大小", 新增
  `kMaxBlockTopk=512`。
- `IndexerLogitsKernel`/`IndexerReduceKernel` 加 `block_off` 参数: 打分**全局**
  块 [block_off, block_off+max_blocks), 去掉 2048 cap, 因果掩码用全局
  n_groups (不 cap)。
- 新增 4 kernel: `BitonicSortAsc` (运行时 N 通用 bitonic) / `InitRunTopkKernel`
  (running top-k 置空) / `MergeChunkTopkKernel` (每 chunk 局部 top-512 与
  running top-512 做 1024 元 bitonic-merge, 保留全局 top-512) /
  `ExpandRunTopkKernel` (running top-512 块 id 展开成 token + 当前 group
  尾部 force-include)。
- forward 分支: `n_groups_max <= max_blocks` (≤8192 token) 走**原 single-shot
  路径不变** (零回归); 否则走**流式路径** — CHUNK=2048 循环覆盖所有块, 每块
  tensor-core GEMM 打分 + merge 进 running top-512, 末尾 expand。内存有界
  ([T,block_topk])。单序列走 GEMM 路径, 多序列走 SIMT IndexerLogitsKernel
  (per-seq idx_comp 切片)。
- workspace 加 `d_run_val`/`d_run_idx` [T,512]。

**验证** (先测后投, 全部闭合):
1. **流式合并 = 精确全局 top-512**: 临时自检把 d_iq/idx_comp 拷回 host, 暴力
   算全部块 logits 取真 top-512, 与流式 run_idx 对比。2-chunk (n_groups=4096)
   多 chunk 合并: `id_diff=1~2` 且 `far_from_boundary=0` (所有差异块紧贴
   边界), `max_logit_diff≤0.00011` — 确凿证明唯一差异是边界 near-tie 的浮点
   tie-break, **非 bug**。单 chunk (n_groups=750) 逐位一致。
2. **>8192 位置可召回** (硬上限已移除的决定性证据): needle 放在位置 ~9000
   (group 2250 > 2048, 旧代码 100% 不可见) → 新代码**召回** "FALCON-42"。
3. **短上下文零回归**: ≤8192 走原 single-shot 路径, 76 测试全绿零警告
   (full_attention_forward l2_rel=4.7e-03 不变)。
4. **模型非确定性说明**: 长 prompt 逐层 logits 对比时, 单序列 forward 在
   layer 1+ 有 float atomicAdd 非确定性 (call=1 sum 跨 run 3082496/3098512/
   3075680/3089312 四个值, call=0 恒等) — 这是既有特性非本次引入, 流式与
   single-shot 在 call=0 逐位一致证明选择逻辑等价。

**已知边界 (非 bug)**: QSA top-512 是**选择性**稀疏 — 当上下文块数远大于
512 且 needle 块 logit 不够突出时, 可能跌出 top-512 (19066 token needle @85%
未召回, 但 needle @9000 召回)。参考无大 recent window (recent_write 仅是
当前 group 尾部, 已处理), 此选择性是 QSA 设计固有, 与 vllm/sglang 一致。

**下一步**: 长上下文性能实测 (30K+ prompt 经 serve chunked prefill) + 文档
STATUS 更新。

## 2026-09-18 — decode 性能: FP8 W8A16 投影 (单流 decode 1.31×)

**背景**: 用户"参考 vllm 一次性完成工业化剩余 + 开始 decode 性能优化, 暂不碰 MTP,
API E2E 测试, 分析权重流量+kernel 开销, 目标单流 decode 达 273 GB/s 上限 (之前连
240 都没到)"。

**profile (先测后投)**: nsys decode 80-tok:
- `Bf16GevKernel` (M=1 BF16 投影 GEMV) = **61.6%** (3.09s/5.0s), 55120 calls,
  max 7.4ms (=lm_head 读 1.27GB/步)。
- **GPU 满载** (kernel busy 5.0s ≈ wall 5.02s) → **非 launch-bound**
  (cudaLaunchKernel 1.6%, 与 GPU 重叠隐藏) → **CUDA Graph 无用**。
- proto (fp8_gemv_proto.cu) 复测: **BF16 GEMV 大投影已 244-252 GB/s** (近 273
  spec/超 241 copy)。**认知修正: 273 GB/s 非"提高 GB/s"而是 FP8 减字节** —
  W8A16 (e4m3 权重 1B + per-channel scale, BF16 激活) 减半权重流量 → 大投影 2×。

**做了什么 (FP8 W8A16, 即既定"计划 C", 双存零风险)**
- **gemv.cu/.h**: `Fp8GevKernel` (16 e4m3/iter via uint4 + 行 scale, BF16 激活) +
  `QuantizeFp8RowKernel` (per-output-row absmax/448) + `Fp8Shadow` +
  `BuildFp8Shadow` + `Fp8ProjEnabled` (`Q4T_FP8_PROJ` gate)。
- **linear.h `ProjGemm`**: M=1 有 shadow → Fp8Gev, 否则严格 = Bf16Gemm。
- **接入**: attn q/k/v/o + GDN in_proj_qkv/z/out_proj + lm_head + MoE
  shared_gu/down。保 BF16: attn index_qk (合并行偏移) / GDN a/b (N=48 微+递归敏感)
  / router gate (top-k 精确) / HC 低秩+小 k/v (latency-bound, 转了收益微)。

## 2026-09-18 — PLE page_reader io_uring exact-recovery (从 ds4 借鉴)

**背景 (用户加的 ds4/tokenspeed 参考对标)**
PLE SSD Stream 对标 ds4 (DwarfStar, 同模型 Qwen4 + 同硬件类 DGX Spark) 与
tokenspeed (datacenter, n-gram 全驻 HBM, 无 SSD stream)。**结论: 我们 PLE 核心

stream。唯一实质借鉴 = ds4 磁盘读失败 exact-recovery (我们此前 fail-closed)。

**做了什么**
page_reader 从 fail-closed (任何 cqe->res<0 → 永久 broken, 一次瞬时 NVMe 抖动即
杀死整个进程生命周期的 reader) 升级为 exact-recovery: 每 wave 跟踪 per-page 已读
字节, 对短读 (res<valid) 或瞬时错误 (EAGAIN/EINTR/EBUSY/ECANCELED) 从未完成 offset
重提交, 上限 kMaxReadRetries=8 轮; 持久 errno + 意外 EOF 仍 fail-closed (绝不
scatter 脏页字节)。正常路径 (首次读满有效长度) 退化为原单次 submit+reap →
成功读逐位一致。

**验证**: env-gated 故障注入 (Q4T_PLE_FAULT_INJECT) + 新测试
ple_page_reader_fault_recovery (8 注入短读跨 12 页 → 重试补齐 → 数据正确 + reader
仍可用)。正常路径 ple_e2e_gather l2_rel 0.000e+00 + working memory 75.17 MiB 不变。
71 测试全绿。对齐 ds4 的 test_qwen4_ngram_state (failed disk reads → exact recovery)。
