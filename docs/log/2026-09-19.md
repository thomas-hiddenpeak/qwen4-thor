## 2026-09-19 — 单流非量化 decode 剖析: 移除 indexer D2H sync 是净损失 (负结果, 已回退)

**背景**: 用户明确 decode 优化方向 = 单流 (B=1) 非量化 (默认 BF16, 无
FP8/MTP)。先 nsys 剖析 (Q4T_PROFILE_DECODE=1 + nsys
--capture-range=cudaProfilerApi, serve --no-mtp --max-seq 1, 单步捕获)。

**剖析结果 (单步 span 82.5ms ≈ 12.1 tok/s)**:
- GPU busy 69.6ms, 间隙 15.2ms (18.5%)。
- kernel: Bf16Gev 55.4% (lm_head 单 kernel 5.17ms = 246GB/s **峰值带宽**,
  大投影全到地板) / MoE nvjet FP4 13.1% (92% 流式地板) / SparseAttention
  9.5% (cp.async 已优化) / MoE 量化+gather 8.1% / IndexerLogits 6.3%。
- 间隙 = 14 个大间隙 (9.59ms) 全是 host-GPU D2H 同步气泡: (a) MoE router
  BuildTokenLists→BuildRowOfFlat (host 读回 expert 分配建 per-expert GEMM
  plan, 不可避免, 最大 4.48ms) + (b) QSA indexer BuildCompressedK→
  IndexerLogits (host 读 max_pos 选分支, 每 full-attn 层一次)。

**尝试 (负结果)**: 以为 (b) 可省 (单流 host 端知道 max_pos), 给
FullAttentionForward/DecoderLayerForward/RunLayers 加 host_max_pos 跳过 D2H。
**首次 nsys A/B 显示 82.5→78.7ms (-4.6%) 误判为正** — 根因: serve decode 走
ModelDecodeBatchMulti (B=1 也是 Multi, 总传 d_seq_id), 只改了
ModelDecodeBatch/RunPrefill/ModelDecodeStep, **Multi 没接上 = NO-OP**
(memcpy/sync 计数 125/61 没变是铁证)。接上 Multi 后 **反而 82.5→117ms
(慢 3×)**: 移除 indexer sync 让 host 提前跑, MoE kernel 提前 enqueue, MoE
router 的不可避免 D2H 要等更长 GPU backlog → 8 个 MoE 间隙全膨胀到 ~4.4-5ms
(合计 36ms)。**看似浪费的 indexer StreamSync 实为有益"排空点", 把 GPU 等待
分摊; 删一个 sync 会把等待转移到下一个不可避免 sync 并放大。已回退, 基线
bit-exact 确认。**

**结论**: 单流非量化 decode 近结构带宽地板 (~12-14 tok/s)。真正最大单点 =
MoE router D2H (8×~4.4ms), 要消需 GPU-resident MoE plan (免 host 读回
expert 分配), 大改高风险。非量化约束下其余杠杆 (MoE 量化融合 ~8% / 小
GEMV) 收益小且难。下一步待用户定夺 (GPU-resident MoE plan / 接受地板 /
重审约束)。


## 2026-09-19 — 启动提速 (终): MoE 加载阶段剖析, 确认到达 NVMe 硬件地板

**背景**: pread 优化后冷启动 32.1s, MoE 占 18.3s/48 层 (~381ms/层)。
上一轮提过 io_uring/合并读方向, 本轮先测量再决定 (避免"计划 D"式
优化错目标)。

**阶段剖析 (Q4T_LOAD_TIMING 新增 read/h2d/swizzle 分段, env 门控零开销)**:
- 热缓存 48 层: read=159.8s 线程时间 (80.5%) / h2d=32.8s (16.5%) /
  swizzle=5.9s (3.0%)。14 线程 × 14.3s wall = 198s 线程时间, 100% 吻合。
- 冷启动 48 层: read=236.6s (80%) / h2d=13.1s / swizzle=5.9s。
  冷 read 带宽 = 84GB/18.4s = **4.56 GB/s, 高于冷 NVMe 顺序读
  (2.72 GB/s) 1.67×** — 14 线程并行已榨出 NVMe 并行性。
- h2d 阶段是 22 万次 cudaMemcpyAsync 的**驱动提交开销**, 非拷贝时间
  (Thor 统一内存, 84GB 拷贝实际仅 ~0.35s)。

**排除的方向 (全部数据驱动)**:
1. **pread 直接到 device** (省 host staging + 权重 H2D): 最小验证
   cudaMalloc 指针 pread 4KB → **errno=14 EFAULT**。Thor 统一内存对
   cudaMemcpy 有效, 但内核 pread 页错误写路径不可写 cudaMalloc 内存。
   死路。
2. **更多线程 (32/64)**: Q4T_MOE_THREADS 覆盖冷测 — 14 与 32 **逐毫秒
   相同** (18274 vs 18262ms), 64 更差 (24421ms, 14 核上 4.5× 过订阅
   上下文切换)。32=14 证明 **NVMe 在 14 线程时已饱和**, 加深队列
   (更多线程/io_uring) 无收益。
3. **合并同类型连续读** (shard 内按类型跨专家连续, 如 128 专家
   gate.weight 连续 105MB): 会失去跨 shard 并行性 → 退化为顺序读
   (2.72 GB/s) 比当前并行 (4.56 GB/s) 更慢。32 线程实验已证明并行
   饱和, 合并只会更糟。

**结论**: MoE 加载 (84GB) 冷 ~18.3s = **NVMe 硬件带宽地板**, 软件
优化空间已闭合。冷 model_load 27.1s = head 1.4s + MoE 18.3s +
非 MoE 层 ~7s + ple 0.1s。再快需架构级改动 (MoE expert 像 PLE 那样
按需流式, 启动换推理延迟), 属 Phase 级决策。

**保留的工具** (env 门控, 默认行为不变, bit-exact 已验证):
- Q4T_LOAD_TIMING: MoE 每层打印 read/h2d/swizzle 分段。
- Q4T_MOE_THREADS=N: 覆盖 MoE 加载线程数 (默认 min(hw, E)=14)。
- worker 重排为 7 阶段 (权重读→权重 H2D→scale 读→swizzle→scale H2D
  →scalar 读→scalar H2D), 无依赖冲突, stream 顺序不变。

**验证**: 76 测试 0 失败; E2E bit-exact (== pread 基线); 零警告;
干净冷测 model_load 27.1s。


## 2026-09-19 — 启动提速 (续): pread 读取 + tensor hash 索引 (冷启动 44.2s → 32.1s)

**背景**: 上一项并行 MoE 加载把冷启动 63.7→44.2s, 但 MoE 每层仍 ~363ms,
非 MoE 层 ~12.3s。继续定位。

**瓶颈定位 (数据驱动)**:
- 每层 512 专家 × 10 小张量 = 5120 次 ReadTensor, 只跨 4 个 shard
  (LRU=32 足够, 非驱逐问题)。
- 每 shard 平均 1504 tensor, 而 SafetensorsFile::Find 是**线性扫描**
  (无 hash 索引) → 每次查找 ~1500 次字符串比较。
- 关键: 热缓存 363ms/层 = 1.26GB/层 ÷ 363ms = **3.5GB/s 聚合**, 远低于
  page cache 带宽。算账: 1.26GB ÷ 4KB = 322K 页, mmap 首次触碰每页建 PTE
  (~1μs minor fault) → 322K × 1μs ≈ 350ms/层, **与实测 363ms 几乎完全
  吻合**。根因是 mmap 的逐页 minor page fault, 不是带宽/锁/字符串。
  (代码注释早已提到参考项目 Qwen3x-Orin 用 ::read 避免此问题。)

**实现** (全在 safetensors.cpp, Pimpl 内部, 零 API 变更, MoE+非MoE+head+PLE
全生效):
1. **ReadTensor 改用 pread** (替代 mmap+memcpy): 单次内核调用拷贝整段,
   线程安全 (无共享 fd lseek 竞争), 且无逐页 user-space fault。EINTR 重试
   + 短读检测。
2. **Find 加 hash 索引**: Open 时建 name→index (unordered_map), O(1) 替代
   O(1500) 线性扫描。次要但安全。

**结果**:
- 冷启动 (drop_caches): **44.2s → 32.1s (-27%)**, model_load 35.1→27.0s,
  layers 32.1→23.7s
- 热缓存: model_load 33.9→20.9s, layers 29.7→18.4s
- **非 MoE 层 12.3s → ~4.2s (-66%)**: pread 消除逐页 fault 效果最大
  (非 MoE 是大张量, 页 fault 占比最高)
- MoE 48 层 17.4s → 14.3s (均 363→297ms), 现 ~4.2GB/s 聚合已接近 NVMe
  带宽 (每专家 10 个小 pread, 5120 次/层, 进一步需 io_uring 批量异步)
- **bit-exact**: pread 输出 == C++17 基线 == C++23 基线 (580 字符 cmp 全等)
- 76 测试全绿, 零警告

**下一步 (未做)**: MoE 每专家 10 个小 pread 是新的带宽受限点, 方向 io_uring
批量异步 (PLE 层已用 io_uring, MoE 可复用); 非 MoE 层 ~4.2s 已接近带宽
下限, 收益有限。当前 32s 冷启动达工业级。

## 2026-09-19 — C++23 全量迁移: host + device (GCC 14 + CMake 4.4.3)

**背景**: 上一项只升了 host C++23 (device 保持 C++17)。用户补充: 迁移到
C++23 是 NVIDIA 工程师建议, CUDA 13.3 已全面支持 host+device C++23;
"暂时不动 device" 是指可逐步迁移, 不是永久不动; GCC 可升级, 环境受控。
→ 目标改为 host+device 全 C++23, 现有 .cu 代码 (C++17 兼容, 是 C++23 子集)
零改动照常编译, 新代码逐步采用 C++23 特性。

**技术验证 (关键发现)**:
1. nvcc 13.3 支持 `--std=c++23` (选项列表有), 但 **GCC 13 时 nvcc 静默忽略**
   ("not supported with the configured host compiler") → device C++23 从未
   真正生效。根因: nvcc 要求 host 编译器也支持 C++23。
2. **GCC 14 是 device C++23 的前提**。noble (24.04) apt 无 gcc-15 (那是
   24.10+), 有 gcc-14 (14.2.0) → 装 g++-14。
3. **CMake 必须 >= 4.0**: `CMAKE_CUDA_STANDARD 23` 只在 CMake 4.x 的 NVIDIA
   模块里映射到 nvcc `--std=c++23`; 3.28/3.31 都只到 CUDA20, 报
   "requires the language dialect CUDA23"。apt 只有 3.28.3 → pip 装
   cmake==4.4.3 (用户级, 不覆盖系统)。
4. GCC 14.2 C++23 实测: host+device 都可用 std::print/expected/format/
   ranges/jthread/顺序指定初始化 (device 需 --expt-relaxed-constexpr, 项目
   已有); 需 GCC 15 的: std::mdspan, constexpr std::string。
   **device 边界**: 乱序指定初始化 (C++23 P1967R3) cudafe 不支持, 用声明顺序。

**实现**:
- CMakeLists: CMAKE_CUDA_STANDARD 17→23 (host 已是 23), cmake_minimum_required
  3.24→4.0, 注释写明 GCC>=14 + CMake>=4.0 要求 + device 边界。
- 配置: `cmake -DCMAKE_CXX_COMPILER=g++-14 -DCMAKE_CUDA_HOST_COMPILER=g++-14`
  (CMake 4.4.3)。现有 .cu 代码零改动。

**验证**:
- 确认 .cu 编译 flags 含 `--std=c++23` (flags.make 实证)。
- 全量重编 (g++-14 host + nvcc C++23 device) **零警告零错误**。
- 76 测试全绿。
- **E2E bit-exact**: 44K prompt 128 gen 输出 == C++17 基线 (par/mtp 全等,
  580 字符 cmp 通过)。C++23 迁移无行为回归。

**环境变更 (受控)**: apt 装 g++-14/gcc-14; pip 装 cmake 4.4.3 (用户级)。
系统默认 c++ 仍 g++-13, 项目构建显式指定 g++-14, 不影响其他工具链。

**下一步**: 新 host/device 代码可采用 C++23 特性 (std::expected 替换裸
Status / std::print / ranges); 现有代码按需逐步迁移, 不强制。

## 2026-09-19 — 启动提速: 并行 MoE 专家权重加载 (冷启动 63.7s → 44.2s)

**背景**: 上一项 (OOM 可靠性) 加了启动分段计时, 测得 model_load 占启动 90%
(58.3s/64.6s)。用户要求启动"稳定快速, 工业级"。定位 model_load 内部分布:
head 1.4s + **layers 58.4s (96%)** + ple 0.09s + buffers 0.2s。layers 里
MoE 专家权重读取是绝对大头。

**瓶颈定位 (Q4T_LOAD_TIMING=1 探针)**:
- 单线程 MoE 专家加载: 每层 ~1000ms × 48 层 ≈ 49s (占 model_load 84%)
- 根因: 24576 个专家 (48 层 × 512) 每个读 10 个小张量 (gate/up/down 的
  weight+scale), 每次 ReadTensor 都构造 tensor 名字字符串 + unordered_map
  查找 + mmap page fault + memcpy, 单线程 host 读取仅 ~1.2GB/s (NVMe 冷读
  能力 2.72GB/s, 热读 6.88GB/s, 远未打满)
- swizzle ~180ms/层, H2D 异步已与读取重叠 (统一内存下 H2D≈memcpy)

**实现**:
1. **并行 MoE 专家加载** (src/quant/moe_weights.cpp): 每层 512 专家用
   14 线程 (hardware_concurrency) 池并行, std::atomic 工作队列
   (fetch_add 领专家), 每线程本地 staging buffer (零跨线程共享), 各专家
   独立 ReadTensor + H2D + swizzle。线程数 = min(cores, E)。
2. **WeightLoader 线程安全** (weight_loader.{h,cpp}): 加 mutable std::mutex,
   EnsureOpen (LRU shard 缓存) 持锁; 之前单线程无锁, 并行下会数据竞争。
   LRU max_open 8 → 32 (14 线程并发读多个 shard, 小 LRU 会 open/evict 抖动)。
3. **零分配 swizzle** (quant/swizzle.h): 新增 SwizzleSfInto (原地 scatter,
   不临时 vector), 每线程复用, 去掉每专家重复分配。
4. **修复潜在异步 use-after-free**: 旧循环在 H2D (cudaMemcpyAsync) 未同步
   时就析构 staging buffer; 并行版每线程 buffer 活到线程结束, 且层末
   cudaStreamSynchronize。

**踩坑 (负优化, 已回退)**: 试过 OpenAllShards 预开全部 197 shard 以省锁内
LRU 重排 —— 热缓存实测 3x 更慢 (46s → 133s, MoE/层 363ms → 956ms)。根因:
197 个并发 mmap 让 14 线程 page fault 在内核 VMA/页表锁上竞争。结论: 保持
32-shard LRU (每层专家集中在少数 shard, 驱逐罕见), 不预开全量。已回退。

**结果**:
- 冷启动 (drop_caches): **63.7s → 44.2s (-31%)**, model_load 58.3s → 35.1s
- 热缓存: model_load 33.9s, MoE 48 层总 17.4s (均 363ms/层, min 157 max 675)
- 14 线程下 MoE 聚合 ~3.5GB/s (受每专家字符串/map 开销 + LRU 锁竞争限制,
  非带宽瓶颈)
- **bit-exact**: 并行加载输出 == 串行 == MTP == plain (580 字符 cmp 全等)
- 76 测试全绿, -Wall -Wextra 零警告

**下一步 (未做, 留待)**: 非 MoE 层 ~12.3s (HC/attn/linear/PLE 加载 +
每层 cudaMalloc/memset) + head 1.3s 仍可优化: 每层专家 tensor 名/offset
预解析 (省 24576×10 次字符串构造 + map 查找), 跨层专家全局工作队列 (均衡
负载), 批量 H2D。当前 44s 已达工业级可接受, 优先保证稳定。

## 2026-09-19 — OOM 可靠性工程: 内存预算 (--mem-fraction) + auto-length + 运行时 preflight + 启动可观测性

**背景**: 08:29 系统 OOM 重启 (根因: --max-len 262144 未配 --max-seq 1 →
KV 池 65GB + 权重 84GB > 122GB 统一内存)。用户要求: (1) 提升运行中 OOM
可靠性; (2) 引入最大内存占用比例启动参数; (3) 引入 vllm auto-length 机制,
即使配置了最大并发/最大长度也不会 OOM; (4) 启动阶段稳定快速, 工业级。

**内存模型 (调研结论)**:
- 权重 84.0 GB = WeightIndex::total_size() (main+MTP+vision 精确字节, 最可靠输入)
- 固定成本 ~14.2 GB (实测): d_ws 2.68GB (max layer @max_prefill=8192) +
  forward buffers 0.4GB + d_prefill_logits [8192,vocab] 4.07GB + MTP ws ~5GB +
  PLE 工作内存 75MiB (51.2GB sidecar 走 NVMe 流式, 不常驻) + 2GB 余量
- 状态池 (随 max_len×max_seq): 13 层 full-attn (12 主 + 1 MTP) 每 token/seq
  33356B (KV 2048B + page_table 4B + indexer 512B + rope 12B) + 36 层 linear
  SSM/conv 110.4MB/seq (O(1) 不随 max_len) + PLE conv 184KB/seq
- 每请求瞬态 (prefill 串行, 最坏 1 个): trunk T×hc_dim×2 (262K=5.37GB,
  MtpDraftExtend 后立即释放) + MTP draft logits [max_prefill,vocab] 4.07GB

**实现**:
1. 新模块 q4t_runtime (src/runtime/memory_budget.{h,cpp}, 纯 host 无 CUDA):
   ComputeMemoryBudget 按 mem_fraction×MemTotal 预算推导 (max_len, max_seq)
   上限; 用户 pin max_len 时推导 max_seq, 装不下则二分回退 max_len (max_seq=1);
   未 pin 时 auto 推导 max_len (vllm gpu_memory_utilization 等价)。
   ReadMemTotal/ReadMemAvailable/ReadMemFree 读 /proc/meminfo。
2. ServerOptions 加 mem_fraction (默认 0.90) + no_budget; main.cpp 加
   --mem-fraction / --no-budget。ChatServer::Start 在 LoadModel 前算预算,
   capped 值穿透 cfg/max_seq_ (MTP/scheduler 全部跟随), 打印预算报告。
3. 运行时 preflight (HandleChat trunk 分配前): MemAvailable < trunk +
   draft_logits + 2GB 余量 → 软降级 plain decode (不 OOM)。注意用
   MemAvailable 而非 MemFree: 稳态 MemFree 仅 2-5GB (权重+page cache 占满)
   会误触发, MemAvailable ~120GB 含可回收 cache 才是 cudaMalloc 真实可用量。
4. 启动可观测性: PhaseTimer RAII 打印 [q4t][startup] <phase> <ms>
   (tokenizer/budget/model_load/mtp_load/vision_load/startup_total)。

**验证**:
- 预算数学 (真实参数): 262144×seq8 (OOM 配置) → CAPPED seq=1; auto seq8 →
  max_len=53248; auto seq1 → 262144; frac 0.85 → 180224

## 2026-09-19 — chunked MTP: 长上下文投机解码 (44K 17.7 → 33.1 tok/s, 精度无损)

**背景**: 44K decode 17.7 tok/s, 目标 18+ 且不改精度。前序发现 (见
2026-09-18.md 末条): plain decode 单步 4K≈44K (57ms), 4K=30 vs 44K=17.7
的差距纯粹是 MTP gate (4K 不 chunked 走 MTP; 44K chunked 被禁用)。

**做了什么**:
1. `MtpDraftExtend` 分块路径 (src/mtp/mtp.cu): T > max_prefill 时每块
   ≤ max_prefill 调 MtpForward, 仅最后一块 compute_logits (logits 只
   [last_c, vocab] 而非 [T, vocab], 44K 省 21.9GB)。draft 模型是单层
   (1 full-attn + 1 MoE, 无 linear SSM/conv), KV/indexer 按绝对位置写
   per-seq 池化切片 (MtpResetState 已清零), 块间天然续接, 与主模型
   chunked prefill 同契约 (bit-identical)。
2. chat_server: trunk 分配去掉 `!chunked` 限制 (软回退: 分配失败 →
   plain decode); chunked prefill 的 ModelPrefill/ModelDecodeBatch 传
   trunk_out 累积全 prompt trunk (每块写 [base, base+c) 行); use_mtp
   gate 从 `mtp_loaded_ && !chunked` 改为 `mtp_loaded_ && d_trunk_full
   != nullptr`。

**为什么 gate 原来过保守**: 旧注释按 262K 最坏情况算 (trunk 5.3GB +
draft KV 26GB), 但 draft KV/indexer 池在 MTP load 时就按 max_len×
max_seq 分配了 (不是 per-request 成本); per-request 新增只有 trunk
buffer (44K 仅 0.9GB)。MTP 精度安全: 主模型验证所有 draft token, 输出
与纯 greedy 完全一致。

**验证**:
- 76 测试全绿零警告
- 44K (44002 tok) MtpDraftExtend 分 6 块全 ok
- **44K decode 17.7 → 33.1 tok/s (1.87×)**, 4K MTP 基线 33.6 持平
- **精度 bit-exact**: 44K 同 prompt, MTP vs --no-mtp 输出逐字完全一致
  (128 tok)
- 4K 非 chunked 路径无回归 (33.6 tok/s)
