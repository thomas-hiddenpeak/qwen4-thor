## 2026-09-17 — 多流 MoE (per-expert 轮询多 CUDA 流填满 SM): prefill 990→1062 / 批 decode B=128 308→374 tok/s

**动机**
09-17 profile 定位: 批处理 decode 的 MoE 仅 ~34% 带宽, 根因 per-expert 小 GEMM
(M_e≈10 tok) 只生成 ~10 个 tile, 20 个 SM 只用一半 (SM 欠占用)。用户批准路径 A
(多流, 不量化, kernel 优化)。per-expert chain (gather→gu GEMM→swiglu→dn GEMM) 无
数据依赖 → 轮询到 N 个 CUDA 流并发, 填满 SM。

**做了什么** (src/quant/moe_gemm.cu)
- N 个流 (env `Q4T_MOE_STREAMS`, 默认 4; 1=旧单流 bit 不变)。流 0 = 调用方流 (复用
  ws+gemm_ws); 流 1..N-1 各自 a_packed/a_sf/gu_out ([M] 行足够, M_e≤M) + cuBLASLt
  workspace (并发专家不互相覆盖)。dn_out 按 per-expert offset 不相交写 → 共享。
- 输入就绪由 counts 的 host sync 保证; 组合前用 event 让调用方流等齐所有流。
- 数值**逐位不变** (各专家算同样的东西, 只是并发; 组合按固定 slot 序求和)。

**负→正 (persistent scratch 是关键)**
初版 per-call `cudaMallocAsync` 每流 32MB gemm_ws → 每步 48 层 ×3 流 ×32MB 分配,
**N=4 反而更慢** (B=128 308→291, B=1 16.8→7.1)。改为**持久 scratch** (静态池, 按最大
M 增长, 分配一次) 后**翻正**。教训: 多流的收益极易被 per-call 大分配吃掉。

**结果** (bench-decode --sweep, persistent):
| B | N=1 | N=4 | 提升 |
|---|---|---|---|
| 8 | 63.5 | 75.0 | +18% |
| 32 | 157.2 | 193.7 | +23% |
| 128 | 308.7 | **373.8** | +21% |

- **prefill (M=2560, ~50 tok/专家, 同样 SM 欠占用): 990→1062 tok/s (+7.2%, 破 1000)**。
- N=4 是甜点 (N=8 ≈ N=4, 373.8 vs 372.0 收益递减)。小 B 也小幅升 (B=1 16.8→17.9)。
- 68 测试全绿零警告, moe 数值逐位不变 (max_rel 0.0077468 / l2_rel 0.0098645),
  generate 输出连贯 ("Paris. The capital of Germany is Berlin.")。

**剩余 MoE 杠杆**: 多流吃到了 SM 欠占用那部分; host launch 开销 + 权重带宽仍在,
monolithic grouped FP4 MoE (路径 B) 是更大但更难的下一步。GDN decode 已地板。

## 2026-09-17 — 批处理 decode 吞吐标度实测: B=1→128 聚合 16.6→308.9 tok/s (18.6×)

**动机**
用户指出 1000 tok/s 是可用下限非上限, 要求推进批处理 (暂不量化, kernel 优化可做)。
Roofline (09-16) 已证 prefill 张量核 ~96% 空转、访存受限; decode 更甚 (单 token/
forward 加载全部 MoE 权重)。批处理正是填满空转张量核的正道 —— 实测验证。

**做了什么**
新增 `q4t bench-decode` 子命令 (src/main.cpp): prefill B 个不同 prompt 的序列 →
N 次打包 decode (`ModelDecodeBatchMulti`, T=B, per-seq 路由真实) → 报聚合 tok/s。
`--sweep` 一次加载 (max_seq=--batch) 扫 B=1,2,4,...,--batch (子集池化状态,
positions 钉在 [P,P+N) 使注意力范围恒定)。计时只前向 (无 argmax/D2H)。修一个自造
bug: 合成 token `(b*9973+step*131+7)%20000` 在 warmup step=-1 时 C++ 负取模 → 负
token id → EmbedLookup 越界; 改强制非负。

**实测标度曲线** (prompt=128, steps=64):
| B | 聚合 tok/s | tok/s/seq | ms/step |
|---|---|---|---|
| 1 | 16.6 | 16.59 | 60 |
| 2 | 21.7 | 10.87 | 92 |
| 4 | 37.7 | 9.44 | 106 |
| 8 | 63.3 | 7.91 | 126 |
| 16 | 101.5 | 6.34 | 158 |
| 32 | 155.9 | 4.87 | 205 |
| 64 | 225.4 | 3.52 | 284 |
| 128 | **308.9** | 2.41 | 414 |

**结论: 批处理 decode 聚合吞吐 B=1→128 提升 18.6× 且仍在爬升 (未饱和)**。ms/step
仅从 60→414 (128× token 只 6.9× 时间) → per-token 成本降 18.6× = MoE 权重摊销正是
roofline 预言。B<51 时激活专家数随 B 增 (权重加载线性增); B>51 专家近全激活, 权重
加载饱和, 加 token 更廉 (边际成本降, B=64→128 步时仅 1.46×)。

**B=128 瓶颈 profile** (nsys, cudaProfiler capture range 隔离 decode):
| kernel | % | 性质 |
|---|---|---|
| GatedDeltaNetDecodeKernel | 34.3% | SSM state 读写 804MB/层, 208 GB/s = **86% 带宽 = 地板** |
| MoE fp4 GEMM (gu+dn) | 24.4% | per-expert ~10 tok/专家, 权重 bound |
| SwiGLUQuant+GatherQuant | 16.4% | per-expert 量化 |
| BF16 投影 (cutlass wmma 16×16) | 7.8% | 小 M 投影 |
| SparseAttention | 1.9% | per-seq |

**关键洞察**: B=128 时 **MoE 仅跑 ~34% 带宽** (~13.7 GB 权重 / ~166ms), 根因 per-
expert 小 GEMM (10 tok/专家, 128×128 tile 只填 1/13) → 2-3× 浪费。GDN decode 则已
在 86% 带宽地板 (大 recurrent state 3MB/seq/层 × 36 层 = 108MB/seq, 每步全量读写,
架构固有, 无量化不可降)。

**下一杠杆**: MoE per-expert 结构是批处理吞吐的主杠杆 (34%→~82% 带宽有 2-3× 空间)。
monolithic grouped FP4 MoE (flashinfer trtllm 式, 一次 kernel 处理所有专家, 消除
per-expert launch + 更好 tiling) 同时惠及 prefill 与批处理 decode。GDN 已地板。
不涉及量化。

**工具**: tools/roofline_prefill.py (09-16) + `q4t bench-decode --sweep` (本次)。
