## 2026-09-17 — 下一杠杆调研 + FP8 W8A16 投影 GEMV 可行性 spike (正结果: Thor 上 ~2×)

**背景**
gather 负结果后定"后续大工程"。两个文档级候选 (均"需用户决策"):
① monolithic grouped FP4 MoE GEMM (批量吞吐, B=128 时 MoE 仅 34% 带宽);
② BF16 投影 → FP8 (单请求 decode 58% 是 BF16 投影 GEMV, 2026-09-16 profile)。

**调研结论 (可行性)**
- **① CUTLASS grouped FP4 在 Thor 高风险**: CUTLASS 4.8 的 block-scaled FP4
  grouped kernel 只 ship SM100 (B200) + SM107 (Rubin), **无 SM110/Thor**;
  sm_100a tcgen05 PTX arch-conditional 不保证跑 sm_110a; CUTLASS 未 vendored。
  cuBLASLt 的 block-scaled FP4 在 Thor 已 work (现有 Fp4Gemm) 但**无 grouped API**。
  → 需移植 CUTLASS 到未官方支持的 arch, 可能多周死路。
- **② FP8 投影更可行**: cuBLASLt FP8 (CUDA 13.3 + cuBLAS 13.5, 头文件有
  CUDA_R_8F_E4M3) 在 Thor 可用。杠杆本质 = **W8A16** (权重 FP8 e4m3 半字节 +
  激活 BF16), decode DRAM-bound 于权重字节 → 半字节 ~2×。且 W8A16 无激活 LUT
  (不同于 W4A4 MoE, 见 fp4-gemv-negative-result.md), 手写 GEMV 易 DRAM-bound。

**做了什么 (de-risk spike, tools/fp8_gemv_proto.cu, 独立合成权重不载模型)**
手写 W8A16 FP8 GEMV (读 e4m3 uint4/iter + per-channel scale, 镜像
src/model/gemv.cu 的 warp-per-output BF16 GEMV) vs BF16 baseline, 真实投影形状。
**关键**: 初版小权重驻 L2 (32MB) → BF16 假性 875 GB/s (测的是 L2 非 DRAM);
加 L2-defeat (循环 96MB>3×L2 权重池, 镜像真实 decode 每步权重被逐出) 后干净。

**结果 (L2-defeat, 均跑 ~250 GB/s DRAM 峰值)**
| shape | BF16 | FP8 | 加速 | l2rel fp8/bf16 |
|---|---|---|---|---|
| qkv/o 2560×2560 | 52.8us | 30.1us | **1.75×** | 2.6e-2 / 2.4e-3 |
| 10240×2560 | 203.7us | 103.9us | **1.96×** | 2.6e-2 |
| 2560×10240 | 210.7us | 105.1us | **2.00×** | 2.7e-2 |
| lm_head 151936×2560 | 3109us | 1525us | **2.04×** | 2.7e-2 |
| small 320×2560 | 8.8us | 6.5us | 1.37× (grid 欠占) | 2.8e-2 |

**结论**
- **速度**: 大投影 FP8 W8A16 = **~2×** (DRAM-bound, 半字节, 物理兑现)。用到 decode
  58% BF16 投影 → 预期**单请求 decode ~1.4×**。**FP8 杠杆在 Thor 成立, 无需 CUTLASS**。
- **质量**: e4m3 per-channel **~2.6% l2rel/投影** (vs BF16 0.24%, ~11× 但仍 e4m3
  固有 3-mantissa 精度)。48 层复合 + 注意力投影敏感度 → **需端到端验证** (转权重 +
  generate 对比参考); 可能需 per-group scale (细于 per-channel) 或选择性应用
  (敏感投影留 BF16) 控误差。MoE 已 W4A4 (更粗) 可容, 但投影是否可容需实测。

**下一步 (待用户授权全量)**: FP8 投影全量 = 权重加载时 BF16→FP8 e4m3 (per-channel
scale) + FP8 GEMV 接入 live forward (M=1 decode 路径, gated) + **端到端质量验证**
(greedy 对比参考, 判据同 Phase 1 L2 噪声带)。属改模型数值的大工程, spike 已证速度
+ 量化质量成本, 待用户定夺是否推进。① CUTLASS grouped FP4 若要推进需先 vendored +
编译 SM100 kernel 到 sm_110a 验证能否跑 (可行性 spike)。

## 2026-09-17 — grouped GatherQuant 尝试 (负结果, 已回退): MoE gather 是 work-bound 非 launch-bound

**背景 / 前提 (后被证伪)**
fresh nsys profile: prefill 中 MoE ~28% (FP4 GEMM 13.7% + GatherQuant 6.0% + SwiGLUQuant
5.6% + CombineGrouped 1.5% + RouterTopk 0.5%), 累计 ~110K per-expert 启动。前提假设:
GatherQuant 6.0% 主要是 **~29K 次 per-expert kernel 启动开销**, 合并成 1 次 grouped 启动
应省 ~5-6%。

**做了什么 (尝试)**
grouped GatherQuant: `GroupedGatherQuantKernel` 一次启动量化全部 R=M*k 路由行到连续
`[R, hs/2]` gate/up 输入 (每 grouped 行经 `grouped_row_expert[r]` 找 expert + 本地 index,
per-row 数学与 per-expert `GatherQuantKernel` **逐位一致**), 每 expert SF 块按
`SfBufferSize` cumsum 布局, gate/up GEMM 直接读 `offset_h[e]*(hs/2)` / `gu_sf_offset_h[e]`
切片。gated `Q4T_MOE_NO_GROUPED` 回退 per-expert。event 同步 extra streams。

**正确性**: `quant_moe_gemm` grouped vs fallback `max_rel=0.0077468` **完全一致**, 69 tests
全绿。

**结果 (A/B 同 binary env 切换)**
| prefill | grouped (默认) | per-expert fallback | 差 |
|---|---|---|---|
| 2560 tok | 1061.5 | 1061.2 | +0.03% |
| 8000 tok | 936.4 / 937.5 | 942.4 / 942.7 | **−0.5% (略慢)** |

**结论: grouped gather 无收益 (甚至略慢), 已回退**。前提证伪 —— GatherQuant 6.0% 几乎
全是**量化 WORK** (读 R×hs bf16 + 写 packed+SF, memory-bound), 不是启动开销; grouped
做**同样的 work**, 只省 (E−1) 次启动 ≈ <1% (被新增 grouped buffer alloc + gu_sf_offset
H2D + event 同步抵消)。**decode (M=1) 只激活 k≈8 experts** (per-token 只路由 k 个), 无
多余 expert 可合并 → decode 也无收益 (实测 85ms 两路径一致)。

**修正认知 (关键)**: MoE 真正的杠杆是 **grouped/monolithic FP4 GEMM** (把 E 次 cuBLASLt
per-expert GEMM 启动合并成 1 次 CUTLASS group-GEMM, 命中 FP4 GEMM 13.7%), 需要 CUTLASS
group-gemm (本仓无现成参考, flashinfer clone 仅 attention; 独立大 session)。grouped gather
是它的**必要 substrate 但单独无用**, 应与 GEMM 一起落地并对"获胜路径"共同验证, 不留 default-off
dead code (MoE bug memcheck 不可见, 未使用的风险面不值得保留)。

**下一步**: MoE 优化 = CUTLASS grouped FP4 GEMM (真杠杆, 独立 session) 或转向其他目标;
不再单独尝试 gather/quant 层合并 (已证 work-bound)。

## 2026-09-17 — scheduler-driven decode 尝试 (负结果, 已回退): serve decode 是 GPU-forward-bound 非协调-bound

**背景**
serve↔bench decode 差距诊断怀疑"每步 64 线程协调 (唤醒/重注册) 造成 GPU 步间空转"。
测量: decode 时 GPU 20W (欠占用) + CPU 单核 46% (都不饱和) → 疑似步间协调 gap。

**做了什么 (尝试)**
scheduler-driven decode: 非流式 plain 请求注册一次, 调度器内部驱动整个 decode 循环
(推进 seq + 累积 token), 结束才唤醒请求线程一次 (消除每步握手, GPU 连续喂)。流式/MTP/
fallback 保持每步路径。env Q4T_NO_DRIVEN 可 A/B。

**结果 (A/B 同 binary env 切换)**
| C | driven ON | driven OFF | 差 |
|---|---|---|---|
| C=16 mt=128 | 113.4 | 112.7 | +0.6% |
| C=64 mt=64 | 265.1/268.3 | 261.8/261.7 | **+1.3%** |

**结论: driven decode 无收益 (+1.3% 噪声内), 已回退**。20W GPU + 46% CPU 都不饱和不是
步间协调 gap, 而是**单步 decode forward 本身 memory-bound 且 batch 只 B=16/64 时张量核/
带宽未打满 → forward 是瓶颈, 调度改造不改 forward**。**serve decode = GPU-forward-bound,
非协调-bound**。

**附带发现: 批量 prefill 在 C=64 收益比 max_seq=16 更大**。C=64 mt=64: 旧 (lockstep+
argmax 无批量 prefill) ~181 → 现 (批量 prefill) **262 (+45%)** (loadtest C=64 prefill
占比高, 64 prefill 打包摊销权重)。**批量 prefill 是真实 serve 大杠杆**。

**下一步 (验证结论指向)**: 最大杠杆 = **decode forward 本身** → monolithic grouped FP4
MoE (移植 flashinfer trtllm, 大/多 session)。调度层已榨干 (lockstep + argmax + 批量
prefill + driven 证无效)。

## 2026-09-17 — serve 集成批量 prefill (增量 3): 并发 prefill 打包一次 forward, prefill-heavy +2.0×

**背景**
ragged 原语 + ModelPrefillBatch + bench (2.39×) 就绪。集成进 serve: 并发 plain 请求
的 prefill 打包成一次 ModelPrefillBatch (dense 权重读一次), 缩小 serve↔bench 差距的
prefill 阶段部分。

**做了什么** (src/server/chat_server.cpp + .h)
1. **PrefillReq + 调度器 prefill 阶段**: plain (非 vision/chunk/MTP) 请求不再各自 inline
   prefill, 而是注册 PrefillReq 到 `prefill_pending_` + cv 等待; SchedulerLoop 机会式收集
   当前所有 pending prefill (预算 max_prefill token / max_seq 序列) 打包一次
   ModelPrefillBatch, 各序列末行 (seq_offset[b+1]-1) D2H 回各请求 h_logits + 唤醒
   (镜像现有 decode collect-batch-distribute)。
2. **B=1 单请求特判**: 孤立请求 (Bp==1) 走单序列 ModelPrefill (与 inline **位级一致**),
   只有真正批处理 (Bp>1) 才 ModelPrefillBatch。因为多序列 full-attn indexer (SIMT) 与
   单序列 (张量核 GEMM) 舍入不同, 会翻转 near-tie token (无害但可见, 如 vllm/sglang);
   B=1 特判保孤立请求行为不变。
3. **门控**: `!mtp_loaded_ && !chunked && 非 vision && scheduler_active_` 才批量
   (MTP 需 prefill trunk_out; vision/chunked 需 per-request)。env `Q4T_NO_BATCH_PREFILL`
   可关 (A/B)。**长序列单流 prefill / generate / MTP / vision 路径完全不变**。

**结果** (serve max_seq=16 --no-mtp, A/B 同一 binary env 切换):
| workload | OFF | ON | 加速 |
|---|---|---|---|
| mt=8 C=8 (prefill-heavy) | 29.5 | 46.5 | **1.58×** |
| mt=8 C=16 | 38.3 | 76.4 | **2.0×** |
| 长 prompt(~120tok) C=16 | 42.5 | 70.8 | **1.67×** |
| mt=64 C=16 (decode 主导) | 100.8 | 117.5 | 1.17× |

- 收益随 prefill 占比升 (prefill-heavy 2.0×, decode 主导 1.17×)。
- **B=1 孤立 2+2 → "Four" (3/3, 与 inline 位级一致)**; B>1 near-tie 翻转 (答案仍正确)。
- 并发 C=32 (2× 超限) 排队存活 0 error; 69 测试全绿; 长单序列 prefill 1058 tok/s 不变。

**下一步**: 最大杠杆项 (用户放行) — decode GEMM 权重带宽 (FP8 计划 C) 或 prefill
SparseAttentionKernel, 见 STATUS「当前焦点」。

## 2026-09-17 — bench prefill crash 定位: 小 max_len 暴露既有 layout OOB (真实配置无碍) + MoE 退化路由加固

**背景**
bench-prefill 合成 token 在 B≥10 某 seq 触发 "cudaMemcpy counts" 非法访问 (bench-decode
同复现)。用户要求先排除再集成 serve。

**定位过程** (排除法)
- compute-sanitizer memcheck **干净且跑完** → 非普通 OOB, 是时序/布局相关 (真 OOB 必被抓)。
- 单流 (MOE_STREAMS=1) **确定性 seq 4 失败** → 非多流竞争 (单流全序无竞争 → 是真 OOB 非 race)。
- 换 benign token 模式 **同样 seq 9/4 失败** → **输入无关, 纯结构性** (seq_id + max_seq 决定)。
- 每次 prefill 后加 sync **无效** → OOB 在单个 forward 内。
- **关键**: 把 bench 的 `max_len` 从 256 → **2048 (serve 默认) 崩溃完全消失** (b16 2.73× /
  b10 p64 3.19× 全绿多次)。**根因 = 小 max_len 收紧 full-attn KV/indexer 布局, 某 OOB 写
  在小布局下落到致命处、大布局 (≥2048) 落到自身 slack**。memcheck 抓不到 → OOB 多半在
  cudaMallocAsync 池子相邻 buffer 间 (池内子分配无 red zone)。
- **真实 serve/generate 用 max_len=2048 → 从不触发** (serve max_seq=64 已验证 0 error;
  长单序列 prefill 1058 tok/s 不变)。

**做了什么**
1. **bench-prefill `max_len` = max(P+8, 2048)** (serve-like): 崩溃消失, 工具可用 (src/main.cpp)。
   sweep 干净 B=1/2/4/8/16 speedup 0.99/1.50/1.86/2.39/**2.67×**。
2. **MoE 退化路由加固** (src/quant/moe_gemm.cu, 防御性, 正常路由**位级不变 + 零成本**):
   BuildTokenListsKernel 加 `e<0||e>=E` + `pos<M` 守卫 (防 corrupted expert_id → token_list
   越界); host 端 `count>M` clamp; `row_of_flat` 按 R=M*k (而非 sum(counts)) 分配 (clamp 后
   sum<R, combine 读 flat∈[0,R) 需 R 大小); **zero-init memset 仅在 clamped 时执行** (正常
   路由跳过 → 零成本)。若任何 corruption 产生 garbage expert_id, 现被守卫吞掉不崩。

**验证**: 69 测试全绿零警告 (位级不变); 长单序列 prefill 1058 tok/s (原 ~1061, 噪声内);
bench sweep 全绿。**残留**: 小 max_len (<~2048) 下的 latent OOB 未 root-fix (masks 于所有
instrumentation + 现实配置无碍), 列为低优先独立排查。

**下一步**: 增量 3 — serve 集成 ModelPrefillBatch。

## 2026-09-17 — ragged 批量 prefill 原语 + ModelPrefillBatch (serve prefill 打包的基础, MTP 位不变)

**背景**
serve 8.3×→10.4× 后, 剩余与 bench 的差距主要来自 **prefill 阶段**: 并发请求各自
prefill, 每个 serialize 在 model_mu_ 上各扫一遍 ~24 GB dense 权重 (mt=32/64/128 →
128.7/180/207 tok/s, 长 decode 才摊薄 prefill)。用户放行"为 prefill 触碰 MTP kernel
也可以, 只要不是专门为 MTP 去"。多流已在 N=4 饱和 (prefill N=4/8/16 = 1061/1061/1062
tok/s, M_e≈50 只需 N≈2 填满 20 SM), 所以真正的杠杆是**把并发 prefill 打包成一次
forward** → dense 权重只读一次。

**做了什么** (增量 1: ragged kernel 原语, dual-path)
把 5 个 MTP 多序列 causal kernel 从 uniform `tokens_per_seq` 泛化到变长, 用一个
`RaggedBatch` 描述符 (新 `include/q4t/model/ragged_batch.h`): `seq_offset[B+1]`
cu_seqlens + `token_local[T]` 每 token 局部位置。
- **token-grid kernel** (conv / PLE 深度卷积): `tt = token_local ? token_local[t] :
  t%T`。关键: `t - tt` = 序列 packed 起点在 uniform/ragged 下都成立, 所以 tap 索引
  `t-(tt-src)` = seq_start+src 自动正确, 只需换 `tt`。
- **batch-grid kernel** (update-state / GDN): `off = seq_offset?seq_offset[b]:b*T`,
  `len = seq_offset?seq_offset[b+1]-off:T`; `seq=d_seq_id[off]`, 循环 `tt<len`,
  `t=off+tt`。
- **full attention 无需改**: 已全由 per-token `positions[t]` + `d_seq_id[t]` +
  page_table 驱动 (长度无关)。
- **dual-path**: `ragged==null` 走原 Tps 路径 → MTP (model_verify_multi /
  mtp_spec_multi) **位级不变**。`ragged` 参数默认 null 一路穿到 RunLayers →
  DecoderLayerForward → LinearAttentionForward / PleLayerForward。

**做了什么** (增量 2: ModelPrefillBatch + 隔离测试)
- `ModelPrefillBatch(m, tokens, lens, seq_ids, B, logits)`: 打包 B 个**变长全新**
  序列 (sequence-major, Ttot=Σlens) 一次 forward。逐序列 ResetState (per-seq slice,
  头注释"整块清零"已过时, 实现是按 seq byte-stride 的 per-seq 清零) → 建 positions
  (局部 0..len-1) / token_seq / cu_seqlens / token_local / 3D MRoPE (纯文本 delta 0) /
  PLE n-gram history → RunLayers 带 RaggedBatch。新增持久 buffer `d_ragged_seq_offset`
  [max_seq+1] + `d_ragged_token_local` [max_prefill]。
- 新测试 `model_prefill_batch_test.cpp`: B=3 变长 (len 5/3/7) 不同 prompt, 对比 B 个
  独立单序列 prefill → **逐 token l2_rel=0.00000 位级一致 + 末 token argmax 全match +
  无跨序列污染**。

**结果**: 69 测试全绿零警告 (含 MTP mtp_spec_multi/model_verify_multi 位不变)。ragged
batched prefill 前向已就绪且经证正确。

**下一步** (增量 3): 调度器把并发 prefill 请求收集成一次 ModelPrefillBatch (dense
权重只读一次), 以 serve 端口 + loadtest 衡量真实 prefill 阶段收益。

## 2026-09-17 — plain decode 调度 lockstep (对齐 MTP plan A): serve 并发吞吐 +26~53%

**背景**
路径 C 实测 serve 8.3× 与 bench 18.6× 的主要差距之一是**调度非 lockstep**: B2b plain
decode 调度器谓词是"任一 pending 即跑"(机会式), 各请求 decode 后处理错峰 → 批被
切成 ragged 小步, 每步都重读 84 GB 权重 (decode memory-bound 的吞吐杀手)。MTP 侧
2026-09-14 已用 plan A lockstep 解决 (等所有活跃 MTP pending 才跑), plain 未落地。
用户指出这是明确收益, 应落地。

**做了什么** (src/server/chat_server.cpp)
1. **plain decode 谓词改 lockstep**: 等**所有活跃 plain 请求都 pending** 才跑 →
   `ModelDecodeBatchMulti` 的 B = 活跃请求数 (uniform, 对齐 vllm/sglang + MTP plan A),
   而非 ragged 子集。谓词统一处理 plain/mtp 两类 (各自 all-pending 触发)。
2. **离场请求 notify**: plain 请求完成 (EOS/max_tokens/error) 从 active_ 移除后
   `sched_cv_.notify_one()` (离场可把"all pending"翻真, 修 lost-wakeup)。

**结果** (serve max_seq=64 max_len=2048 plain, loadtest max_tokens=64):
| concurrency | 机会式 | lockstep | 提升 |
|---|---|---|---|
| 8 | 42.6 | **65.2** | +53% |
| 32 | 101.6 | **137.4** | +35% |
| 64 | 138.1 | **173.4** | +26% |

- **scale 8.3× → 10.4×** (concurrency 1→64 = 16.7→173.4), 更接近 bench 纯 decode 18.6×。
- 正确性保持: "2+2 一词回答" → "Four"; 128 并发 (2× 超限) 排队存活 0 error; 68 测试全绿。
- 剩余差距 = prefill (每请求各自, 打断 decode 批) + HTTP/tokenizer 串行。

**下一步**: prefill 与 decode 交错/打包 (prefill 打断 decode 批是剩余主要差距) 或回引擎
路径 B (monolithic MoE)。

## 2026-09-17 — 路径 C 兑现: serve 并发吞吐 concurrency 1→64 = 16.6→138.1 tok/s (8.3×)

**背景**
修复 serve 资源背压后 (max_seq=64 现安全), 量化引擎批处理 scale 是否兑现为真实
HTTP 服务吞吐 (bench 纯 decode 证 B=1→128 = 18.6×)。

**实测** (serve max_seq=64 max_len=2048 plain, loadtest.py, max_tokens=64):
| concurrency | 聚合 tok/s | scale |
|---|---|---|
| 1 | 16.6 | 1× |
| 8 | 42.6 | 2.6× |
| 32 | 101.6 | 6.1× |
| 64 | 138.1 | 8.3× |

**结论: 批处理在真实 serve 兑现 8.3× (concurrency 1→64) 且仍爬升**, 0 error 全程存活
(max_seq=64 载入 93GB/28GB 余, 背压修复后安全)。与 bench 理想 18.6× 的差距 = prefill

tokenizer 并行 (ICU 线程安全)。或回引擎路径 B (monolithic MoE)。

## 2026-09-17 — serve 资源背压修复 (请求超限排队而非崩溃): 共享 prefill buffer + 阻塞 AllocSeqId + 连接上限

**背景**
并发压测 serve 时系统崩溃 (unified memory OOM → 系统级)。根因: 每请求独占
`d_logits` = [chunk, vocab] 最大 ~1 GB (长 prompt), 持有整个生命周期; max_seq=64
并发 → 64 × 1 GB = 64 GB 叠加在模型上 → OOM。且超 max_seq 的请求返回 503 (拒绝)
而非排队。

**做了什么** (src/server/chat_server.cpp + .h)
1. **共享 prefill logits buffer** `d_prefill_logits_` [max_prefill, vocab] (Start
   分配一次)。prefill 只需最后一行 (首 token), prefill 又都串行在 model_mu_ 后,
   故一个共享 buffer 足够。首 token D2H 移到 **持锁内** (下个 prefill 覆盖前读走)。
   fallback decode 也用它 (持锁)。**峰值内存不再随 prompt 长度 × 并发 增长**。
2. **阻塞 AllocSeqId (排队)**: seq slot 满时 CV 等待而非返回 -1/503 → 超 max_seq
   的请求**排队**, slot 释放时唤醒。FreeSeqId notify。析构 seq_stopping_ 唤醒退出。
3. **连接上限** `conn_cap_` = max(max_seq×8, 128): 原子计数 in-flight 线程, 洪泛超
   上限时 503 卸载, 防线程爆炸耗尽 host 内存。
4. MTP 的 `d_trunk_full` 用完 (draft-extend 后) 即释放, 不再持有到 decode。

**验证** (serve max_seq=16 max_len=2048, plain decode):
- 并发 8 (≤16): 256 tok, 0 error, 内存稳 88 GB。
- **并发 32 (2× 超限)**: 1024 tok 全完成, 内存稳 86 GB, 0 error, 存活 (排队生效,
  延迟 6→11.5s 但不崩)。
- **并发 64 (4× 超限)**: 1024 tok 全完成, 内存稳 86 GB, 0 error, 存活。
- **16 并发长 prompt (~1350 tok, 原 OOM 向量)**: 256 tok, 内存稳 86 GB 无增长,
  0 error, 存活 (旧代码 16×1GB=16GB 会 OOM)。
- 68 测试全绿零警告。

**继续优化**: 修复后回到批处理落地 (路径 C) —— serve 现可安全高并发压测, 下一步
量化并发聚合吞吐 vs 引擎 bench 的 18.6×。

## 2026-09-17 — 多流 MoE (per-expert 轮询多 CUDA 流填满 SM): prefill 990→1062 / 批 decode B=128 308→374 tok/s

**动机**
09-17 profile 定位: 批处理 decode 的 MoE 仅 ~34% 带宽, 根因 per-expert 小 GEMM
(M_e≈10 tok) 只生成 ~10 个 tile, 20 个 SM 只用一半 (SM 欠占用)。用户批准路径 A
(多流, 不量化, kernel 优化)。per-expert chain (gather→gu GEMM→swiglu→dn GEMM) 无
数据依赖 → 轮询到 N 个 CUDA 流并发, 填满 SM。

**做了什么** (src/quant/moe_gemm.cu)
- N 个流 (env `Q4T_MOE_STREAMS`, 默认 4; 1=旧单流 bit 不变)。流 0 = 调用方流 (复用
  ws+gemm_ws); 流 1..N-1 各自 a_packed/a_sf/gu_out ([M] 行足够, M_e≤M) + cuBLASLt
  workspace (并发专家不互相覆盖)。dn_out 按 per-expert offset 不相交写 → 共享。
- 输入就绪由 counts 的 host sync 保证; 组合前用 event 让调用方流等齐所有流。
- 数值**逐位不变** (各专家算同样的东西, 只是并发; 组合按固定 slot 序求和)。

**负→正 (persistent scratch 是关键)**
初版 per-call `cudaMallocAsync` 每流 32MB gemm_ws → 每步 48 层 ×3 流 ×32MB 分配,
**N=4 反而更慢** (B=128 308→291, B=1 16.8→7.1)。改为**持久 scratch** (静态池, 按最大
M 增长, 分配一次) 后**翻正**。教训: 多流的收益极易被 per-call 大分配吃掉。

**结果** (bench-decode --sweep, persistent):
| B | N=1 | N=4 | 提升 |
|---|---|---|---|
| 8 | 63.5 | 75.0 | +18% |
| 32 | 157.2 | 193.7 | +23% |
| 128 | 308.7 | **373.8** | +21% |

- **prefill (M=2560, ~50 tok/专家, 同样 SM 欠占用): 990→1062 tok/s (+7.2%, 破 1000)**。
- N=4 是甜点 (N=8 ≈ N=4, 373.8 vs 372.0 收益递减)。小 B 也小幅升 (B=1 16.8→17.9)。
- 68 测试全绿零警告, moe 数值逐位不变 (max_rel 0.0077468 / l2_rel 0.0098645),
  generate 输出连贯 ("Paris. The capital of Germany is Berlin.")。

**剩余 MoE 杠杆**: 多流吃到了 SM 欠占用那部分; host launch 开销 + 权重带宽仍在,
monolithic grouped FP4 MoE (路径 B) 是更大但更难的下一步。GDN decode 已地板。

## 2026-09-17 — 批处理 decode 吞吐标度实测: B=1→128 聚合 16.6→308.9 tok/s (18.6×)

**动机**
用户指出 1000 tok/s 是可用下限非上限, 要求推进批处理 (暂不量化, kernel 优化可做)。
Roofline (09-16) 已证 prefill 张量核 ~96% 空转、访存受限; decode 更甚 (单 token/
forward 加载全部 MoE 权重)。批处理正是填满空转张量核的正道 —— 实测验证。

**做了什么**
新增 `q4t bench-decode` 子命令 (src/main.cpp): prefill B 个不同 prompt 的序列 →
N 次打包 decode (`ModelDecodeBatchMulti`, T=B, per-seq 路由真实) → 报聚合 tok/s。
`--sweep` 一次加载 (max_seq=--batch) 扫 B=1,2,4,...,--batch (子集池化状态,
positions 钉在 [P,P+N) 使注意力范围恒定)。计时只前向 (无 argmax/D2H)。修一个自造
bug: 合成 token `(b*9973+step*131+7)%20000` 在 warmup step=-1 时 C++ 负取模 → 负
token id → EmbedLookup 越界; 改强制非负。

**实测标度曲线** (prompt=128, steps=64):
| B | 聚合 tok/s | tok/s/seq | ms/step |
|---|---|---|---|
| 1 | 16.6 | 16.59 | 60 |
| 2 | 21.7 | 10.87 | 92 |
| 4 | 37.7 | 9.44 | 106 |
| 8 | 63.3 | 7.91 | 126 |
| 16 | 101.5 | 6.34 | 158 |
| 32 | 155.9 | 4.87 | 205 |
| 64 | 225.4 | 3.52 | 284 |
| 128 | **308.9** | 2.41 | 414 |

**结论: 批处理 decode 聚合吞吐 B=1→128 提升 18.6× 且仍在爬升 (未饱和)**。ms/step
仅从 60→414 (128× token 只 6.9× 时间) → per-token 成本降 18.6× = MoE 权重摊销正是
roofline 预言。B<51 时激活专家数随 B 增 (权重加载线性增); B>51 专家近全激活, 权重
加载饱和, 加 token 更廉 (边际成本降, B=64→128 步时仅 1.46×)。

**B=128 瓶颈 profile** (nsys, cudaProfiler capture range 隔离 decode):
| kernel | % | 性质 |
|---|---|---|
| GatedDeltaNetDecodeKernel | 34.3% | SSM state 读写 804MB/层, 208 GB/s = **86% 带宽 = 地板** |
| MoE fp4 GEMM (gu+dn) | 24.4% | per-expert ~10 tok/专家, 权重 bound |
| SwiGLUQuant+GatherQuant | 16.4% | per-expert 量化 |
| BF16 投影 (cutlass wmma 16×16) | 7.8% | 小 M 投影 |
| SparseAttention | 1.9% | per-seq |

**关键洞察**: B=128 时 **MoE 仅跑 ~34% 带宽** (~13.7 GB 权重 / ~166ms), 根因 per-
expert 小 GEMM (10 tok/专家, 128×128 tile 只填 1/13) → 2-3× 浪费。GDN decode 则已
在 86% 带宽地板 (大 recurrent state 3MB/seq/层 × 36 层 = 108MB/seq, 每步全量读写,
架构固有, 无量化不可降)。

**下一杠杆**: MoE per-expert 结构是批处理吞吐的主杠杆 (34%→~82% 带宽有 2-3× 空间)。
monolithic grouped FP4 MoE (flashinfer trtllm 式, 一次 kernel 处理所有专家, 消除
per-expert launch + 更好 tiling) 同时惠及 prefill 与批处理 decode。GDN 已地板。
不涉及量化。
