## 补载管线（路径 C）代码核验：stage→commit 串行无重叠，可重叠优化（06:38）

第二轮候选在途（204800 档）期间核验补载管线（纯代码，无 GPU/构建）：
`Resolve()` 循环为 `LoadPhase1(stage, 并行 NVMe→L2) → LoadPhase2(commit,
串行 H2D→GPU slot) → LoadPhase1 → LoadPhase2 …`，**stage 与 commit 不重叠**
（每 chunk 先全部 stage 完再 commit，下一 chunk 在上一 chunk commit 后才
stage）。L2 buffer 复用靠 commit 的 CUDA event 保证安全，但当前实现未利用
event 做 stage/commit 重叠。路径 C 的具体优化点：(1) 用 commit event 重叠
「stage chunk i+1」与「commit chunk i」（隐藏 NVMe 时延于 H2D 之后）；
(2) LoadPhase2 的 H2D commit 目前逐专家串行，可多 stream 并行；(3) 提高
NVMe 并行度（load_threads_）。定量：单 miss 有效 6.2 ms 中 NVMe 仅
~1.44 ms，~4 ms 为管线开销（串行 commit + 无重叠 + 互斥/条件变量往返），
重叠+并行 commit 有望压到 ~2 ms（C=256 下 decode≈54% 基线，过门槛）。
属补载管线工程改动，GEMM 冻结、语义不变。待用户定 A/C 后实施；第二轮
实测落地前不动 build/q4t。
## 稳态机制核验：256 槽是 LRU 动态缓存；decode 导向热点表排除，补载管线优化升为路径 C（06:35）

第二轮候选在途（45056 档）期间做非重叠分析（纯 trace/代码，无 GPU/构建）：
(1) 静态 top-256 decode 覆盖（calib→policy 留出）：combined 63.6%、
decode-only 84.5%、prefill-only 61.1%（.q4t-work/decode_hotlist_analysis.py，
sanity：combined top-256 与冻结 hot-256 46/48 层一致）。(2) 但运行时稳态
decode miss 仅 5.3%（45056 档 dmiss=6539/dlook=122400），远低于静态覆盖——
代码核验根因：`moe_hot_protect` 默认 false（r2 未传 --moe-hot-protect），
`SetHotProtected()` 不调用，256 槽是**热启动 LRU 动态缓存**（evictions==
loads==418662，槽常满持续换入换出），稳态 miss 由「LRU 容量 256 vs 逐层
decode 工作集 ~250 专家」决定，与热点表选择几乎无关。

推论：**decode 导向热点表只改善冷启动、不改善稳态，对 50% 门槛基本无效，
排除**。有效路径剩两条：A（第三轮增 C，nu-15552 推荐 ≈68.8 GB，新增超支）
与 C（补载管线优化，不增内存：并行 NVMe 读+消除 ~4 ms 管线开销，单 miss
6.2→~2 ms，定量 C=256 下 decode≈54% 基线可达门槛，GEMM 冻结、语义不变）。
决策包 docs/MOE_RESIDENCY_R3_DECISION_2026-10-01.md 已回填机制澄清与双路径
决策项。下一步：第二轮矩阵完成 → compare-report-r2.txt → 向用户提交 A/C 决策。
