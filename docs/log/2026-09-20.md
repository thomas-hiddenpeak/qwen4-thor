## 2026-09-20 — 五档 HTTP 时间线完成，确认尾部无用前向与 200K top-k 成本

**结果**：已通过 E2E 的同一二进制上，Nsight 只采集加载后的真实请求，
五档各一条，实际输入准确、输出 256、正常 length、摘要全部与正式参考

没有修改运行时逻辑；仅更正 bitonic 注释中“流式 indexer 成本很小”的
失实断言。无 bench，无前置低层测试。

**事实**：五档每条 256 输出都有 256 次 decode embedding/argmax/结果回读，
首 token 来自 prefill，最后一次前向没有消费者。decode BF16 GEMV 占累计
kernel 时间 53%–60%；每步 48 次专家 counts D2H、698 次 cudaMallocAsync。
200K prefill merge top-k 累计 63.35 秒（24.59%），sparse attention 22.84%；
44K merge 7.12%，需按长度分开判断。未消费的 prefill head 投影存在，
但 200K 对应投影约 175.5 ms，远非该档主因。

**边界**：采集使 decode 时段比正式基线长约 7.8%–9.9%，不回填性能参考。
GPU busy 按区间并集，kernel 累计占比不等于窗口占比；API 等待与 GPU 重叠，
不能相加。未测实际 DRAM 字节或精确 CPU ModelPrefill 时间。1K 是首请求。

**下一步**：先单独去掉生成尾部无用前向，真实 E2E 包含 max_tokens=1 和
原五档；后续分别研究 200K 精确 top-k 归并和 decode workspace/host 控制。

## 2026-09-20 — prefill T=8192 nsys profile: 推翻 P0 路线图 (SparseAttention + GDN 循环是真瓶颈)

**做了什么**: nsys profile 包裹 serve --max-seq 1 --max-prefill 8192, 发 1 个
  8194-token 请求 (8.33s wall), 提取 GPU kernel 时间构成 (nsys stats

**关键结果**: 总 GPU kernel 8.377s, 时间线窗口 8.317s — **GPU 满负荷, 无
  idle 间隙** (host 开销不是瓶颈)。时间构成: **SparseAttentionKernel 2.268s
  (27%, 最大单点)** + **GatedDeltaNetRegKernel<8> 1.345s (16%)** + MoE 量化
  (GatherQuant 0.418 + SwiGLUQuant 0.397) 0.82s (9.7%) + GEMM nvjet 全部

  conv (CausalConv1dWithCkpt) 0.22s (2.6%)。

**为什么重要 (推翻 P0)**: 文档 §4.2 的 P0 (GDN ①+③+④ conv/norm 融合 + HC

  已落地")。源码确认 SparseAttention 是 **KV 散射 gather 带宽/延迟受限**

  recurrent scan 延迟受限** (grid 192 blocks, 20 SM 占用率低)。"先测量再
  决定" 原则兑现 (计划 D 教训的正面版本): **新 P0 = SparseAttention (2.27s)
  + GDN 循环 (1.35s)**。

**下一步**: 优化 SparseAttention (第一靶点, 27%) — 方向: (a) 提高 gather
