## 2026-09-20 — SparseAttention topk 排序 E2E 负结果 (已回退, 流程纠正)

**做了什么**: 按用户 E2E-first 指令 (任何改动必须在 API 上 E2E 评估), 针对
  nsys 确认的 prefill SparseAttention 瓶颈 (13 个 gridX=8192 慢实例各 ~170ms
  占 97.5%) 实施 `SortTopkByPosKernel`: 在 SparseAttentionKernel 前把每 token
  的 topk 位置按 position 升序重排 (恒等 page table 下 slot==position →
  gather 变近似顺序读 → DRAM row locality)。q4t_tests 76 项全过, 零警告。

**E2E 结果 (evalscope)**: 短 prompt conc 1/4/8 = 21.88/37.46/~57 tok/s
  (基线 21.6/31.4/57.1, 无回退); **长 prompt 8192 TTFT 7580→7751ms, 回退
  171ms**。排序 kernel (bitonic 4096 × 144 轮 syncthreads × 8192 blocks ×
  12 层) 开销 > locality 收益。

**为什么重要**: (1) 负结果已回填 DATAFLOW_OPTIMIZATION.md §4.7, 排除
  "scatter locality" 方向 — kernel 已达 176GB/s (72% 峰值), 剩余差距是
  延迟隐藏/cp.async 粒度, 不是地址顺序。(2) 流程纠正: 此前花大量时间修
  与生产不同步的 bench (漏拷 d_pos 致 topk_len=1, 测出 17ms vs 生产 170ms,
  差 10×) 被用户否决; 本次严格走 生产 nsys 定位 → 改生产 kernel →
  q4t_tests 验正确性 → evalscope E2E 验收 的闭环, E2E 暴露了理论假设
  (locality 必赢) 的错误。生产代码已回退干净, 零警告。

**下一步**: SparseAttention 剩余方向 (gather 批量/向量化, 减少 gather 字节
  需保召回, 延迟隐藏深度); GDN 循环 (1.35s, 16%) 并行度/chunked scan。
  均按同一 E2E 闭环执行。

## 2026-09-20 — prefill T=8192 nsys profile: 推翻 P0 路线图 (SparseAttention + GDN 循环是真瓶颈)

**做了什么**: nsys profile 包裹 serve --max-seq 1 --max-prefill 8192, 发 1 个
  8194-token 请求 (8.33s wall), 提取 GPU kernel 时间构成 (nsys stats
  cuda_gpu_kern_sum + sqlite 聚合)。结果回填 DATAFLOW_OPTIMIZATION.md §4.6。

**关键结果**: 总 GPU kernel 8.377s, 时间线窗口 8.317s — **GPU 满负荷, 无
  idle 间隙** (host 开销不是瓶颈)。时间构成: **SparseAttentionKernel 2.268s
  (27%, 最大单点)** + **GatedDeltaNetRegKernel<8> 1.345s (16%)** + MoE 量化
  (GatherQuant 0.418 + SwiGLUQuant 0.397) 0.82s (9.7%) + GEMM nvjet 全部
  ~1.3s (17%) + HC (CombineWithGate 0.347 + MixGate 0.270) 0.62s (7%) + GDN
  conv (CausalConv1dWithCkpt) 0.22s (2.6%)。

**为什么重要 (推翻 P0)**: 文档 §4.2 的 P0 (GDN ①+③+④ conv/norm 融合 + HC
  融合) 基于 "347GB 激活字节" 估算, 但**实测时间大头是延迟/带宽受限的
  SparseAttention (27%) + GDN 循环 (16%), 合计 43%** — 这两个 kernel 文档
  恰恰标成 "已最优/不动" (§3.3 "tensor core 已最优" / §3.2 "register-state
  已落地")。源码确认 SparseAttention 是 **KV 散射 gather 带宽/延迟受限**
  (grid=(T,nkv)=16384 blocks, 每 block CpAsync16 散射读 512 topk 位置的
  K/V, QK/PV mma 仅 3.9 TFLOPS=1.5% 峰值, 非算力); GDN 循环是**顺序
  recurrent scan 延迟受限** (grid 192 blocks, 20 SM 占用率低)。"先测量再
  决定" 原则兑现 (计划 D 教训的正面版本): **新 P0 = SparseAttention (2.27s)
  + GDN 循环 (1.35s)**。

**下一步**: 优化 SparseAttention (第一靶点, 27%) — 方向: (a) 提高 gather
  带宽 (更大 cp.async 批量/向量化); (b) 减少 gather 字节 (topk 512 是否可
  降, 需保召回); (c) 提高 SM 占用率。


## 2026-09-20 — evalscope E2E 吞吐基线: 短 prompt 并发 + 长 prompt TTFT

**做了什么**: 搭 tools/evalscope/ uv 环境 (uv venv + uv pip install
  'evalscope[perf]' 1.12.0, 含 transformers 5.17.0), 固化
  tools/evalscope/run_baseline.sh。serve 配置 --max-seq 8 --max-prefill 8192
  --max-len 16384 (MTP k=3, 连续批处理), 模型加载 30.7s (weights 84GB +
  fixed 98.2GB budget)。random 数据集, OpenAI 兼容 API, stream。结果回填
  DATAFLOW_OPTIMIZATION.md §4.5。

**关键结果**: 短 prompt (256/256) 并发 1/4/8 聚合 21.6/31.4/57.1 tok/s
  (TTFT 440/1063/1965ms, TPOT 44/75/110ms, 100% 成功); 长 prompt 8192
  (gen 64): **TTFT 7.58s, prefill ~760 tok/s**, TPOT 52ms。单请求 decode
  22.5 tok/s 与 STATUS 记录 (~21.8) 一致, 基线可信。

**为什么重要**: 这是数据流优化的端到端"尺子" — 任何 kernel 改动最终要在这
  把尺子上兑现。长 prompt TTFT 7.58s 是用户 agent 工作负载 (40K-200K) 的
  痛点入口 (prefill 760 tok/s → 200K prompt TTFT >4 分钟); prefill 优化
  (P0 = HC + GDN 融合) 直接打这个 TTFT。40K-200K 超出 max_prefill=8192,
  需分块 prefill (PHASES.md 262K 预算), 本轮基线只覆盖 ≤8192。

**踩坑**: ① uv init 项目名 evalscope 与依赖包名冲突 → 改 uv venv + uv pip
  install; ② evalscope perf 需额外依赖 uvicorn → 装 'evalscope[perf]';
  ③ --tokenizer-path 要传目录不是 tokenizer.json 文件; ④ 默认 dataset 需
  下载 (无网) → 用 --dataset random (本地生成); ⑤ --parallel 多值时
  --number 必须等长。

**下一步**: 按 P0 开始 HC 融合 (HC-A rmsnorm+down+inject 合一 / HC-B
  combine 去冗余) 实施, 验收 = 长 prompt TTFT 下降 + 短 prompt 聚合不回归。


## 2026-09-20 — gemm_roofline_bench 尺子: BF16 库利用率实测, Pole 2 修正

**做了什么**: 造 tools/gemm_roofline_bench.cu (CMake target
  q4t_gemm_roofline_bench), 忠实复刻模型 Bf16Gemm 路径 (CUBLAS_COMPUTE_32F
  + BF16 + FP32 累积 + 禁 split-K), 测 9 个真实 dense GEMM shape ×
  T∈{1,8,512,8192} 的 cuBLASLt TFLOPS vs SM110a BF16 峰值 259 TFLOPS。
  结果回填 DATAFLOW_OPTIMIZATION.md §4.4 + 修正北极星 §0.0.3。

**关键结果 (T=8192)**: GDN in_proj_qkv 158 TFLOPS (61%) / QSA qg 187 (72%)
  / HC inject 161 (62%) / lm_head 144 (56%) — 库在 BF16 大 GEMM 上 46-72%
  峰值, **不是 <10%** (那是 NVFP4 的事)。真正库低效点在瘦 GEMM: **HC down
  (N=320) 仅 40 TFLOPS (15.5%) / HC up 75 (28.8%)**。prefill GEMM 时间账
  T=8192 ≈786ms/forward, **HC 占 56%**。

**为什么重要 (修正北极星)**: "手写 tcgen05 赢库 5-6×" 在 BF16 大 GEMM 上
  **不成立** — 库已 61-72%, 手写难超越。Pole 2 在 BF16 大 GEMM 上没那么大,
  机会集中在瘦 GEMM (HC down/up), 且与 Pole 1 (HC 中间激活搬运) 重叠 —
  HC 融合同时打两极。这强化了 P0 = HC + GDN, 但 HC 的赢法是**融合**
  (HC-A rmsnorm+down+inject 合一, 省 normed 2× 重读 + 瘦 GEMM 低效), 不是
  手写大 GEMM。

**下一步**: evalscope E2E 吞吐基线 (tools uv 环境) → 回填 → 按 P0 开始
  HC 融合 (HC-A/HC-B) 实施。

## 2026-09-20 — 数据流驱动的逐级优化分析: 5 环节搬运账单 + L1/L2/L3 路线图

**做了什么**: 用户提出"专用 runner 按数据流向逐环节手写 kernel"方向,
  要求先整理整个推理过程数据流再逐环节讨论。逐环节读真实源码整理数据流
  + 搬运账单 + 四维度分析, 落文档 docs/DATAFLOW_OPTIMIZATION.md (468 行,
  方法论/数据流/5 环节/路线图/约束)。

**为什么**: 用户认为之前思路是参考项目延续, 专用模型+专用设备应针对
  全部硬件 (寄存器/缓存/SM/tensor core) 按数据流向设计每个环节; 约束
  (带宽/容量/指令开销) 逐层逐级, 分次序分级别 (L1 带宽无效搬运 → L2
  降复杂度 → L3 融合)。

**关键发现** (全数据驱动, 基于源码静态分析):
- 核心结构: 窄流 [T,2560] 计算 / 宽流 [T,10240] 残差 (HC 4 分支, 4×),
  宽窄桥低秩 320 是无效搬运结构性来源。
- 分场景决定性: decode T=1 激活 <0.3% (纯权重带宽地板 241GB/s 已闭合,
  无空间); prefill T=8192 激活:权重 ≈15-20× (主战场, 正对 agent 40K-200K
  场景)。
- 总账: prefill 激活 ≈347GB/forward, 可省 ≈82.8GB (24%), 与权重读取同
  量级。GDN 32GB (44%) + HC 42.2GB (27%) 是 P0; MoE/QSA GEMM 全 tensor
  core 已最优 (手写打不过, 已证), 只动 elementwise 链。
- MoE ② (persistent token-parallel, 17.3GB) 否决: 需重写调度模型且可能
  失去 nvjet → 净损失。QSA ③ 不可行 (数据依赖)。

**下一步**: 待用户裁决 (先插桩实测确认 347/82.8GB 估算 / 直接 GDN
  ①+③+④ 低风险 bit-exact 21.6GB)。技术哲学讨论继续。
