## 2026-09-20 — 数据流驱动的逐级优化分析: 5 环节搬运账单 + L1/L2/L3 路线图

**做了什么**: 用户提出"专用 runner 按数据流向逐环节手写 kernel"方向,
  要求先整理整个推理过程数据流再逐环节讨论。逐环节读真实源码整理数据流
  + 搬运账单 + 四维度分析, 落文档 docs/DATAFLOW_OPTIMIZATION.md (468 行,
  方法论/数据流/5 环节/路线图/约束)。

**为什么**: 用户认为之前思路是参考项目延续, 专用模型+专用设备应针对
  全部硬件 (寄存器/缓存/SM/tensor core) 按数据流向设计每个环节; 约束
  (带宽/容量/指令开销) 逐层逐级, 分次序分级别 (L1 带宽无效搬运 → L2
  降复杂度 → L3 融合)。

**关键发现** (全数据驱动, 基于源码静态分析):
- 核心结构: 窄流 [T,2560] 计算 / 宽流 [T,10240] 残差 (HC 4 分支, 4×),
  宽窄桥低秩 320 是无效搬运结构性来源。
- 分场景决定性: decode T=1 激活 <0.3% (纯权重带宽地板 241GB/s 已闭合,
  无空间); prefill T=8192 激活:权重 ≈15-20× (主战场, 正对 agent 40K-200K
  场景)。
- 总账: prefill 激活 ≈347GB/forward, 可省 ≈82.8GB (24%), 与权重读取同
  量级。GDN 32GB (44%) + HC 42.2GB (27%) 是 P0; MoE/QSA GEMM 全 tensor
  core 已最优 (手写打不过, 已证), 只动 elementwise 链。
- MoE ② (persistent token-parallel, 17.3GB) 否决: 需重写调度模型且可能
  失去 nvjet → 净损失。QSA ③ 不可行 (数据依赖)。

**下一步**: 待用户裁决 (先插桩实测确认 347/82.8GB 估算 / 直接 GDN
  ①+③+④ 低风险 bit-exact 21.6GB)。技术哲学讨论继续。
