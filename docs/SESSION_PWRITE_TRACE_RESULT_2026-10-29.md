## 为什么没有放行HTTP，哪些记录仍可用

原能力审计发现：raw NVMe setup、CQ处理、complete各265条，带格式的
setup265条，但带格式的CQ处理和complete各259条。ring丢失、map失败、
栈失败计数均0，2343条已发事件全部落盘；**这些计数只证明已发事件没有
在该传输环节丢失，不保证每次探针都执行。** 原审计保留为失败。

随后仅对原记录作离线审查，得到补充结论：

1. 全部265对setup可按相同task/CPU、明确事件顺序和逐项相同CID配对，
   从而把控制器、队列和CID关联到全部265条raw completion。故6条
   **次级记录缺口不能解释成实际设备完成丢失**，有效主链并未丢弃。
2. 6个缺口均在控制器0、队列5、CPU4；所有raw NVMe事件都位于捕获的
   syscall区间内。不能用“pwrite退出后active过滤”单独解释，精确原因
   未证实。没有采集探针重入/内核侧跳过计数，不能宣称已定位成内核丢事件。
3. ring顺序存在3处时间戳逆序；源码在reserve后取时间，中断可插入。
   顺序和时间戳必须分别处理，不能按相邻记录盲目相减。

**停止依据是完整工具合同未在20分钟预算内完成，不是文件大小，也不只是
6条冗余记录数量不等。** 现有脚本仍依赖夹具提供文件代次；没有完成
fd/inode/request/CID复用、merge/requeue/partial completion、丢事件及
对抗性重排的通用解析合同。采集器统一RAM峰值、落盘干扰、整阶段驱动、
diskstats/SMART边界也未验收。离线补回setup标识不能把这些缺项变成通过。
因此不在两次夹具耗尽后追加第三次，不用未验证工具占用模型HTTP额度。

## 三层归因与工程决定

| 维度 | 本轮结论 |
|---|---|
| 文件系统 | 可见映射、journal相关事件及位图读取等待栈；未量化旧慢保存的秒数 |
| 块层排队 | 小夹具request生命周期和字节闭合；提交前等待及通用解析合同未完整验证 |
| 设备完成 | raw完成主链有效，次级事件有缺口；没有旧慢保存的设备区间，更非NAND耗时 |
| 证据有效性 | CPU记录部分有效、原始数据完整保存；不丢弃有效窗口 |
| 测量完整性 | 能力检查按停止出口结束；20HTTP/两head恢复观测未执行 |
| 统计结论 | 没有新的模型性能、因果回归或非劣结论 |
| 工程决定 | STOP / TOOL_UNAVAILABLE，不扩样、不安装、不合main |

旧慢写仍不能在文件系统、块排队和设备完成之间定量归属。本轮未尝试
重现模型慢窗口，不能写成“模型慢写未复现”。复用原A112五档/质量、S32
两head重复收益、40HTTP/8次覆盖后恢复/68项CPU存储合同，以及未变目标/
草稿状态合同；这些证据不会因研究工具未完成而作废。

后续若重开，范围应先限于**工具修复**：以已完整的raw request主链和
setup身份减少对次级完成事件的依赖，补齐文件代次及离线异常生命周期
合同、解释次级缺口和时间戳顺序，再决定是否有资格进行HTTP。这里没有
自动续预算、追加试验或承诺已能完成三层秒数分解。
